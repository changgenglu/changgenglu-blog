# 用 release tag 判斷功能是否已上線

> 一次跨團隊溝通中，雙方都用「主幹分支有沒有包含那個 commit」來判斷功能是否已經上線，結果判斷錯了。這篇記下正確的判斷方式與幾個指令。寫於 2026 年。

## 問題與背景

情境是這樣的：某個修復已經合併、也已經部署。幾小時後有人問「這個修好的東西上線了嗎？」

雙方當時用的是同一個判準：**看 `master` 有沒有包含那個 commit**。當時 `origin/master` 還停在較舊的位置，部署系統上也查不到對應的部署紀錄，於是「已上線」被改成「待證實」。

結果判準本身是錯的。這個專案的進版流程是：

1. 在功能分支或獨立的發版分支上打 **版更 tag**（例如 `v20260101001`）。
2. 從 tag 部署。
3. 事後才把 `master` 拉到那個 tag。

也就是說，**tag 先於 `master`**。`master` 含不含某個 commit，跟「有沒有上線」沒有關係。對方隔天主動更正，並確認「已更新上線、目前沒有問題」。

## 結論

**判斷有沒有上線，看「版更 tag 指向哪個 commit」，不是看 `master`。**

前提：你的流程是「從 tag 部署」。如果你的流程是「從 `master` 自動部署」，那 `master` 才是判準。**先確認流程，再選判準**；流程文件不夠時，不能拿它當證據，要用部署紀錄或 tag 實際比對。

## 怎麼判斷

以下用一個完全虛構的例子：要確認 commit `abc1234` 是否已經在 tag `v20260101001` 裡。

### 1. 這個 tag 指向哪個 commit

```bash
git rev-list -1 v20260101001
```

`rev-list -1` 會輸出 tag 最終指向的 commit 雜湊。對 annotated tag（有訊息、有簽署者的 tag），這個指令會自動穿透到底層的 commit。

如果只用 `git rev-parse v20260101001`，annotated tag 會得到「tag 物件」本身的雜湊，不是 commit，容易拿來比對出錯。想明確要 commit，可以寫成：

```bash
git rev-parse 'v20260101001^{commit}'
```

### 2. 某個 commit 是不是這個 tag 的祖先

```bash
git merge-base --is-ancestor abc1234 v20260101001 && echo "已包含" || echo "未包含"
```

`--is-ancestor A B` 的意思是「A 是不是 B 的祖先（包含 A 本身）」，結果用 exit code 回傳（0 是、1 否），很適合寫進腳本。

### 3. 反過來問：哪些 tag 包含這個 commit

```bash
git tag --contains abc1234
```

列出所有包含該 commit 的 tag，通常最早出現的那個就是第一次上線的版本。

### 4. 驗證「tag 先於 master」這件事

```bash
git merge-base --is-ancestor v20260101001 origin/master && echo "master 已拉到此 tag" || echo "master 尚未拉到此 tag"
```

如果輸出「尚未」，而你已經從該 tag 部署，這就是「tag 先於主幹」流程的正常狀態，不是異常。

## 這個案例實際驗證到的事

我當時是用上面的方式獨立（唯讀）驗證的：

- 最新的版更 tag（annotated tag）指向的 commit，正是那個修復的 commit。
- 版更 tag 有固定的日期加流水號慣例（例如 `v20260101001`、`v20251231001`……），而且成序列存在。
- 最新的 tag **不是** `origin/master` 的祖先，正好佐證「tag 先於 master」。

## 踩過的坑與教訓

- **兩邊用同一個錯判準，不會因為「兩個人都這樣想」就變對**。當時雙方都沿用「看主幹」的直覺，沒人先確認對方的進版流程。
- **「查不到部署紀錄」不等於「沒上線」**。如果部署紀錄不是你有權限看的系統，或紀錄的記法和你預期不同，就只能說「無法確認」，不能說「沒上線」。當時的措辭選了「無法確認」，事後證明這個保守措辭是對的。
- **跨團隊的流程，先問清楚再下結論**。每個團隊的分支與發版慣例不同，用自己團隊的慣例去推論別人的系統，很容易錯。
- **更正要保留軌跡**。當時任務卡上分兩次記錄：第一次寫「待證實」及依據，第二次寫「依據已證實錯誤，撤回」，並保留原本的推論過程，之後才查得到為什麼會判斷錯。
- **ref 的真值用 `git rev-parse`、`git rev-list` 取得**。有些壓縮或過濾過的 `git log` 輸出會省略 merge commit，頂端看起來可能像「HEAD 退回去了」，不能拿來當 ground truth。
- **查遠端有哪些 tag，用 `git ls-remote --tags`**，不要順手 `git fetch --prune-tags`：後者會把遠端沒有的本地 tag 全部刪掉，其中包含你純本地的備份 tag，而 lightweight tag 刪了很難救回。

## 檢查清單

- [ ] 這個專案是從 tag 部署，還是從主幹自動部署？先確認。
- [ ] 用 `git rev-list -1 <tag>` 拿到 tag 實際指向的 commit。
- [ ] 用 `git merge-base --is-ancestor <commit> <tag>` 確認該 commit 在不在這個 tag 裡。
- [ ] 查不到部署紀錄時，回答「無法確認」，不要回答「沒上線」。
- [ ] 判斷錯了，更正時保留原本的推論與修正依據。
