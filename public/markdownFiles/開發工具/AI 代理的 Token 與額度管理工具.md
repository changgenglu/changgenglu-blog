# AI 代理的 Token 與額度管理工具

> 這篇整理我在 2026 年看過的幾類「管 token、管額度」的工具與觀念：量花費、壓縮內容、狀態列顯示、效能量測，以及雲端額度政策變動。主要用 Claude Code 當例子，大部分觀念也適用其他 coding agent。

## 問題與背景

用 coding agent 久了，會碰到兩種不同的痛：

- **帳單或額度燒得比預期快**，但不知道燒在哪裡。
- **額度突然不夠用**，同樣的用法前一個月沒事，這個月就撞牆。

這兩件事需要的工具不一樣。我把市面上看到的工具分成四層，先分清楚「它管哪一層」，比比較功能多寡更重要：

| 層次 | 要回答的問題 | 本文的例子 |
|---|---|---|
| 量測 | token 花在哪個模型、專案、子代理、skill | CodeBurn |
| 壓縮 | 送進模型的內容能不能變小 | Headroom |
| 顯示 | 目前 context 用了多少、壓縮過幾次 | ccstatusline |
| 效能 | 每次工具呼叫之間的額外延遲是多少 | toolrush 的量測方法 |

另外還有一層不在自己掌控內：**供應商的額度政策**。這一層沒有工具可以裝，只能查證與調整用法，放在文末。

## 結論先講

- **先量再壓縮**。沒有量測就動手壓縮，只是憑感覺。能零安裝跑一次報表的工具（例如 CodeBurn 的 `npx` 用法）CP 值最高。
- **壓縮工具的宣稱數字要看內容種類**。工具輸出大量 JSON 或 log 的流程，壓縮空間大；以規則、決策文字為主的流程，空間小很多。
- **你是按 token 計費還是訂閱制，決定哪些優化有意義**。訂閱制下，「省錢」的賣點大多變成零，剩下的是速度與少撞用量上限。
- **常駐載入的檔案（CLAUDE.md、規則檔）要把 prompt cache 算進去**，否則排名會失真。
- **額度突然變緊，先查是不是平台級變動**，再決定是不是自己的用法出了問題。

## 量測：CodeBurn

[CodeBurn](https://github.com/getagentseal/codeburn) 是一個本機優先的 CLI，讀磁碟上既有的 session 檔，把花費拆成「工具 × 模型 × 專案 × 任務種類 × 子代理」多個維度。依它的說明，支援 36 種 AI 工具，包含 Claude Code、Cursor、Codex、Gemini CLI 等。

### 為什麼我覺得它值得記一筆

1. **不需要裝 hook、不改設定檔**。核心報表只讀 `~/.claude/projects/` 底下的 JSONL 對話紀錄，跑完就結束，沒有常駐程序。
2. **能拆到子代理與 skill 這一層**。Claude Code 的子代理 transcript 放在巢狀目錄（`subagents/`，工作流程再深一層），一般的扁平掃描會漏掉，它有特別處理，所以「哪個子代理佔比高」能直接看到。
3. **預設不外送資料**。README 寫明沒有 wrapper、沒有 proxy、不需要 API key。例外是選配功能（團隊用的 sync 是預覽階段）以及 MCP 工具，MCP 回傳的內容會進對話上下文，所以預設會把專案名稱假名化。

### 臨時查看的用法

```bash
npx codeburn overview                      # 本月總覽：按工具、按模型、按專案
npx codeburn models --by-agent -p week     # 近 7 天，按子代理種類拆花費
npx codeburn models --by-task -p week      # 近 7 天，按任務種類拆花費
npx codeburn optimize -p week              # 找「定義了但從沒被呼叫」的代理、skill
```

需要 Node.js 22.13 以上。我只評估了這種「零安裝臨時查看」的用法，沒有裝它的守門 hook（`guard`）、MCP 或桌面外殼。

### 設計上值得學的幾點

- **外殼不重複實作核心**：選單列 App、桌面 App 等都只是呼叫同一個 CLI 印出的 JSON，邏輯漂移的風險集中在一處。
- **診斷指令要保證零副作用**：`doctor` 明講全程離線、唯讀、不寫快取，這樣使用者懷疑哪個工具偵測錯了，才有一個乾淨的基準線。
- **單一 provider 壞掉不拖垮整份報表**：每個資料來源的解析錯誤各自顯示一行 ERROR。
- **訊號不是判決**：README 的「訊號對照表」（cache 命中率偏低、一次成功率偏低、小任務用了最大的模型……）都明講「這些是起點，不是結論」。
- **用真實呼叫紀錄反查「幽靈元件」**：把 transcript 裡實際出現過的代理、skill、指令，跟你設定目錄裡定義的清單對帳，找出從沒被用過的。這個「拿使用紀錄當 ground truth」的角度，比只看檔案時間戳的健檢更準。

### 限制

我只讀到它約五成的程式碼（核心解析、守門、MCP 等關鍵機制有讀，桌面外殼與 31 個 provider 的個別解析沒有逐檔驗證）。`guard` 與其他 PreToolUse hook 同時掛載時的執行順序，只是從原始碼推論，**未實測**。

## 壓縮：Headroom

[Headroom](https://github.com/chopratejas/headroom) 自稱是「AI 代理的 context 壓縮層」：在 prompt、工具輸出、log、RAG 片段、對話歷史送進模型**之前**做內容感知壓縮，宣稱可省 60 到 95% 的 token，答案不變，而且**可逆**。

### 它怎麼做

- **依內容種類選壓縮器**：JSON、程式碼（用語法樹）、純文字各用不同方法，避免「一種壓縮套所有內容」造成失真。
- **可逆壓縮**：原文留在本機，模型需要時再用工具把原文取回來。這解決了「壓縮就是永久丟資訊」的痛點。
- **穩定前綴**：讓請求的開頭部分維持不變，提高供應商端 prompt cache 的命中率；如果壓縮破壞了前綴，反而會推高快取寫入成本。
- **四種介面共用同一條管線**：函式庫、本機 proxy、MCP server、`headroom wrap claude|codex|cursor|aider|copilot` 一鍵包裝。
- **壓縮停用時退化成純轉發**，不需要下載模型，受限網路也能用。

README 也很誠實地把另一個 CLI 輸出壓縮工具 RTK（Rust Token Killer）列為對手，並標出「可逆」這一欄；同時說明它內建 RTK，兩者定位是疊加而非互斥。

### 我的評估

我沒有全量採用，理由有三個：

1. **整合成本偏重**：要下載 ONNX 執行環境與 Hugging Face 模型、telemetry 預設開啟、把全部流量導到第三方本機 proxy 在 WSL 下有網路設定風險。
2. **宣稱數字有場景前提**：92% 這類數字來自「大量工具輸出、大 JSON」的流程。我的場景偏規則與決策文字，內容種類的交集只有中等（我粗估 40 到 50%，**這是推測，沒有實測**）。
3. **訂閱制讓「省錢」賣點失效**（下一節詳述）。

如果要試，建議的順序是：

```bash
export HEADROOM_TELEMETRY=off
pip install "headroom-ai[proxy]"
headroom proxy --port 8787     # 先用「純轉發」模式量 baseline，再開壓縮對照
```

純 proxy 模式可以隨時關閉還原，沒有持久化的副作用。

### 訂閱制與 API 計費的前提修正

這份評估一開始是用「按 token 計費的 API」框架寫的，後來發現前提不對：我實際用的是**訂閱制**（月費加用量上限）。修正後的結論：

- 用歷史資料算出來的美金金額，只是「假如用 API 計費的換算值」，不是真實帳單。token 數字是真的，乘上單價才不是。
- **prompt cache 的存活時間（5 分鐘或 1 小時）不是使用者能調的旋鈕**，由組請求的程式決定。想靠定時送訊息「保溫」快取，在訂閱制下是淨損：省下的是你本來就不付的錢，卻消耗用量額度。
- 壓縮工具的核心賣點「省 90% token 等於省錢」，在月費制下收益是零，只剩速度與少撞上限。
- 唯一仍然有效、而且完全在自己掌控內的槓桿：**縮小常駐 context**（瘦身 CLAUDE.md 與規則檔、適時 `/compact` 與 `/clear`）。

訂閱方案如何把快取 token 計入用量上限，我沒有查到確切規則，**未驗證**。

## 顯示：ccstatusline 與「兩種資料來源」

[ccstatusline](https://github.com/sirmalloc/ccstatusline)（我評估的是 v2.2.22）是 Claude Code 狀態列的客製工具。我當時想做六個自訂指標，評估可行性時發現一個很通用的觀念：

| 資料來源 | 內容 | 取得成本 |
|---|---|---|
| **stdin JSON**（Claude Code 每次呼叫狀態列指令時餵進來） | 當下快照：模型、花費、context 使用率、worktree、用量上限窗 | 零 |
| **transcript 檔**（對話的 JSONL 全文） | 逐則訊息的 usage、工具呼叫（含 skill）、壓縮邊界標記 | 要讀檔、解析，還得顧慮刷新頻率 |

官方文件**只規範 stdin JSON**。所以如果只看 JSON，會得出「壓縮次數、skill 清單、單輪 token 不可行」的結論。但 ccstatusline 實際出貨了這些 widget，因為它**額外解析 transcript**，並用本機快取與雜訊過濾（例如忽略小於 1% context 的瞬時讀數，避免假計數）把成本壓下來。

所以評估「這個指標做不做得到」時，要分清楚：資料在 stdin 快照裡，還是要從 transcript 補。後者可行，只是要付解析成本。

### 六個指標的可行性結果

| 指標 | 做法 | 可靠度 |
|---|---|---|
| context 壓縮次數 | 內建 widget，數 transcript 裡的壓縮邊界 | 高 |
| 最後對話時間 | 自訂指令讀 transcript 檔的修改時間 | 高 |
| prompt cache 倒數 | 官方與工具都沒暴露 TTL，只能用「最後活動加 300 秒」推估 | **低，僅供心理參考** |
| 本 session 用過哪些 skill | 內建 widget，解析 transcript 的 skill 呼叫 | 中高（是「用過」不是「此刻仍在 context」） |
| 這一輪問答的 token 總量 | 內建的 per-turn scope；stdin 的 `current_usage` 只是最新一次回應的快照，不是整輪累加 | 中高（近似） |
| 設定檔最後優化時間 | 自訂指令讀某個標記檔的修改時間 | 高 |

其中「cache 倒數」最弱，因為 5 分鐘是 API 端的實作細節，可能改，而且 transcript 修改時間不等於 API 呼叫時刻。我用 `~` 前綴標明這是推估值。

### 一個 worktree 的小坑

如果你的 `.claude/` 目錄被 git-ignore、又用腳本在每個 worktree 之間同步，**讀「檔案修改時間」的指標必須指向全域路徑**（例如 `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/...`），不能用相對路徑。否則每個 worktree 各看各的副本，數值不一致或缺失。讀 transcript 的指標則不受影響，因為它跟 session 綁定。

### 自訂指令範例

```bash
#!/usr/bin/env bash
# last-activity.sh：最後對話時間（statusline JSON 由 stdin 進來）
json=$(cat)
tp=$(printf '%s' "$json" | jq -r '.transcript_path // empty')
if [ -n "$tp" ] && [ -f "$tp" ]; then date -r "$tp" "+%H:%M"; else echo "--:--"; fi
```

這類「自訂指令吃整包 JSON」的逃生口設計很值得學：官方沒給的指標，都能用腳本補。

## 效能：toolrush 的量測方法

[toolrush](https://github.com/OnlyTerp/toolrush) 是為 [Hermes Agent](https://github.com/NousResearch/hermes-agent) 做的工具呼叫加速層。它的論點是：模型吐 token 的速度已經快過 harness 讀檔的速度，瓶頸從「每秒多少 token」變成「**工具呼叫稅**」，也就是每次讀檔、搜尋、執行終端指令都要付一次行程啟動與包裝層的成本。

### 我不能用它，但可以借它的量測方法

准入條件檢查結果：授權是 MIT（過），但**平台綁定 Windows/MSYS**、又**綁死 Hermes Agent 的內部私有介面**（兩項不過）。所以工具本體我無法安裝。此外：

- 整個倉庫只有一個 squashed commit，README 說的「四波演進」無法用 git 歷史覆核。
- 它自報的 4.7x 到 57.5x 加速、206 個回歸測試，我**沒有獨立重現**（環境跑不起來，我也沒有嘗試執行），只能確認「倉庫與上游依賴確實存在」。
- 另外有兩個外部使用者送的 PR（擴充 macOS/POSIX 支援、讓它能對公開版 Hermes 運作）都還沒合併，間接佐證現況只在特定環境可跑。

**可以借鏡的是量測紀律**：

1. **分層計時**：把一次呼叫拆成 L0 到 L6 等固定命名的層，每層獨立計時，寫進同一份 JSON。這樣才知道哪一層變快，而不是只有一個籠統的總數。
2. **每次重跑用全新標籤**：避開被測系統自己的快取，否則第二次之後的數字會偏低。
3. **用中位數與 p90，不用平均**：離群值會扭曲平均。
4. **負向對照**：在獨立子行程內用 monkeypatch 製造故障，不去改磁碟上的檔案，跑完比對安裝檔雜湊前後一致，確保驗證過程本身沒弄髒環境。
5. **量完就停**：它的第四波用數字證明「剩下的 4.44 毫秒是安全護欄，不要再最佳化」，把「不值得再做」變成有證據的結論。

### 把這套方法套到 hook 疊加（提案，未執行）

如果你掛了多個 hook（我的情況是每次執行 shell 指令前後疊了 8 個），每個 hook 通常是一次新的 shell 行程加上 `jq` 解析。這一層的耗時我從沒量過。借 toolrush 的方法，設計大致是：

- 在每支 hook 腳本的最前與最後各記一次高解析度時間戳，寫到獨立的 JSONL；探針自己的 I/O 成本要和被測邏輯分開算。
- 對照臂：移除全部自訂 hook、只留某一個，再全部移除，量出「harness 原生地板值」。
- **先加一個刻意 `sleep 0.05` 的假 hook 當正向對照**，證明量測方法真的抓得到已知差異，才能相信「真實 hook 開銷可忽略」這種結論。否則可能只是量測接線沒接對。
- 訊號門檻用重複量測得到的雜訊帶決定，不憑感覺。
- 如果疊加開銷只在個位數毫秒、遠小於一次模型往返，就該「量完就停」，不要為了省幾毫秒拿掉安全用途的 hook。

這份設計**只是提案，沒有執行**。

## 外部變數：雲端額度政策收緊

2026 年 6 到 7 月，我自己用個人 Google 帳號跑 Antigravity CLI（`agy`）做程式碼審查，用法與頻率沒變，卻突然開始撞額度。我去查是不是個案。結論是：**不是個案，是平台級變動**，至少四個彼此獨立的來源指向同一件事。

| 來源 | 日期 | 內容 |
|---|---|---|
| [Google Developers Blog 公告](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/) | 2026-05-19 | 2026-06-18 起，Gemini CLI 對 AI Pro、Ultra 與個人免費使用者停止服務，轉往 Antigravity CLI。公告只講平台整併，沒有主動提額度縮減；企業授權與 API key 不受影響 |
| [The New Stack 報導](https://thenewstack.io/google-antigravity-cli/) | 約 2026-05 中 | 引用多則 Reddit 貼文：有人說以前用 13% 額度做完整專案，現在 6 到 7 個 prompt 就撞頂 |
| [GitHub Discussion #27307](https://github.com/google-gemini/gemini-cli/discussions/27307) | 開於 2026-05-20，官方回應 2026-07-05 | 每個請求固定吃 23 到 25k token 的系統提示與工具開銷（`/context` 顯示系統提示約 7.8k、系統工具約 15.1k），兩小時就撞 5 小時限制；官方回應「正在處理」，暫時建議縮小 context |
| [Google AI 開發者論壇](https://discuss.ai.google.dev/t/navigating-antigravity-pro-quota-limits/130212) | 2026-03-10 起 | 多位使用者記錄 Pro 額度從「每 5 小時刷新」變成「多日鎖定」，並抱怨有未寫進文件的 7 天週上限；官方只回「已轉達」 |

### 成因是兩個效應疊加

1. **政策面逐步收緊**（2025-12 起貫穿 2026 上半年）：免費額度被砍、Pro 的週上限、Pro 免費層移除。
2. **新工具本身的固定開銷很重**：每個請求先吃掉 23 到 25k token，對「大 context 加大量工具呼叫」的程式碼審查特別致命。

至於「免費額度砍 50 到 80%」「縮減 97%」這類百分比，來自二手聚合部落格，**官方未確認**，只能當趨勢佐證，不能當硬數字。

### 這給我的教訓

- 額度突然不夠用時，**先查公告與社群，再懷疑自己的用法**。
- 工具的固定開銷（系統提示加工具定義）會在每個請求重複付一次，所以「同樣的操作頻率」在新版工具上可能耗掉多倍額度。
- 供應商的額度政策可能不寫進文件，不要把某個用量當成永遠成立。

## 附：全域設定檔的 token 熱點審計與一個方法論教訓

我曾經審計過自己 `~/.claude/` 底下哪些檔案最耗 token，初版用「檔案大小 × 觸發頻率權重」排名，結果發現三個方法論偏差，排名數字不能直接當行動依據：

1. **沒有計入 prompt cache**。實測近期對話的快取讀取量佔輸入總量 70 到 91%（對話越長比例越高，一段 427 輪的對話達 91%）。常駐載入的檔案只有第一次要付快取建立成本，之後每輪都走便宜的快取讀取，所以「常駐檔案是最大熱點」被高估了約 7 到 9 倍。**修正後的真正優先序**：高頻委派、每次都全價建立快取的共用 reference 與子代理定義檔，高於常駐的 CLAUDE.md。
2. **bytes 不等於字元數**。`wc -c` 算的是位元組，中文一個字是 3 bytes，直接拿來估 token 會失真。
3. **把不會同時載入的多個檔案合計後再均分**，和單一檔案的常駐項不在同一個比較基準上。

可套用的教訓：做 token 審計時，先確認載入方式（常駐、委派時載入、按需載入）與快取行為，再談排名；估算公式要註明（我用的是中英混合 3.5 字元約 1 token，保守估計），沒驗證的項目（例如某檔案只量了大小、沒讀內容）要明講「未驗證」。

## 可直接套用的檢查清單

- [ ] 想省 token 之前，先用一個唯讀工具把花費拆到「模型、專案、子代理、skill」。
- [ ] 確認自己是 API 計費還是訂閱制，再決定哪些優化有意義。
- [ ] 壓縮工具的數字，先問「我的內容種類跟它測的一樣嗎」。
- [ ] 想加的狀態列指標，先判斷資料在 stdin 快照裡還是要解析 transcript。
- [ ] 讀檔案時間的指標，路徑用全域，別用相對路徑（worktree 會各看各的）。
- [ ] 量效能時：分層計時、全新標籤、中位數加 p90、先放正向對照、量完就停。
- [ ] 額度突然變緊：查公告、查社群，區分政策變動與工具固定開銷。
- [ ] 任何沒實測的推估，都要在文字裡標「未實測」或「推估」。
