# AI 輔助理解專案的工具

> 評估三個「幫 AI 或人理解專案」的工具：把資料夾轉成知識圖譜的 graphify、用瀏覽器自動化查 NotebookLM 的 notebooklm-skill、把 JSON 編譯成架構圖的 Archify。重點不是推薦哪個，而是我怎麼判斷「該不該用」。寫於 2026 年。

## 問題與背景

接手大型專案，或要請 AI 幫忙追跨檔案的呼叫路徑時，常見的做法是讓 agent 現場 grep、逐檔讀。這在小專案沒問題，專案一大就會遇到：

- 讀了十幾個檔還沒定位，context 先被塞滿。
- 同一個問題，每次都要重新探索一遍。
- 想把理解結果整理成「別人看得懂的圖」，得手動畫。

於是出現一類工具：**先把專案預先解析成結構化的索引或圖，再讓 AI 查小範圍的結果**；或者反過來，**讓 AI 只負責產生結構化描述，由程式決定性地渲染成圖**。我用同一套評估流程看了三個，結論差異很大，可以拿來對照。

## 我的評估流程

每個工具都走同樣幾步：

1. **先看維護狀態與授權**：最近一次提交是什麼時候、有沒有人接手、授權是什麼。
2. **找出它的核心賣點，再問「賣點成立的前提是什麼」**。
3. **對照自己的工作方式**：前提成立嗎？不成立就是場景錯位。
4. **分級決定**：立即採用、按需臨時使用、只借鏡觀念、不採用。
5. **把「引用數字」和「實際跑過」分開**：沒親自跑過的，文章裡一律標「未驗」。

幾次下來，我發現第 2 與第 3 步最容易被忽略。工具的 GitHub 星數很亮眼時，很容易直接跳到「看起來很好用」。

## 工具一：graphify，把資料夾轉成知識圖譜

[graphify](https://github.com/Graphify-Labs/graphify)（PyPI 套件名 `graphifyy`）把專案裡的程式碼、文件、PDF、圖片解析成一份知識圖譜（`graph.json`），讓 AI 用 `query`、`path`、`explain` 查一小段子圖，取代逐檔 grep。

### 它怎麼運作

- **程式碼部分**用 tree-sitter 做語法樹解析（約 36 種語言文法，另有 Blade、Terraform、SQL 等擴充），在本機執行、**不呼叫任何 LLM**，所以零 token 成本。
- **文件、圖片等非程式碼內容**交給呼叫端的 AI 助理讀檔、寫出結構化 JSON，或接設定好的外部 API。沒設定任何 key 時，預設退回「呼叫端自己讀檔」。
- **每條關聯都標信心標籤**：`EXTRACTED`（原文寫明）、`INFERRED`（推論）、`AMBIGUOUS`（不確定）。這是資料結構的一級欄位，不是報告上事後加註。
- 預設只輸出三個檔案：`graph.html`、`GRAPH_REPORT.md`、`graph.json`。

### 它的賣點與前提

最大賣點是「**一個人建圖，全隊共用**」：建好的圖 commit 進 repo，用 git post-commit hook 自動保鮮，甚至註冊一個自訂 merge driver，讓兩個人平行 commit 時圖檔自動合併。

這個賣點的**前提**是：專案 repo 長期存在、進版控、團隊共用同一份。如果你的工作方式是每個功能開一個 worktree、各自獨立、整個專案資料夾被 git-ignore，那每個 worktree 都得各建各的圖，最大的賣點就沒了。

### 我的結論：按需使用，不常駐

- 語言覆蓋（TypeScript、PHP 含 Blade、Python）與工程品質都紮實。
- 但它還是 pre-1.0（我看的是 v0.9.18），介面與 schema 每天都在變。
- **證據偏弱**：它的程式碼理解評測樣本很小（6 題），另外的對話記憶評測不是程式碼理解場景，不能直接當「省 token、降幻覺」的強證據。

建議用法是：子代理已經 grep 或讀檔三次以上還沒定位，或任務明確是追蹤跨檔案呼叫鏈時，在該 worktree 臨時建圖、查完就丟：

```bash
uv tool install graphifyy      # 或 pipx install graphifyy
graphify extract .             # 純程式碼、零 LLM 呼叫，本機建圖
graphify query "什麼連接 X 到 Y？"
graphify path "ServiceA" "ServiceB"
```

不執行 `graphify install`（會寫入專案設定），也不裝常駐 hook。

注意：這份評估**只讀了原始碼與文件，沒有實際安裝或在自己的專案上跑**，所以 token 與延遲的實際收益是「未驗」。

### 兩個值得借鏡的設計觀念

1. **把信心分數離散化**。它的抽取規格把 `confidence_score` 鎖成 0.95、0.85、0.75、0.65、0.55 五個固定值，理由寫得很具體：模型對離散選項的遵守度比連續區間好；實測分數呈雙峰（超過 50% 落在 0.5、超過 40% 落在 0.85 以上），表示連續區間的指引被模型壓縮成二選一。**要求 AI 標信心層級時，給固定選項，不要讓它自由填「中等」。**
2. **先判斷值不值得做**。它的報告第一段是「Corpus Check」，會直接告訴你「語料太小，圖結構不見得有幫助」，而不是不管如何都硬產一份。審查類的流程也可以先加一道「這個範圍值不值得跑完整審查」的量級判斷。

其他可學的小細節：hook 永遠 fail-open（任何例外都放行，寧可少提醒也不誤擋合法操作）、節點 ID 強制用「完整相對路徑加實體名稱」避免兩個同名檔案被誤認成同一個節點、載入圖檔前先檢查檔案大小上限。

## 工具二：notebooklm-skill，一個「已壞且停止維護」的反例

[notebooklm-skill](https://github.com/PleasePrompto/notebooklm-skill)（我看的是 v1.3.0）是一個 Claude Code skill，讓 Claude 能查詢自己的 Google NotebookLM 筆記本。NotebookLM 沒有公開 API，所以它的做法是**瀏覽器自動化**：開一個真的 Chrome，帶著使用者先前手動登入留下的 cookie，在網頁輸入框逐字打出問題，再從網頁 DOM 把答案抓回來。

### 現況：主線已壞

| 證據 | 內容 |
|---|---|
| 網域搬遷 | 我用 curl 實測，舊網域現在會 301 導向新網域 |
| 程式碼硬編碼 | 判斷登入成功的條件寫死舊網域，導向後永遠不成立，登入卡滿十分鐘逾時；社群 issue 有人回報同一症狀 |
| 作者停更 | 最後一次提交與最後一則留言都在 2025-11-21，距我檢查時約九個月 |
| PR 堆積 | 十餘個外部修補 PR 沒合併，修好網域問題的那個被直接關閉 |
| 沒有社群接手 | 依推送時間排序前 10 個 fork，全是個人自用修補 |

另一個重複被回報的 bug 更危險：**抓到上一題的答案**（聊天介面的 DOM 有虛擬化與伺服器端歷史），有五筆重複回報、全未合併。壞掉會報錯，抓到舊答案卻會**安靜地回錯**。

### 安全面的觀察

- 認證方式是 **session replay**（重放已登入的瀏覽器工作階段），不是 OAuth。cookie 與 localStorage 以明文寫進本機 `state.json`，程式碼裡沒有任何設定檔案權限的動作（grep 零命中），共用機器上其他帳號可能讀得到。
- 有明確的反偵測設計（裝真 Chrome、關掉自動化旗標、模擬人類打字節奏），README 的免責聲明承認無法保證 Google 不會偵測或標記。
- README 要求把筆記本設成「任何知道連結的人可存取」，上傳內部文件再開公開連結就是外洩路徑，文件中沒有標成風險。
- 回傳值是「答案文字加上一段寫給呼叫端 LLM 的提示字串」。作者自己加的內容無害，但同一條通道回來的還有外部產生的答案文字。
- 好的一面：沒有 `shell=True`、`eval`、`exec`、`pickle`，也沒有對非 Google 主機的網路呼叫。

### 我的結論：不整合，只借觀念

**一個靠爬第三方網頁的工具，必然會腐爛**（網域、CSS 選擇器、頁面改版都會讓它壞）。所以評估這類工具時，第一順位要看的是「該產品多久改版一次」與「維護者還活不活躍」，而不是功能多不多。

可以借鏡的四個觀念：

1. **無完成訊號時，用「連續 N 次穩定」判斷串流結束**：它把「同一段答案文字連續 3 次輪詢都沒變」視為完成（上限 120 秒）。任何要判斷外部輸出是否寫完的場景都能套用。
2. **工具回傳值就是提示詞**：外部工具回傳的文字會被呼叫端 LLM 當指令讀。凡是會吃外部工具回傳文字的流程，都該把回傳值視為不可信內容。
3. **單一入口包裝層**：SKILL.md 明寫「永遠經過 `run.py`，不要直接呼叫腳本」，由這個入口統一處理 venv 與環境準備，避免 LLM 忘了啟用環境。
4. **文件與程式碼要對得上**：它的 SKILL.md 寫的打字速度預設值，與程式碼預設值不同，而且那兩個參數根本沒被使用（死參數）。

## 工具三：Archify，讓 AI 寫 JSON、程式決定性地畫圖

[Archify](https://github.com/tt-a1i/archify) 是 Node.js 的渲染與驗證系統：AI 只負責寫一份型別化 JSON（中介表示，intermediate representation，共五種圖：architecture、workflow、sequence、dataflow、lifecycle），CLI 再「決定性地」（同輸入必同輸出）把它編譯成自足的互動式 HTML，內嵌 SVG，支援平移縮放、搜尋、追蹤上下游。另有「前後快照比較」引擎，輸出新增、移除、變更、移動、改道的結構化差異。

授權 MIT，維護活躍（抓取當天仍有提交，CI 涵蓋 Node 18、20、22、24 四個版本）。安裝經由 `npx skills add`，那個安裝器我另外查過：屬 Vercel Labs 官方的 [skills](https://github.com/vercel-labs/skills) 專案，不是可疑的第三方。

### 我實際跑了什麼

在暫存目錄 `git clone --depth 1`，用系統既有的 Node 20，**刻意不執行 `npm install`、也不做全域安裝**：

```bash
node bin/archify.mjs doctor
node bin/archify.mjs validate architecture examples/web-app.architecture.json --quality showcase --json
node bin/archify.mjs deliver architecture examples/web-app.architecture.json out.html --quality showcase --json
node bin/archify.mjs compare architecture base.json head.json delta.html --json
```

四個指令都成功。`validate` 的 9 項檢查全過，`deliver` 產出約 715 KB 的自足 HTML，回報了輸入與輸出各自的 SHA-256；`compare` 吐出結構化的差異清單。零依賴能跑，是因為 JSON Schema 驗證器在建置時就預先編譯進檢入版控的檔案裡。沒有跑它的測試套件（需要建置期依賴）。

### 設計上最值得學的幾點

- **「驗證」與「交付」是兩個指令**：`validate` 可以反覆跑，`deliver` 才會凍結輸入的確切位元組並寫入帶雜湊的收據。「驗收通過的是哪一份 JSON」變成可事後稽核的事實。
- **三種「通過」不能互相取代**：交付收據通過、視覺檢查通過、人眼或圖像模型的美觀複核，是三個獨立的宣稱，要分開回報。SKILL.md 還寫死「非零 exit code 絕對不能描述成成功」，並禁止在失敗後拿舊產物去跑視覺檢查，否則會驗到「上一次成功」而不是「這一次失敗」。
- **把「圖好不好看」變成程式能量化的檢查**：9 項檢查包含線交叉、走廊歧義、標籤與路由的淨空、容器邊框重疊等。模型自己肉眼判斷版面是否乾淨並不可靠，這種做法把它變成可以擋下的錯誤。
- **圖上的證據可以用 git 驗真**：啟用 `--repo-root` 時，圖中節點聲稱的來源檔案或 commit，會實際用 `git cat-file -e` 核對是否存在，不存在就 fail closed。
- **品牌標誌只能是「目錄內建」或「使用者明確給的 HTTPS 網址加 SHA-256」二選一**，不准從「database」這種模糊詞反推品牌，防止 AI 自己腦補 logo。
- **SKILL.md 只有 138 行**，四份深度參考標明「只在使用者明確要求某功能時才讀」，用分層載入控制常駐的 context 佔用。

### 它能擋什麼、擋不了什麼

這是我最想講清楚的一點：它**擋得住**「引用不存在的檔案或 commit」這種可被 git 物件模型驗證的捏造；但**擋不住**「兩個真實存在的元件之間，被寫上一條不存在的業務關係」這種語意層的捏造。決定性驗證只保證結構與幾何，不保證內容為真。

### 我的結論：按需臨時使用，不全域安裝

- **全域安裝會讓觸發詞碰撞**：它的描述寫「視覺化系統架構、轉換或美化 Mermaid」，與我已有的 Mermaid、純文字圖兩個 skill 觸發詞高度重疊，要重寫邊界才能消歧。
- **輸出恆為獨立 HTML**，貼不進 GitLab 這類要內嵌渲染 Mermaid 的地方。所以它不能取代我最常用的圖表通道。
- 我的痛點「想把專案變成可互動的系統地圖」其實是個**期望**，不是上週真的吃過虧的重複性痛點，所以我不把它升到「立即採用」。
- 適用情境：非內嵌、節點超過 15 個、需要平移縮放搜尋，或需要「架構變更前後」對照（例如大型重構的審查附件）時，臨時 clone、跑完就刪暫存目錄。

## 三個工具的對照

| | graphify | notebooklm-skill | Archify |
|---|---|---|---|
| 做什麼 | 專案轉知識圖譜，供 AI 查詢 | 用瀏覽器自動化查 NotebookLM | JSON 轉決定性渲染的互動圖 |
| 維護狀態 | 非常活躍，但 pre-1.0 | 停更、主線已壞 | 活躍，CI 完整 |
| 賣點的前提 | 專案進版控、團隊共用一份圖 | 目標網站不改版 | 輸出通道能接受獨立 HTML |
| 我的分級 | 按需臨時使用，借鏡觀念 | 不整合，只借觀念 | 按需臨時使用，借鏡觀念 |
| 最大的疑慮 | 運作模型與 worktree 工作方式衝突 | 靠爬第三方網頁，必然腐爛 | 全域安裝造成觸發詞碰撞 |
| 實跑過嗎 | 沒有（只讀文件與原始碼） | 部分（網域搬遷用 curl 驗證） | 有（四個指令） |

## 踩過的坑與教訓

- **賣點有前提，先問前提在不在**。graphify 的「團隊共用」建立在 repo 長期存在上，我的工作方式不符，就算工程品質亮眼也不該常駐安裝。
- **維護者是否活躍，比功能豐富度更重要**，尤其是靠爬第三方網頁或呼叫非公開介面的工具。
- **掃描啟發式也會誤判**。我的評估腳本對 Archify 建議用「片段整合」模式（因為根目錄有 SKILL.md），但它其實是完整的渲染引擎專案，我改用「工具評估」模式並把理由寫下來。啟發式只供參考，不強制遵循。
- **不要把星數當採用理由**。星數只能佐證「不是無人維護的空頭專案」。
- **文件說的與程式碼做的不一致時，兩邊都要懷疑**（死參數、說明文字列出不存在的腳本）。
- **「驗證通過」要說清楚是哪一層的通過**，Archify 的三層宣稱分離值得套用到自己的報告上。

## 可直接套用的檢查清單

- [ ] 最近一次提交與最後一則維護者回覆是什麼時候？有沒有未合併的修補 PR 堆積？
- [ ] 它的核心賣點，成立的前提是什麼？我的工作方式符合嗎？
- [ ] 它靠爬第三方網頁或呼叫非公開介面嗎？如果是，維護風險直接加一級。
- [ ] 它會把外部內容原樣回傳給我的 LLM 嗎？回傳值要當不可信輸入。
- [ ] 它寫入本機的憑證或 cookie，檔案權限是什麼？
- [ ] 會不會跟我現有 skill 的觸發詞碰撞？
- [ ] 能不能用「暫存目錄加 clone 加用完就刪」的方式先試？
- [ ] 我寫下的每個「有效」，是親自跑過，還是只讀過文件？沒跑過的標「未驗」。
