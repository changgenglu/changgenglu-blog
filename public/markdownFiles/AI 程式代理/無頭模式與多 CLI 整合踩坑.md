# 無頭模式與多 CLI 整合踩坑

> 讓一個程式代理（Claude Code）去呼叫另一個 CLI（Gemini／Antigravity CLI 的 `agy`、Codex CLI）以無頭（headless，沒有人互動、一次跑完）模式工作，聽起來很簡單，實際上我踩了半年的坑。這篇整理那些「失敗長得像成功」的案例、權限與環境的陷阱、無頭測試意外燒額度的事故，以及外部模型捏造證據的處理方式。2026 年寫成。

## 先講結論：不穩常常是「好幾個獨立問題疊在一起」

過去半年，我一直把「Gemini 呼叫不穩」當成同一個問題。統計下來，無頭模式失效已經超過 9 次，**每次故障的樣子都不同**，所以每次都被當成獨立事件排查，沒有人問過「這條路徑整體可靠度是多少」。

後來做了一次根因診斷，結論是：那是**三個各自獨立的問題**疊在一起，其中兩個還是我自己的呼叫方式造成的，不是工具壞了。

這個經驗後來變成我的通則：

- 單點修補治標；先把失效形態**彙整成清單、找共同因子**，再決定修幾個地方。
- 失效清單要附證據來源與日期，避免「印象中很不穩」。
- 能算的別憑印象：委派成功率要從紀錄算，不是靠感覺。（我後來發現記帳紀錄沒有「結果」欄位，算不出來，這本身也是個發現。）

## 坑一：失敗長得像成功

### 現象：status 成功、exit code 0，內容是空的

`agy` 在無頭模式（`-p`）下，碰到需要授權的工具時，**不再卡住**，改成當場拒絕，並把「你該加哪條授權規則」印在 stderr。於是出現這種輸出：

```json
{"status":"SUCCESS","response":"","duration_seconds":2.89,"num_turns":1,
 "usage":{"input_tokens":23697,"output_tokens":754,"total_tokens":24451}}
```

- `status` 是 `SUCCESS`。
- exit code 是 `0`。
- 只有 `response` 是空字串。

呼叫端看狀態碼會判定成功，實際上什麼都沒做，還白燒了約 2.4 萬 input token（每次請求固定的 system prompt 開銷）。

### 唯一的線索被我自己丟進垃圾桶

stderr 其實寫得很清楚：

```text
a tool required the "command" permission that headless mode cannot prompt for,
so it was auto-denied. Add an allow-rule under permissions.allow in settings.json
```

但我的呼叫模板固定帶 `2>/dev/null`，**正好把這唯一的診斷訊息丟掉**。連 6 個任務失敗都查不出原因，訊息一直都在，只是被自己蓋掉了。

這也解釋了「同一個 prompt 兩次結果不同」：不同 prompt 讓模型選走不同的工具路徑，需要授權的那條被拒（0 輸出），只用內建能力的那條通過。看起來像隨機不穩，其實是決定性的。

### 通則

- **成功判定要三項一起看**：exit code、status 欄位、**回應內容非空**。
- **不要把 stderr 丟掉**。尤其是整合一個你還不熟的 CLI 時，stderr 是最有價值的診斷來源。
- 還有更前一層的失敗：**呼叫根本沒送出**。有一次子代理跑了 63 次工具呼叫、約 22 萬 token、11 分鐘，最後回報停在「已啟動背景 monitor，等待完成」就結束，輸出檔完全沒建立。我用 `ps` 查，子代理「等待中」的當下，系統上根本沒有任何相關行程。第一次委派同樣模式也是零產出，合計約 43 萬 token。

  原因是子代理臨場拼湊的指令，多行字串被攤平成一行，`cd` 與 `agy` 被吃成前面 `rm -f` 的檔名參數，`agy` 從未被啟動。
- 對這類情況要求子代理的**終態只有兩種：完成、受阻**。「等待中」不是終態，要嘛等到結果、要嘛回報受阻。

## 坑二：權限規則比對的是「工具名稱字串」

### 授權了，卻還是被拒

我修好上面的授權問題後，在 `permissions.allow` 補了規則：

```text
allow = ["command(defuddle)", "read_file(*)", "command(*)", "write_file(*)"]
```

過了幾週，同一個任務又失敗，這次錯誤指名是 `write_to_file` 權限錯誤。**名單裡是 `write_file(*)`，沒有 `write_to_file(*)`**。

我用 `strings` 檢查 `agy` 二進位檔，兩個名字都存在（`write_to_file` 出現 22 次，`write_file` 8 次）。allow-rule 是**逐個工具名稱的白名單**，不是萬用授權。授權了名字對得上的，名字對不上的照樣被拒。

教訓：

- 權限規則比對的是字串；不同 CLI、甚至同一個 CLI 的不同版本，工具命名可能不同。
- 診斷時不要只看「有沒有授權」，要看「授權的名稱與實際被呼叫的名稱是否一致」。

### 「在 /tmp 測試」會得到假通過

另一個坑：缺少寫檔授權時，寫到 `/tmp` 底下照樣成功（內建豁免），寫到專案內任何路徑一律被拒。

我當初做了三次端到端驗證，輸出路徑全部指到暫存目錄，所以得到「61 秒、57.6KB」的成功基準；真實委派寫到專案內，結果是**結構性 100% 失敗**。實測：同一份 prompt 只換落點，`/tmp` 成功、專案內路徑檔案不存在。

白跑一輪的代價是 116 秒、input 約 7.5 萬加 output 約 4.2 萬加 thinking 約 1.1 萬 token，產出 0 位元組。

教訓：

- **測試落點要和真實落點一致**，否則基準是在有豁免的路徑上量的。
- 設計「預設引擎失敗就回退到另一個引擎」時，如果預設引擎是結構性失敗，預設就是反向的：不但省不到，還多花一輪。
- 這次修法是補上寫檔授權。我也試了把授權範圍限縮到某個目錄，實測**不被匹配**，照樣拒絕；而且 shell 本來就全開，限縮寫檔路徑沒有實質收益。

## 坑三：「別人的文件」宣稱的限制，可能是錯的

我的文件宣稱單一參數可以到 2MB，來源是 `getconf ARG_MAX`（本機確實回報 2097152）。但那是「所有參數加環境變數的總和」上限，**單一參數另有更低的天花板**（Linux 的 `MAX_ARG_STRLEN`，固定 128KB）。實測：

| 單一參數大小 | 結果 |
|---|---|
| 100KB、120KB、127KB | 正常 |
| 130KB、200KB | 參數列太長（E2BIG） |

另外，用 stdin 餵 prompt 也行不通：`printf '...' | agy -p` 並沒有把 stdin 當成 prompt，模型反而去試 `read_file` 工具並被拒。

可行的做法是「餵料模式」：把檔案內容直接寫進 prompt、明確禁用工具，完全成功、stderr 乾淨，代價是受 128KB 上限約束。

## 坑四：`--dangerously-skip-permissions` 在外層代理內走不通

我的呼叫模板預設帶 `--dangerously-skip-permissions`（跳過所有授權確認）。實測在 Claude Code 內被它自己的自動模式分類器硬擋：

```text
Permission for this action was denied by the Claude Code auto mode classifier.
```

這不是被呼叫端的問題，是呼叫端（外層代理）的限制。所以模板的預設寫法，在這個環境內**必然失敗**。

替代路徑有官方依據：被呼叫端從某個版本起，無頭模式會遵守持久化 `settings.json` 的政策，包含 `permissions`。所以把授權寫進設定檔，就不需要那個旗標。

## 坑五：`--model` 被靜默忽略

官方 changelog 提到過一個修正：`--model` 與 `--effort` 旗標在無頭模式下被**忽略**，因為旗標在模型設定初始化之後才被套用，執行靜默退回持久化的預設模型。

連帶的推論（信心：中，間接推論）：我當時以為在用高階模型做逐檔呼叫鏈追蹤，實際上可能靜默降級成較便宜的模型。用較便宜的模型做高精度的追蹤，出現後面會講的「捏造」，並不意外。**沒有當時的實際模型使用紀錄可以直接證明**，所以必須實測複驗才能宣稱捏造問題已解決。

## 坑六：要求外部模型做研究，會被捏造

### 外部模型的引用要逐筆核實

早期我用 Gemini 做外部研究，產出 78 行看起來完整的報告。逐筆核實後：

- **5 個網址不存在（404）**。
- 1 篇 arXiv 論文的內容與報告中的主張不符。
- 有一個宣稱的「95% 遵循率」數字，來源網頁 404，數字無從驗證。

全部要不是修正，就是標記成「無法驗證」，或直接丟棄。

### 內部審查員也會捏造證據

同類問題也發生在我自己的子代理：審查員宣稱「某方法仍在 A 檔案被呼叫」，實際上該模組零呼叫（是另一個模組才有）。**連續兩次**。第二次還是沒有追呼叫者就下判斷。另一個審查員聲稱某些常數值，沒有直接讀原始碼，信心標得很高（90 分以上），內容卻是錯的。

兩次都是主代理在驗收時親自 grep 才攔下來。

如果沒攔下來，後果是：第一次會誤刪 6 個孤兒方法中仍應保留的方法；第二次會把修復方向誤導到錯的地方。

### 對策

- 委派 prompt 加強制約束：**聲稱方法被呼叫或沒被呼叫，必須附 grep 的指令輸出；沒有 grep 證據的呼叫鏈聲明自動降級成低優先建議**。
- 涉及常數值的發現，必須附「直接讀檔」的輸出；禁止從函式名稱推論 TTL 或行為。
- 主代理的驗收義務不可省略，是最後一道防線。
- 對外部模型的研究輸出：每個網址都要實際打開、每個數字都要找得到出處。

## 坑七：無頭測試會偷偷開出一堆真的 session

這是事故最大的一類，值得單獨講。

### 事故一：description 最佳化迴圈燒光額度

用最高階模型跑 skill 的 description 最佳化迴圈，開了 38 次以上的無頭 session，一天額度耗盡，結果是 0 bytes。後來把紀律寫成規則並用 hook 機械化（細節見〈Skill 撰寫與維護〉）。

### 事故二：測試經通知腳本，每輪開 39 個真 session

審查端的測試每跑一次，就經由一支「通知腳本」呼叫無頭 `claude -p`。每次測試開 39 個最高階模型的 session，兩天累積約 360 個。

這支通知腳本的呼叫是 `"${CLAUDE_BIN:-claude}" -p ...`，**沒有設 `CLAUDE_BIN` 就用真的 claude**。部分測試有用假的執行檔頂替，有些會走到通知鏈的測試沒有。

當時我只加了規則（「跑測試前先在 PATH 最前面放假的 `claude`」）和事後偵測的 hook，**測試本身沒修**。幾天後，同一個測試套件又開出 27 個真 session，合計 input（含 cache）約 1,001 萬、output 約 6.4 萬 token，而且其中 12 次還真的呼叫了「傳訊給某人」的工具，只是運氣好，測試用的收件名稱剛好沒人用，12 次全部送失敗。

### 教訓：只靠「執行者記得」不夠

- **規則加事後偵測不夠，要把防線做在測試本身**。第二次修法有三層：
  1. **測試層**：共用的測試前置載入檔，強制讓 `claude` 指向假執行檔；叫到真的就讓測試**失敗**，不要默默打出去。
  2. **腳本層**：通知腳本偵測到在 node 測試環境（`NODE_TEST_CONTEXT` 有值）但沒給假執行檔，**拒絕執行**。
  3. **本機全域層**：在 PATH 最前面放攔截腳本。
- **驗收**：跑一次測試，對照前後 session 目錄的檔案數量，應該不變。
- **「測試通過」不等於「沒有副作用」**。這次測試 754 個全過，副作用靠事後偵測 hook 才發現。
- 我目前的無頭規則：啟動前先告知使用者（目的、模型、預估次數）；測試一律用最便宜模型並限制載入來源；非最便宜模型要明確警告並取得同意；沒有人可以回覆的 session 不准啟動無頭 session。

### 附帶的小坑：被「互動模式」的護欄打到

給無頭 worker 用的環境，常常會被原本為互動 session 設計的護欄擋到，例如指令改寫（為了省 token 的改寫）會讓權限層比對到的指令與白名單永遠對不上。處理方式是對無頭 worker 的工作階段跳過改寫。

## 坑八：配額錯誤，不要重試

最後是策略層的決定。半年累積 9 次以上的失效形態，其中不少是配額（429、`RESOURCE_EXHAUSTED`）。裁決選項有三個：

| 選項 | 內容 |
|---|---|
| 甲 | 照舊先派外部引擎，**但配額類錯誤不重試**，立即退回 Claude 子代理 |
| 乙 | 預設不派外部引擎 |
| 丙 | 維持重試 |

最後選甲。理由是：我要先知道根因再決定策略，不要在不了解不穩的原因時就先砍掉一條能力。配額類錯誤重試沒有意義，額度不會因為你再試一次就回來。

實際做法是在代理定義加一條「配額類錯誤不重試」：stderr 或 JSON 含 `429`、`RESOURCE_EXHAUSTED`、`quota`、`usage limit`、`rate limit` 就不做第二次呼叫、不走模型 fallback 鏈，直接回報受阻並附錯誤原文前 5 行；並明訂它是「連續 2 次失敗」條款的例外。

驗收是**文字層**的（因為本機沒有配額問題，觸發不了真實的 429），行為驗證登記成待辦，等下一次真實配額事件時確認。

另外一個相關的取捨是：預設引擎失敗再回退的**等待成本**沒有人記錄。有一次使用者等了約 20 分鐘才拿到報告，期間沒有任何進度訊號可查，只能從「沒有 agy 行程在跑」反推它已進入回退階段。如果要用「先試、失敗再回退」的策略，需要量化回退的等待成本，並且讓外部引擎呼叫留下可查的階段痕跡。

## 可直接套用的檢查清單

整合另一個 CLI 之前：

- [ ] 成功判定同時看 exit code、狀態欄位、**內容是否非空**嗎？
- [ ] 呼叫範本有保留 stderr 嗎？（不要 `2>/dev/null`）
- [ ] 呼叫前後有確認「呼叫是否真的送出」嗎（例如行程是否出現）？
- [ ] 權限規則的工具名稱，和實際被呼叫的名稱一致嗎？
- [ ] 測試的落點，和真實落點一致嗎？（避免 `/tmp` 豁免造成的假通過）
- [ ] 文件上寫的上限（參數大小、逾時），實測過嗎？
- [ ] 外部模型引用的網址、數字，逐筆核實了嗎？
- [ ] 審查類的發現，有附 grep 或讀檔的原始輸出嗎？

跑無頭測試之前：

- [ ] 用最便宜的模型、限制載入來源、限制回合數了嗎？
- [ ] 測試會不會在背後呼叫真的 `claude`？有沒有假執行檔頂替，並且「叫到真的就失敗」？
- [ ] 總呼叫數估過了嗎？超過 20 次先取得同意了嗎？
- [ ] 跑完對照 session 目錄，確認沒有新增檔案了嗎？
