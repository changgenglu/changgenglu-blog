# AI 代理的記憶分層與跨 session 接續

> AI 程式代理每次開新 session 都是「失憶」的。這篇整理我怎麼把「記憶」依性質分成五個落點、什麼樣的決策該永久保存、以及怎麼用結構化存檔取代自動壓縮，讓下一個 session 能直接接手。2026 年寫成，以 Claude Code 為例；分層的判準本身與工具無關。

## 問題：記憶放錯地方，比沒記更糟

一開始我的做法是「想到什麼就寫進 CLAUDE.md」，或「讓審計流程自動把教訓存進 `lessons/`」。跑了幾個月後遇到三種狀況：

- **常駐檔越長越肥**：每個 session 都全量載入，什麼都放進去，AI 注意力被稀釋，真正重要的硬規則反而被淹沒。
- **自動提取的教訓不新鮮**：審計流程會把「這次學到什麼」自動寫進資料夾，但沒有人維護。我曾訂過「30 天標 stale、90 天封存」的規則，後來檢查發現 12 個超過 30 天的檔案，一個都沒被轉換過。**規則寫了、從來沒被執行，等於沒有**。
- **專案紅線只進了教訓資料夾**：我口頭說明過「這個專案的某個機制不能做 X」，AI 把它記成一則「教訓」，但教訓不保證新鮮、也不會自動被載入，下次規劃時沒人看到它。

解法不是「更努力記」，而是**先判定這則知識屬於哪一種，再決定放哪**。

## 五個落點

| 落點 | 放什麼 | 載入方式 |
|---|---|---|
| 1. 全域常駐規則（`CLAUDE.md`、`rules/*.md`） | 跨專案都要遵守的紀律、安全、偏好 | 每個 session 全量載入 |
| 2. 原生 auto-memory（`MEMORY.md` 索引加個別檔） | 使用者偏好、糾正過的做法、跨 session 的小陷阱 | 索引前 200 行自動載入，個別檔按需讀取 |
| 3. 永久架構決策（PAD，放在 `memory/pad/`） | 決策的「為什麼」與背景、佐證 | 規劃或審查時按需讀取 |
| 4. 審計副產物（`patterns/`、`anti-patterns/`、`lessons/`） | 歷史查閱用 | 按需讀取，**不保證新鮮** |
| 5. 專案參考文件（`<project>/.claude/references/*.md`） | 專案的業務紅線、機制、硬限制、SOP、外部 API 規格 | 專案主檔放指標表，用 grep 按需讀取 |

幾個要點：

- **落點 1 是「做什麼」的唯一來源**。要硬性強制的，再往上走一步變成 hook（見另一篇〈Hooks 當強制層〉）。
- **落點 3 與落點 1 是雙軌**：PAD 記「為什麼這樣決定」，常駐規則記「現在要這樣做」。沒有「為什麼」，下個 session 的 AI 會重新推導一遍，有機會得到不同結論。
- **落點 4 後來被我降級成唯讀封存**。原因就是前面提到的：沒人維護、不保證新鮮。會改變行為的教訓，一律晉升到落點 1、2、3 或 5。
- **落點 5 是專案業務知識的唯一來源**，與程式碼衝突時以紅線為準、改程式碼不改紅線。

### 判斷順序：專案 → 全域 → 使用者

不確定放哪時，**從窄到寬**判斷：

| 這則知識是…… | 放哪 |
|---|---|
| 使用者口頭說明的專案業務規則、紅線、機制、硬限制 | 專案 `references/*.md`，並在專案主檔的指標表登錄 |
| 專案實作的教訓、架構債、成功模式 | 專案自己的 memory |
| 跨專案通用的工作流、紀律、工具行為 | 全域 memory |
| 跨專案的個人偏好、使用者所在公司的事實 | auto-memory |

放錯空間的代價是雙向的：放太寬會污染共享範圍，放太窄會造成載入遺漏。

### 一個容易漏掉的細節：索引

auto-memory 的個別檔案**必須在 `MEMORY.md` 索引裡有一行**，才會被自動載入。所以寫入有兩個步驟，要在同一個 turn 完成：

1. 寫個別記憶檔。
2. 在 `MEMORY.md` 追加一行 `- [標題](檔名.md) — 一句話鉤子`。

漏了第 2 步，那則記憶不會進新 session，等於沒存。所以我要求 AI 在宣稱「已記下」之前，必須實際讀一次 `MEMORY.md` 確認那一行存在。

索引那行字的寫法也有講究：它是一句話的「做什麼／別做什麼」，而不是主題標籤。

```markdown
- [zsh 純量不分詞](zsh-word-split.md) — 迴圈裡別對純量變數裸展開，改用陣列或命令替換
```

## PAD：什麼決策該永久保存

大部分記憶都有時效，但有些決策的有效期不是由時間決定，而是由決策本身的性質決定。

舉例：我的 skill 優化工具，對第三方授權的 skill 採「只評分、不修改」的做法，依據是授權條款禁止衍生作品。這個授權性質不會隨時間改變。如果把它當成一般教訓，90 天後被封存，下次 session 的 AI 可能推導出「可以優化這個 skill」，等於踩進授權風險。

### 判斷標準（任一命中就適合）

1. **不可逆**：改變這個決策需要大規模重構，或有授權、法律層級的約束。
2. **跨任務影響**：每個相關任務都必須知道這條規則，不是一次性教訓。
3. **防止重複犯錯**：沒有這條記錄，未來 session 有合理機率重新踩坑。

### 反面判斷

如果一個決策「可能因為框架升級而改變」或「只在這次任務有意義」，就不要放進 PAD。

保守原則：**不確定它是否永久有效，就不要放進去**。進 PAD 應該是主動、有意識的判斷，而不是把「說不定有用」的東西都塞進來。

### 內文四段式

每份 PAD 固定四段：

- **決策內容**：具體的規則或限制是什麼。
- **理由**：為什麼這樣決定、當時的背景。
- **影響範圍**：哪些工具、代理、任務受它約束。
- **不可逆原因**：為什麼不該輕易改變。

### PAD 與常駐規則的同步

PAD 的內容被寫進常駐規則檔之後，要在 PAD 末段補一節「已落地」，列出落地到哪個檔案的哪個章節、哪天、哪些子決策已落地、哪些還沒。

沒有這個標註，未來的 AI 在規劃或審查時會：

- 重複討論已經決議過的取捨。
- 無法判斷 PAD 的內容是不是現行規則。
- 做審計抽樣時無法快速核對。

**標明單一來源**：未落地的子決策以 PAD 為準，已落地的以常駐規則為準。

## 跨 session 接續：用結構化存檔取代自動壓縮

### 自動壓縮的問題

Claude Code 在 context 快滿時會自動壓縮（compact）。壓縮是為了「讓對話變短」，不是為了「讓下一個人接得上」。它會造成三種資訊損失：

- **決策脈絡消失**：「走 X 方案而不是 Y」的理由，壓縮後可能只剩「使用 X 方案」。下個 session 不知道 Y 為什麼被放棄。
- **半成品狀態模糊**：第二階段做到一半，壓縮後可能只剩「已完成第一階段」。
- **失敗嘗試遺忘**：試過 A 做法但發現不穩，這個教訓壓縮後很可能消失，下個 session 會重蹈覆轍。

壓縮演算法不知道什麼是重要的。所以我用一個自訂指令 `/save-context`，在關鍵節點手動做一份**結構化存檔**，保存什麼、用什麼格式，都是可控的。

### 為什麼存成 JSON，而不是摘要文字

接手 session 的目標是**不重讀對話歷史**，直接從檔案恢復狀態。JSON 讓接手方可以精確取出三個最關鍵的欄位：

- `in_progress`：現在要做什麼。
- `failed_approaches`：不要重試什麼。
- `handover_context`：下一步的明確行動。

純文字摘要無法保證這三類資訊各自獨立可定位，而且「讀懂摘要」本身又多一次解讀誤差。

整份 JSON 概念上分五類：

| 類別 | 內容 |
|---|---|
| 識別與時間 | 一句話現況、格式版本、時間戳 |
| 環境快照 | git 分支與 commit、專案路徑與技術棧 |
| 任務進度 | 本次目標、已完成清單、進行中任務 |
| 教訓與決策 | 失敗嘗試與原因、關鍵決策與理由 |
| 交接資訊 | 使用者偏好、關鍵檔案索引、`handover_context` |

### `handover_context` 的寫法：路徑加動詞加狀態

這是整份存檔最重要的欄位，要求三件事：

- **具體路徑**：`WalletService.php:120-145`，不接受「修改 Service 層」。
- **動作動詞**：新增、修復、驗證、執行、刪除；不接受「繼續處理」「接著做」。
- **現在狀態**：完成度，或卡住的原因。

接手方沒有前文，「繼續處理」是零資訊量的交接。

好的例子：

```text
第三階段已完成，第四階段要在 docs/ 下新建 6 個文件。
下一個是 hooks-guide.md，起點是 hooks/README.md 的 hook 清單表。
```

壞的例子：

```text
接著繼續做剩下的文件。
```

### `/save-context` 與 auto-memory 的分工

| | `/save-context` | auto-memory |
|---|---|---|
| 用途 | 這次任務做到哪 | 長期有效的模式與規則 |
| 有效期 | 與任務同壽，完成後棄用 | 跨任務持久 |
| 格式 | JSON（結構化） | Markdown 加 frontmatter |
| 誰讀 | 下個 session 或接手代理 | 所有未來的 session |

一句話判斷：**下次接著做**，用 `/save-context`；**以後都這樣做**，用 auto-memory。

### 什麼時候存

手動場景：

- 任務做到一半要切換。
- 只想記錄某個範圍（可以帶參數指定）。
- 手動 `/compact` 之前。
- 大任務每個階段完成之後。

流程規定的強制時機（不等使用者開口，主代理主動做）：

- 實作階段每個波段派出子代理**之前**。
- 波段結束、整理完交接資訊之後。
- 使用者表達關鍵決策（「走 X 方案」「放棄 Y」）之後。
- 審查的第一輪完成、平行派出大量子代理之前。

### 接手流程

1. 列出任務目錄下的存檔，依檔名時間戳排序。
2. 讀最新的一份。
3. 從 `handover_context`、`in_progress`、`failed_approaches` 恢復狀態。
4. 不重讀整段對話。

### 自動化層：攔截、催辦、恢復

光靠「記得手動存」仍然會漏，所以我又接了三個 hook，彼此互補：

| 機制 | 時機 | 做什麼 |
|---|---|---|
| 壓縮前存檔 | 自動壓縮觸發前 | 先寫一份半成品快照，攔下這次自動壓縮，並留下 session 標記 |
| 催辦注入 | 攔截後，下一次工具呼叫時 | 把「立刻執行 `/save-context`」注入給主代理 |
| 啟動恢復 | 新 session 開始 | 讀最新存檔，直接把現況、下一步注入，導引接續 |

### 一個踩到的坑：攔截訊息模型收不到

壓縮前 hook 攔截時，會回傳一段 `reason` 文字，原本想靠它叫 AI 去存檔。結果實測發現：**`reason` 只會顯示給使用者看，模型根本收不到**。transcript 證明：攔截成功、指令從頭到尾沒進對話、筆記沒寫、之後每次自動壓縮都再被攔，context 就卡在上限，只剩手動壓縮能救。

修法是加上第二個 hook，在攔截之後的下一次工具呼叫，用 `additionalContext` 把指令真正注入給模型。同時加兩道保險絲：

- 10 分鐘內已經有新存檔，就放行壓縮。
- 攔截標記超過 10 分鐘仍沒有新存檔，也放行（逃生閥，退回一般壓縮，不再卡死）。

**教訓**：做「攔截加催辦」的設計時，要確認每一段訊息的接收者是誰。能給使用者看的，不等於能給模型看。

### 存檔路徑

| 情境 | 路徑 |
|---|---|
| 任務分支（不是主幹分支） | 專案工作區的任務資料夾下 `compact-notes/` |
| 主幹分支、非 git 目錄、detached HEAD | 全域的 `compact-notes/` 目錄 |

## 另一個接續問題：多個 session 共寫同一個檔案

跨 session 不只是「前一個 session 傳給下一個」，也包含「兩個 session 同時存在，寫同一份檔案」。我遇過一次幾乎毀資料的事故：

1. session A 寫入了一份共用的 JSON 檔。
2. session B 在背後也修改了同一份檔。
3. session A 再用 Edit 修改，`old_string` 不匹配，失敗。
4. session A 重新 Read 想確認現況，工具回報「檔案自上次讀取後沒變」（**偽陰性**，並沒有偵測到另一個 session 的修改）。
5. session A 據此判斷檔案仍是自己寫的版本，改用整檔 Write 覆寫，B 剛寫的三筆資料全部遺失。

後來靠 B 重寫救回，沒有造成永久損失，但屬於資料損毀級事故。

### 教訓

- **Edit 突然不匹配，是「有人並發修改」的訊號，不是改用整檔 Write 的許可。**
- 覆寫共寫檔之前，用 shell 的 `cat` 或 `jq` 取得檔案的真實內容，不要信任工具的檔案狀態快取。
- 多個 session 共寫的檔案，設計成**單一寫入者**，或改成 append-only。
- 若要用 hook 強制：把「非寫入者的 session 對這份檔案做 Write／Edit」擋下，但 Bash 重導向（`echo > file`）不在 PreToolUse 的 Write／Edit 範圍內，這是已知的缺口。

## 新規則落地後，馬上用它跑下一步

記憶與規則的「可操作性」常常要到用了才知道。我留下的一條經驗是：**新約束規則落地後，立刻用該規則執行下一個同類任務，是最低成本的驗證**。

例如我導入了「審查的每個發現都要附證據三件套」的規則，落地後第一個使用者就是下一次審查本身。審查報告的每一條發現都符合三件套格式，這就驗證了規則可操作，不用等到累積多個任務才評估。

同一次升級還有一條相關的教訓：靜態檢查（`grep`、`wc`、`bash -n`）全過，不代表 hook 在 pipeline 環境下行為正確。兩個動態 bug（YAML 解析與 PPID 不穩定）都是靠「真的跑一次、讀輸出」才發現的。**hook 任務的驗收清單要包含管線測試**：

```bash
echo '{"tool_name":"Bash","tool_input":{"command":"..."}}' | bash hook.sh
echo "exit=$?"
```

## 可直接套用的檢查清單

- [ ] 寫記憶前先判定落點：這是規則、偏好、決策的原因、教訓，還是專案紅線？
- [ ] 使用者口頭說明專案的機制或紅線，有寫進專案 `references/`，並在專案主檔登錄指標嗎？
- [ ] 新的 auto-memory 檔，同一個 turn 有加進 `MEMORY.md` 索引嗎？
- [ ] 想放進 PAD 的決策，符合「不可逆、跨任務、防重複犯錯」其中之一嗎？
- [ ] PAD 內容落地到常駐規則後，有標「已落地」嗎？
- [ ] 存檔的 `handover_context` 有「具體路徑加動詞加現況」嗎？
- [ ] 設計過期或封存機制時，有人真的在執行它嗎？沒有的話，直接降級成唯讀封存，不要保留一條不會被執行的規則。
- [ ] 多個 session 共寫的檔案，有單一寫入者或 append-only 的設計嗎？
