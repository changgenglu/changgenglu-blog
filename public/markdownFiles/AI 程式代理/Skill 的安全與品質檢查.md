# Skill 的安全與品質檢查

> 裝別人寫的 skill 之前，要怎麼檢查它安不安全？有了自己的 skill，又怎麼知道它有沒有在好好工作？這篇記錄我試用兩個公開工具的結果：一個是 NVIDIA 的靜態掃描器 SkillSpector，一個是用真實對話替 skill 打分的 skill-doctor。結論是兩者都有用，但都有不能照單全收的地方。2026 年寫成。

## 兩個問題，兩種工具

| 問題 | 時間點 | 工具類型 | 本文的例子 |
|---|---|---|---|
| 這支外來的 skill 有沒有惡意或危險的寫法？ | 安裝前 | 靜態安全掃描 | SkillSpector |
| 我已經裝的 skill，實際使用時有沒有幫上忙？ | 使用後 | 用真實對話評分 | skill-doctor |

先講背景：skill 其實就是一包「會被模型當成指令讀進去」的文字，外加可能附帶的可執行腳本。風險有兩面：

- **文字面**：內文夾帶 prompt injection（藏在說明裡的惡意指令），或誘導模型把資料送出去。
- **腳本面**：附帶的 Python、shell 腳本可能做你沒預期的事。

## SkillSpector：安裝前的靜態掃描

### 它是什麼

SkillSpector 是 NVIDIA 公開的 AI agent skill 安全掃描器（GitHub：NVIDIA/SkillSpector），支援 Claude Code、Codex CLI、Gemini CLI 等平台的 skill。我試用的是 v2.1.5。

- 偵測範圍：16 類、64 種 pattern，包含 prompt injection、資料外洩、權限提升、供應鏈、觸發濫用、惡意簽章、MCP 權限等。
- 兩階段管線：先靜態分析（正規表示式加語法樹，高召回、中等精確），再選用 LLM 語意分析過濾誤報（官方稱精確度可到約 87%，我沒有驗證這個數字）。
- 風險分數 0 到 100，對應 SAFE、CAUTION、DO NOT INSTALL。

```bash
git clone --depth 1 https://github.com/NVIDIA/skillspector.git
uv sync --project skillspector
uv run --project skillspector skillspector scan <目標路徑> --no-llm
```

`scan` 支援目錄、單檔、Git URL、zip，輸出格式有 terminal、json、markdown、sarif。我用的是 `--no-llm` 純靜態模式。

### 試跑結果

我拿兩個自己的 skill 做對照：

| Skill | 結構特徵 | 分數 | 判定 |
|---|---|---|---|
| 一支畫文字圖表的 skill | 純文字，無腳本，無額外工作目錄 | 0/100 | SAFE，0 個 issue |
| 一支 skill 優化器 | 含 Python 腳本，工作目錄塞滿備份 | 100/100 | CRITICAL，DO NOT INSTALL（4 個 HIGH、3 個 MEDIUM） |

乾淨的那支判定準確。爭議全在第二支的滿分 CRITICAL。

### 100 分是誤報放大

拆開 7 個 finding：**沒有任何一個是 CRITICAL**（4 個 HIGH、3 個 MEDIUM），分數卻封頂在 100。原因有三個。

#### 根因一：計分不按信心加權

計分規則是 CRITICAL 加 50、HIGH 加 25、MEDIUM 加 10、LOW 加 5，含可執行腳本再乘 1.3：

```text
4 個 HIGH   × 25 = 100   <- 已達上限
3 個 MEDIUM × 10 = +30
有可執行腳本 × 1.3 -> 封頂 100/100 CRITICAL
```

而這 4 個 HIGH 的偵測信心其實**只有 65%**。分數機制完全不參考信心值，低信心的 finding 一樣足額加分。

#### 根因二：誤報來源是「文件在討論危險詞」與「備份資料」

| Finding | 位置 | 真相 |
|---|---|---|
| HIGH：工具參數濫用 ×4 | 幾份說明文件，以及備份目錄內的檔案 | 文件**文字提到** `shell=True`、`-rf /` 這類危險 pattern；那支 skill 是優化器，教學內容本來就會討論這些。正規表示式把「提到」當成「做了」 |
| MEDIUM：session 持久化 | 工作目錄內其他 skill 的備份副本 | 是備份，不是執行邏輯 |
| MEDIUM：間接 prompt 外洩 | 工作目錄內的 baseline 備份 | 同上 |

掃描器把這些**資料檔當成執行內容**掃，疊加文件裡的危險詞討論，分數就爆表了。

#### 根因三：唯一較合理的 finding 仍是標準落差

那個 MEDIUM（偵測到檔案讀寫能力卻沒宣告 `permissions` 欄位），但 Claude Code 的 `SKILL.md` 本來就沒有 `permissions` 機制。這是 NVIDIA 的標準與 Claude Code 慣例的落差，不是真實漏洞。

### 這類工具的限制

這次試跑印證了官方 README 提到的限制：

- 純靜態正規表示式對「文件在討論危險詞」**完全沒有辨識力**。教學型、優化型、文件型 skill 的誤報率高。
- 備份檔、測試資料都被當執行內容掃。
- 中文內容下，語意類偵測（prompt injection、觸發濫用）幾乎使不上力。
- 只做靜態分析，不執行程式碼，看不到執行期行為。
- 完整的漏洞資料庫查詢要連外網，離線只用內建小清單。

### 怎麼用才合理

| 場景 | 建議 | 理由 |
|---|---|---|
| 粗篩來路不明的外部 skill | 適用 | 真正的惡意腳本會被語法樹與簽章規則抓到，是有價值的第一道防線 |
| 掃自己寫的、含大量文件與備份的 skill | 謹慎 | 純靜態誤報極高，分數要大幅打折 |
| 信任哪些 finding | 真實 `.py` 腳本內的 > `.md` 或備份目錄內的 | 後者多半是文字討論或備份資料的誤判 |
| 降低誤報 | 開啟 LLM 語意階段（需 API key） | 官方稱可過濾文字誤報；我**未實測** |

**一句話**：它適合當「安裝前粗篩外部 skill」的第一道，但分數（尤其是 HIGH 封頂機制）不能照單全收。對中文、文件型、含備份的 skill，要人工複核每個 finding 的落點再判定。

## skill-doctor：用真實對話替 skill 打分

### 它在做什麼

skill-doctor 是一個公開的 skill（GitHub 上 warpdotdev/common-skills 的一個目錄），做的事是：

1. 讀本機各種程式代理的對話紀錄（Claude Code、Codex 等六種）。
2. 用兩張評分表（效率、程式碼品質）替每個取樣 session 打分。
3. 聚合成加權總分：效率 0.5、程式碼品質 0.35、skill 涵蓋率 0.15。
4. 從「失敗的對話」（任一評分低於 0.5）反推哪些 skill 的描述沒觸發、哪個步驟被試錯出來。
5. 草擬具體的 `SKILL.md` 修改 diff。
6. 渲染成一頁自足的 HTML 報告。

### 值得學的設計

我讀完它的 17 個設計點後，覺得最值得借鏡的是這幾個：

- **草稿與落地分開**：建議一律先落在暫存目錄，「套用到你真正的 skill 檔」是另一個需要使用者同意的獨立步驟。這是把「產出建議」與「實際改動」拆成不同信任等級的做法。
- **同一缺口要在多個 session 出現才提修改**（或單一但夠嚴重），防止拿一個雜訊 session 就改 skill（過擬合）。
- **區分「指令缺口」與「模型變異」**：如果既有的指令已經寫了正確行為、模型卻沒遵守，那不是指令缺口，改文字治不了。
- **「沒證據」不等於「品質差」**：評分表有第三種標籤 `insufficient_evidence`，從平均中排除，而不是算成壞分。
- **預設不主動提修改**：明文「猜測性的修改比不改更糟」，對抗模型為了有產出而硬找問題的傾向。
- **兩份評分表互相聲明「不在範圍」**：避免同一個缺陷被兩張表各記一次、灌水扣分。
- **每條建議必須帶獨立的證據欄位**（哪個 session、發生了什麼），把「引用證據」變成結構欄位，而不是交給散文自由發揮。

### 先做准入查核：它宣稱「全部在本機跑」是真的嗎

這支工具要讀你全部的對話紀錄，風險很高。它的說明寫「Everything runs locally. Never upload transcripts」。我的做法是不先信，對 5 個腳本檔逐一查：

- 有沒有任何出站網路函式庫的 import（`requests`、`urllib.request`、`http.client`、`socket`）。
- 有沒有可疑的網路字面值。

結果通過：沒有任何出站網路 import；唯一命中「upload」字樣的是某個資料格式的欄位名稱常數（事件類型的解碼用）；唯一的對外互動是用 `file://` 在本機瀏覽器開報告。

**但要注意准入查核只回答「會不會外送」，不回答「本機留下什麼」**。

### 本機落檔的風險：沒有脫敏

查核時另外發現：它把濃縮過的對話寫進本機暫存目錄，而且**全程沒有任何脫敏或過濾邏輯**。我對整份程式碼 grep `redact|secret|password|token|api_key|sanitiz`，只命中變數名稱與截斷邏輯，沒有一處做內容過濾。

後果：如果對全歷史跑一次，查詢結果裡的憑證字面值、正式環境資料都可能原文出現在暫存目錄的 Markdown 檔裡。「不外送」與「不留下」是兩件事。

這是我對所有「讀取對話紀錄」類工具的檢查重點：

- 紀錄存在哪裡？權限是什麼？
- 有沒有脫敏？
- 用完誰負責刪？
- 是否限縮範圍（它有 `--repo` 參數只掃某個專案，這是比較安全的預設）。

### 範圍限縮的相容性：一個隱性缺口

它的 `--repo` 比對邏輯是：session 的工作目錄落在該 repo 內，或「repo 名稱」出現在工作目錄的路徑元件裡（完全相等的成員檢查）。

我的 worktree 命名慣例是 `<專案>-workspace/<分支名>/`。worktree 目錄叫分支名，repo 名稱只出現在上一層、而且是 `<專案>-workspace` 這個完整元件，並不等於專案名本身。所以 `"專案名" in ["專案名-workspace", "分支名"]` 為 False，**對非主 checkout 的 worktree 跑 `--repo` 時，會漏掉那些 session**。

教訓：套用別人的工具時，要確認它對「你自己的目錄慣例」是否成立，不能只看它在自己 README 的範例上能不能跑。

### 它與我既有工具的關係

我已經有三個相近的東西，所以先劃清楚：

| 軸 | skill-doctor | 我自己的 skill 優化器 | 週期性設定健診 |
|---|---|---|---|
| 觸發 | 使用者主動要「用真實對話打分」 | 使用者主動要「對某 skill 做迭代優化」 | 週期性 |
| 範圍 | 全部已裝的 skill | 單一指定的 skill | 全部已裝的 skill |
| 證據來源 | 真實歷史 session，逐筆 LLM 評分 | 合成的測試提示，A/B 對照 | 聚合統計 |
| 產出 | 逐 session 引證的 SKILL.md diff | 迭代改版與 git 保留／回滾 | 「已整合／未整合」的 finding，不產 diff |

三者座落在不同軸（廣度、證據型態、週期），並存不衝突。**真正的能力缺口**是「用真實歷史 session 逐筆評分，並把證據綁定到草擬的 diff」，另外兩個都沒有。

## 兩個工具放在一起看

| | SkillSpector | skill-doctor |
|---|---|---|
| 看什麼 | skill 的內容與腳本 | 實際使用時的對話 |
| 時間點 | 安裝前 | 使用後 |
| 最大風險 | 誤報放大，分數不可信 | 本機落檔未脫敏 |
| 不可替代之處 | 能抓真實的惡意腳本 | 能看到 skill 在真實任務中沒觸發或沒幫上忙 |
| 我的使用建議 | 粗篩外部 skill；人工複核 finding | 限縮範圍；用完清掉暫存；不全歷史掃描 |

兩者都不是「跑了就放心」的工具。

## 通用的審查流程（我自己的檢查順序）

裝一支外部 skill 前：

1. **看來源**：誰寫的、有沒有人維護、授權條款是什麼。
2. **看有沒有腳本**：純文字 skill 風險低；有腳本的先讀腳本。
3. **grep 危險動作**：網路呼叫、寫檔位置、`eval`、`curl | sh`、讀取憑證的路徑。
4. **跑靜態掃描當輔助**，每個 finding 回頭看落在哪個檔案。落在文件或備份的，通常是誤報。
5. **在隔離環境試跑一次**，看它實際寫了什麼檔案。
6. **確認它對你的環境慣例成立**（目錄結構、路徑、語言）。

- [ ] 讀取對話紀錄的工具，有查過它「不外送」的宣稱嗎（grep 網路 import）？
