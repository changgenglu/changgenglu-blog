# 主代理調度、子代理執行：為什麼要分層

> 讓單一 AI 程式開發代理（coding agent）從頭做到尾，做大任務時會遇到哪些結構性問題？本文整理我為什麼把工作拆成「主代理調度、子代理執行」兩層，以及這個分層怎麼運作。寫於 2026 年，範例以 Claude Code 為主，概念同樣適用於其他支援子代理（sub-agent）的工具。

## 問題：一個對話扛下整個開發任務

直接叫一個 AI 代理「做完這個功能」，小任務沒事，任務一大就會出現三個問題。

### 1. 脈絡爆炸（context 爆炸）

規劃、實作、審查的細節全部堆在同一個對話裡。模型能有效注意的內容有限，對話越長，前半段講過的限制條件越容易被忽略。常見症狀：

- 第 30 輪的時候，忘了第 3 輪說過「這個欄位不能動」。
- 為了讀 7 個檔案的全文，把主對話塞滿，後面要做決策時反而沒空間。
- 一個長 session 做完實作，審查階段已經沒有餘裕仔細看。

### 2. 品質不穩：自己審自己

同一個模型既寫規劃、又寫程式、又負責審查，它對自己的盲點通常視而不見。這不是「它不夠聰明」，而是推理鏈同源：後面的判斷被前面的假設條件化，看起來像多視角，其實是同一條思路走第二遍。

### 3. 無法平行

複雜功能其實有很多互不相依的子任務，例如同時新增三個獨立的 API 端點。單一對話只能一件一件排隊做。

## 核心做法

**主代理（main agent）只負責調度與決策，大量讀取與實作交給子代理（sub-agent）。**

三層結構：

```text
使用者
  │  提需求、確認規劃、決定修復項目
  ▼
主代理 ── 需求釐清、路徑判斷、品質把關、在決策點停下來問人
  │
  ├─▶ 分析型子代理：規劃、架構設計
  ├─▶ 執行型子代理：實作程式碼（可依層次拆多個）
  └─▶ 審查型子代理：從不同維度挑問題
```

主代理的 context 只放「調度邏輯與決策」。每個子代理只看自己那一份任務，做完回報一份結構化結果，主代理只收結論、不收過程。

這個設計有五條原則，下面逐條說明為什麼。

### 原則 1：主代理不寫程式碼

主代理負責：理解需求、拆分工作、驗收、在關鍵岔路停下來問人。實際動手的事交給子代理。

好處很直接：主 context 保持乾淨，不被每個子任務的技術細節佔滿。代價是要多一層「把任務講清楚」的成本，這也是後面兩篇筆記（委派模板、完成證據）要處理的事。

什麼算「該委派」？我給自己訂了幾個數字門檻，命中任何一條就委派：

- 預期要讀 3 個以上檔案的全文
- 任何單一檔案超過 500 行
- 要掃整個 repo 並逐筆判讀
- 要查 2 個以上網頁
- 要對 3 個以上檔案套同一個模式
- 探索性實作（不知道要改哪裡，要邊讀邊找）

反過來，也要有「煞車」：改法已經確定、3 次工具呼叫內能做完的機械小改，直接做就好，不要為了形式派子代理。門檻寫成數字的原因是：「這個任務夠不夠複雜」靠感覺判斷，模型很容易替自己找理由（「我掌握最深」「來回溝通太貴」）。數字不完美，但至少可以事後檢查有沒有違反。

> 這些數字是我初設的值，沒有經過量測校準。我把它們視為「待校準的預設」，定期抽幾個任務比較「自己做」與「委派」對主 context 的實際增量，再調整。

### 原則 2：流程驅動，不是指令驅動

使用者不需要記一堆指令，用自然語言說「幫我做一個 X 功能」即可。由主代理判斷：

- 要不要先規劃？
- 走哪一條實作路徑？
- 什麼時候必須停下來讓人拍板？

這部分的細節寫在下一篇〈規劃、實作、審查：AI 協作的開發流程〉。

### 原則 3：多模型交叉驗證

審查階段同時動用不同的模型（例如 Claude 加上 Gemini）。不同模型的盲點不同，交叉看能攔下單一模型看不到的問題。這是「自己審自己」問題的直接對策之一；更進一步的做法見〈多代理對抗審查 loop〉。

### 原則 4：共用護欄，行為一致

所有子代理都引用同一份行為約束（不要全域格式化、不要碰範圍外的檔案、不要用破壞性 git 指令）與同一份輸出格式。這樣不管派哪個子代理，主代理驗收時都有統一標準，不用為每個角色重新記一套規則。

### 原則 5：每個子代理單一職責

規劃代理只規劃、安全審查代理只看安全、建置修復代理只解 CI 錯誤。單一職責讓每個代理的提示詞可以針對性優化，不必兼顧各種情境。

## 為什麼子代理不能取代「對話」

有一件事子代理做不到：**多輪對話**。子代理被派出去之後，遇到模糊的需求只能猜，或者停下來問；而一停下來問，就得重新切換脈絡。

所以我把「需求釐清」留在主代理身上：

- 主代理跟使用者來回確認背景、目標、方案選擇、驗收標準。
- 確認清楚之後，才把整理好的結論一次交給規劃子代理。

這也衍生出一條實務規則：**需要和使用者來回澄清的任務留在主代理，不要派子代理。**

## 怎麼運作：一次委派的生命週期

以「新增一個查詢端點」為例（概念示意，非特定專案）：

1. 使用者提出需求，主代理跟使用者確認背景與驗收標準。
2. 主代理把確認好的需求交給規劃子代理，產出規劃報告（落檔，不貼進對話）。
3. 使用者確認規劃。
4. 主代理把實作任務拆好，派給執行型子代理，每個子代理拿到明確的檔案範圍與驗收條件。
5. 子代理回報：結論、證據、狀態。長內容寫成檔案，只回傳路徑與摘要。
6. 主代理驗收（跑驗收指令、檢查檔案內容），不是轉述子代理的話。
7. 審查型子代理從不同角度挑問題，最後由使用者決定哪些要修。

整個過程裡，主 context 只出現：需求討論、規劃報告路徑、各步驟的結論、驗收證據。沒有任何一個子任務的細節污染它。

## 用哪個模型跑子代理

模型選擇依「任務性質」，不是依「檔案多不多」：

| 情境 | 建議 | 理由 |
|---|---|---|
| 一般預設 | 中階模型 | 多步驟工具使用的甜蜜點，量大但規則明確的工作也適合 |
| 純機械、低風險 | 小模型 | 列檔、格式整理、單一搜尋摘要；prompt 要短、目標單一 |
| 高歧義 | 大模型 | 要選邊並說服人的設計、複雜 bug 根因、架構或安全審查 |

幾個補充：

- 升級看的是「歧義深度」，不是「量」。300 行機械搬移，用中階模型就好，檔案多不等於要升級。
- 模型層級與 prompt 長度是兩件獨立的事。prompt 太長造成的失敗，先縮短 prompt，不要用升模型來掩蓋。
- 不同模型對 prompt 結構的反應不同：大模型加上範圍框，避免它「善意地」多做；中階模型用 checklist 或表格；小模型只給單一目標與明確輸出格式。

> 以上是我在自己環境觀察到的使用心得，不是對各模型的嚴格評測。

## 踩過的坑與教訓

### 規則寫在文件裡，不等於會被遵守

我曾經有一次明確違反自己的委派門檻：主代理親手重寫一個 549 行的服務檔，又改了十幾處測試。事後它自己的推理紀錄顯示，它**清楚意識到門檻已命中**，卻以「我掌握最深、委派溝通成本高」為由自己做。

這個事件有三個教訓：

1. **「優先但非自動」的措辭，給了模型說服自己的空間。** 規則要寫成「命中就必須」，不留「通常」「優先」這種彈性字眼。
2. **自律是單點防線。** 光靠文件，一次疏忽就全失效。需要至少一個外部的偵測或強制層（例如 hook 記帳、超過門檻攔截）。
3. **「越線前明示」比「禁止」好用。** 與其禁止主代理動手，不如要求：第一次動手改程式碼檔之前，先寫一句「命中哪條門檻、為什麼不委派」，然後停下來等使用者回應。這個動作是可觀察的，可以事後檢查；而「思考中是否權衡過」是不可觀察的。

### 唯讀分析也會越線

後來又發現另一種越線：主代理一行程式碼都沒寫，但是跨 3 個檔案讀碼診斷，還產出方案 A 與方案 B 的完整比較。所有「看你有沒有 Edit/Write」的偵測都看不到這種情形。

我評估過幾個偵測方向（讀取次數計數會誤判太多，因為讀 3 個檔是日常），最後採用最保守的一個：**只記帳、不阻擋**，記錄主代理每個任務實際讀了多少非文件檔案，先累積真實分布，再決定要不要設門檻。沒有資料之前，任何門檻都是猜的。

### 把審查也外包，仍然要自己驗收

子代理回報「完成」不是終點。主代理對寫過檔的子代理，至少要做一次最小驗證（例如 `grep -c` 驗收字串、`wc -l` 檢查行數）。這部分展開在〈宣稱完成要有證據〉。

## 可直接套用的檢查清單

開始一個任務前，問自己：

- [ ] 這個任務需要來回澄清嗎？需要 → 留在主代理。
- [ ] 預期要讀幾個檔案全文？有沒有單檔超過 500 行？
- [ ] 是不是探索性工作（不知道改哪裡）？是 → 委派。
- [ ] 改法是否已經確定、3 次工具呼叫內能完成？是 → 直接做。
- [ ] 如果我打算自己動手改程式碼檔，而任務已命中任何門檻：先寫下命中哪條、為什麼不委派，等使用者回應。
- [ ] 子代理回報後，我有自己跑一次驗收指令嗎？

## 小結

- 單一對話做大任務，會遇到脈絡爆炸、自評盲點、無法平行三個結構問題。
- 分層解法：主代理管調度、決策、驗收，子代理管讀取與實作；需求釐清留在主代理。
- 門檻用數字寫，並加上「越線前明示」這種可觀察的動作；光靠文件規則不夠，要有偵測或強制層。
- 分層本身有成本（要把任務講清楚、要驗收）。後續幾篇處理這些成本：委派模板、完成證據、審查流程。
