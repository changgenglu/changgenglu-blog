# GitLab Issue 驅動的 AI 自動開發（一）架構

> 本篇說明我為什麼把「規劃、實作、審查」拆給不同的 AI session，並用 GitLab 的 label 加留言當作唯一的狀態儲存，讓常駐程式（worker）重啟也不會丟進度。2026 年寫成，是三篇系列的第一篇；範例都是虛構資料。

系列目錄：

- （一）架構：本篇
- （二）狀態機與卡單處理
- （三）設計教訓與 glab 踩坑

## 問題：三個階段沒有共同的對話脈絡

用 AI 寫程式時，最順的情況是同一個 session 從頭做到尾。但實際上我遇到的情況是：

- 規劃是「人加上一個 AI session」討論出來的，對話很長，前提都在對話裡。
- 實作如果交給另一個 session，甚至另一台機器，它看不到規劃時的對話。
- 審查如果由同一個 session 做，等於自己審自己，很容易自己放過自己。

所以我需要一條管線，滿足兩件事：

1. 交接只靠「issue 內文」與「GitLab 上看得到的狀態」，不靠任何 session 記憶。
2. 人只在兩端出現：發單，以及最後合併。中間的實作、審查、修復由程式推進。

這套東西的核心取捨是：**寧可把每一步都寫在 GitLab 上，也不要讓任何元件「記得」什麼。**

## 整體架構：三層

我把它切成三層，每層職責單純：

```text
┌────────────────────────────────────────────┐
│ 規劃端（人 + AI session）                    │
│   操作手冊（skill）+ 發單前的檢查腳本          │
└──────────────────┬─────────────────────────┘
                   │ 發 issue、貼 label
┌──────────────────▼─────────────────────────┐
│ GitLab：label 狀態機 + issue/MR 留言          │
│   ← 唯一的狀態儲存                            │
└───────┬────────────────────────┬───────────┘
        │ 輪詢                    │ 輪詢
┌───────▼──────────┐   ┌─────────▼──────────┐
│ 實作 worker       │   │ 審查 worker         │
│ 常駐 Node 程式    │   │ 另一支常駐程式       │
└──────────────────┘   └────────────────────┘
```

- **規劃端**：一份操作手冊（對 Claude Code 來說是一個 skill），告訴規劃用的 session 怎麼依範本發 issue、怎麼放回卡住的單。
- **GitLab 層**：一組 label 表示「這張單現在在哪個階段」，留言表示「發生過什麼事」。
- **worker 層**：兩支常駐程式，一支負責實作與修復，一支負責審查。它們自己不是 AI，只是排程與守門的程式；真正寫程式與審查的，是它們啟動出來的無頭（headless）AI session。

這個結構不綁特定工具。我實際上用的是 Claude Code 的無頭模式（`claude -p`），但任何能在命令列非互動執行、能讀寫工作目錄的程式碼代理都能套進同一個位置。

## 角色

| 角色 | 是誰 | 做什麼 |
|---|---|---|
| 規劃者 | 人加上一個 AI session | 規劃、依範本發 issue、貼上待認領 label；最後把 Draft MR 標成 ready 並合併 |
| 實作 worker | 常駐程式，跑在擁有者的機器 | 認領單、在獨立 git worktree 啟動無頭 session 實作、自己再跑一次測試、開 Draft MR |
| 審查 worker | 另一支常駐程式 | 認領待審的單、在自己的 worktree 重跑測試、審 MR diff、貼審查結果 |
| 擁有者（owner） | worker 或 session 所屬的人 | 用來決定「誰該被通知」，以及審查者不可以是同一個擁有者 |

兩條設計原則，後面會一再用到：

- **審查者預設與實作者不是同一個擁有者，session id 也必須不同。** 防止自己審自己。
- **規劃者只在兩端出現。** 中間的所有狀態變化都是程式依規則做的。

## 觸發方式：輪詢，不是 webhook

常被問的一點：為什麼不用 webhook、不用 CI 觸發？

我選擇「常駐程式輪詢」，原因是：

- webhook 需要有一個對外可連的接收端，在個人機器或 WSL 上很麻煩。
- CI 的執行環境不是我那台有完整開發環境、有已登入 AI 工具的機器。
- 輪詢出錯的後果最容易推理：下一輪再做一次就好。

具體參數（我的預設值，不是通則）：

- 實作 worker 每 60 秒輪詢一次，再加 0 到 15 秒的隨機延遲，避免多台機器同時搶同一張單。
- 建議用 systemd 的使用者服務常駐，開機自啟、掛掉重啟，並可設記憶體上限。
- 首次啟動預設是乾跑（dry run）：只在紀錄裡寫出「我打算做什麼」，不真的寫 GitLab。確認行為符合預期後才關掉乾跑。

明確不做的事（寫下來才不會被一直問）：

- 不接 GitLab CI。
- 不用 webhook。
- 不做「審查者額度用完就換人接手」。
- 不支援 Windows 原生命令列（WSL 可以）。

## 狀態只存在 GitLab：這是最重要的設計

整套流程的狀態只有兩個來源：

1. issue 或 MR 上的 **label**：現在在哪個階段。
2. issue 或 MR 上的 **留言**：發生過什麼、誰認領了、測試輸出是什麼。

任何輔助通知（例如傳訊息提醒某人）只當「加速器」，內容不承載狀態，收不到也不影響流程。通知的原則是「issue 留言 @ 對方」當保底，直送訊息當加速、允許失敗。

這帶來一個很實用的性質：**worker 不需要記憶。** 重啟後它只做兩件事：

1. 重新輪詢 label，找出該自己處理的單。
2. 依留言的建立時間，重新計算所有逾時。

不需要資料庫、不需要本機狀態檔。機器重開、程式崩潰、換一台機器接手，行為都一致。

### 一個類比

把 GitLab 想成一間共用的白板，每張單是白板上的一張便利貼：

- 便利貼的顏色是 label（待處理、進行中、受阻、完成）。
- 便利貼背面的簽名與時間是留言（誰拿走了、什麼時候拿的）。
- worker 是輪班的工讀生，每次上班都只看白板，不看前一班留下的任何私人筆記。

類比對到本案：便利貼就是 issue，顏色就是 label，背面簽名就是 `[claim:…]` 這類留言。worker 重啟等於換班，但白板不變，所以進度不會丟。

## 一次順利的完整路徑

用虛構的例子走一遍。專案是 `example/app`，issue 是 #1，要做的事是「新增一個匯出 CSV 的指令」。

1. **規劃者發單。** 依範本寫好 issue #1，通過發單前的機械檢查後，貼上 `ready-for-claude`。
2. **實作 worker 認領。** 它在 issue 貼一則認領留言，label 換成 `claude-in-progress`。
3. **實作。** worker 在獨立的 git worktree 啟動無頭 session。session 依 issue 內的任務拆分，一個任務一筆提交。
4. **守門檢查。** session 結束後，worker 先檢查這段 session 的 git 歷史有沒有違規動作（細節在第三篇），再自己跑一次測試指令，不採信 session 自己說的「測試過了」。
5. **開 Draft MR。** 推送分支、開 Draft MR，描述第一行是 `Closes #1`；issue 上貼交接留言，label 換成 `ready-for-review`。
6. **審查 worker 認領。** 在自己的 worktree 再跑一次測試，審 MR diff，把結果貼在 MR 上。
7. **分岔：**
   - 通過：label 換成 `review-passed`，通知規劃者。
   - 有問題：label 換成 `ready-for-review-fix`，指名原實作者修復，修完回到第 6 步重審。
8. **交回規劃者。** 規劃者看到通過通知，把 Draft MR 標成 ready，人工合併。

修復輪最多 5 輪；第 5 輪仍有問題就轉人工，不再自動空轉。

時序示意：

```text
規劃者        實作 worker       審查 worker        GitLab
  │ 發單        │                  │                 │
  ├────────────────────────────────────────────────▶ ready-for-claude
  │            │ 輪詢到、認領       │                 │
  │            ├─────────────────────────────────────▶ claude-in-progress
  │            │ 實作→守門→測試     │                 │
  │            ├─────────────────────────────────────▶ 開 Draft MR
  │            │                  │                 ready-for-review
  │            │                  │ 輪詢到、認領      │
  │            │                  ├──────────────────▶ review-in-progress
  │            │                  │ 重跑測試、審 diff  │
  │            │                  ├──────────────────▶ review-passed
  │ ◀───── 通知 ─────────────────────────────────────┤
  │ 標 ready、合併                                    │
```

## 發單：issue 必須自包含

實作者看不到規劃對話，所以 issue 就是唯一的規格書。我用範本強制以下幾點。

### 頂端固定欄位

issue 描述最前面放幾行固定格式的欄位，worker 只解析這些鍵，其餘內文原樣交給實作 session 當規格：

```text
Planner-Owner: alice
Planner-Session-Id: 00000000-0000-4000-8000-000000000000
Depends-On: #1
Base-Branch: develop
Requires-Env: TEST_DB_URL
Implement-Model: sonnet
Review-Model: sonnet
Model-Reason: 需要在兩種設計間取捨，但改動範圍小
```

- `Planner-Owner`、`Planner-Session-Id`：必填，用來找人與追溯規劃當時的 session。
- `Depends-On`：上游的單必須已關閉或已有合併的 MR，才放行這張。
- `Requires-Env`：需要哪些環境變數；缺少的機器會跳過這張單，留給有的機器。
- `Implement-Model`、`Review-Model`：選模型。

選模型的判準我覺得值得抄：**看「需要多深的判斷」，不看改動多大。** 行數很少但要在兩種設計間取捨，就用較強的模型；很多處但套同一個模式，用較弱較便宜的就夠。審查模型我設定不低於中階，涉及安全的單審查用最強的。

### 內文結構

- 背景與 Goal。
- Scope：允許修改與禁止修改的範圍。
- 驗收條件：用 Given/When/Then 寫、編號，至少涵蓋成功、三個邊界、一個錯誤情境。
- 驗證指令（含測試指令 `TEST_CMD`）。
- 未驗證假設：每一項寫「如果錯了會怎樣」與「怎麼驗證」。
- 實作任務拆分（T1、T2…），讓實作 session 一個任務一筆 commit，提交訊息帶任務編號。

寫作規則只有幾條，但很有用：

- 不寫檔案系統路徑，不寫「見之前討論」，因為讀的人沒有那段脈絡。
- 具體到可驗證，範圍要有邊界。
- 不夾帶機密。
- 需要拍板的事先問完再發單。

一個容易漏的細節：**測試指令必須能在多個 worktree 同時跑**，例如測試資料庫名稱、快取 key 要有前綴區隔。worker 會把一個叫 `WORKTREE_SLUG` 的環境變數注入 session，供指令組出不重複的名稱。

### 發單前的機械檢查

我寫了一支檢查腳本：

```bash
node scripts/check-issue.js --project example/app issue-body.md
```

結束碼不是 0 就不得建單。這支腳本與 worker 認領前的攔截共用同一套解析規則。worker 端的攔截是最後防線，擋網頁上手動開的單，以及被事後改壞的描述；被擋下的單 worker 會貼一則拒收留言，不處理。

## 留言協議：機器要讀得懂

worker 之間靠留言溝通，所以留言有嚴格格式：

- 標記行必須是留言的**第一行**，格式 `[標記名]`，後面是 `key: value` 的單行欄位。
- 自由文字放在明確的分隔線之後。
- session id 用小寫 UUID，時間用 ISO 8601 的 UTC。
- 同一種標記有多筆時，取建立時間最新的一筆。
- 所有逾時一律用 GitLab 留言的建立時間起算，不用 issue 的更新時間；「現在幾點」讀 worker 機器的時鐘，與 GitLab 差超過 60 秒啟動時就印警告。

一則認領留言長這樣（虛構）：

```text
[claim:implement]
owner: alice
session-id: 00000000-0000-4000-8000-000000000001
lease-until: 2026-01-01T00:15:00Z

認領中，開始實作。
```

幾個主要標記：

| 標記 | 用途 |
|---|---|
| `[claim:…]` | 認領，同時是租約（第三篇詳述） |
| `[review-ready]` | 實作完成的交接，含測試的原始輸出與結束碼 |
| `[review-claim:…]` | 審查者認領 |
| `[review-result]` | 貼在 MR，結論是通過或有 findings |
| `[review-fix-complete]` | 修復完成 |
| `[env-blocked]` | 環境或規劃受阻，停單 |
| `[planner-notify]` | 通知規劃者 |

另有一組雙向問答標記，讓審查者能問實作者、修復者能問審查者，但有額度（預設每個方向每張單 2 次）與逾時退路，避免兩邊互相等。

### 一個重要的限制

**一般留言不會進任何 worker session。** worker 只讀 issue 描述，以及特定標記的留言。所以中途想給實作者提示，不能隨手留一句話。要嘛改描述（新開的 session 才會重新抓），要嘛走正式的需求修訂標記，才能確定被讀到。

## 時限與門檻速查

這些是我的預設值，每項都可以調：

| 項目 | 預設 |
|---|---|
| 輪詢間隔 | 60 秒加 0 到 15 秒隨機 |
| 心跳間隔 | 5 分鐘 |
| 租約過期 | 15 分鐘 |
| 實作、審查 session 上限 | 各 45 分鐘 |
| 測試指令上限 | 30 分鐘 |
| 修復輪上限 | 5 輪 |
| 雙向問答額度 | 每方向每單 2 次 |
| 問答逾時 | 90 分鐘 |

## 這個架構的取捨

好處：

- worker 無狀態，重啟、換機器都安全。
- 全部狀態可在 GitLab 網頁上直接檢視，出事時人可以一眼看懂。
- 角色分離讓「自己審自己」在結構上不可能發生。

代價：

- 輪詢有延遲，最壞要等一分多鐘才接到單。
- 留言格式要嚴格，寫錯一個字元機器就不認，所以才需要發單前的檢查腳本。
- 社群版 GitLab 沒有互斥的 scoped label，「狀態 label 恰好一個」要靠程式自己維持（第二篇說明）。

適用邊界：這套做法假設專案成員都可信，因為 issue 內文與測試指令最終會在 worker 的機器上執行。它適合私有、小團隊的專案，不適合接受外部人員開單的公開專案。

## 小結

- 把「誰記得什麼」全部改成「GitLab 上寫了什麼」，是這套流程能無人值守的根本。
- 輪詢加 label 加留言，粗糙但好推理。
- 角色分離與自包含的 issue，是為了應付「沒有共同脈絡」這個前提。

下一篇會講 label 狀態機：有哪些狀態、怎麼轉移、失敗與受阻怎麼區分，以及卡住的單要怎麼放回去。
