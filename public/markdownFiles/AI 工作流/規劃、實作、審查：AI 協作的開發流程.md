# 規劃、實作、審查：AI 協作的開發流程

> 和 AI 程式開發代理合作時，如果沒有固定流程，任務會在「需求模糊就開工」「做到一半才發現依賴」「做完才發現架構錯」之間來回跳。本文整理我用的 12 步流程、三條實作路徑（A/B/C）、範圍合約（Scope Contract）與停等點的設計。寫於 2026 年，以 Claude Code 為具體例子，流程概念不綁定特定工具。

## 問題：沒有流程時任務怎麼壞掉

三種常見的壞法：

- **需求模糊就開工**：規劃偏了，實作全部要重來。
- **做到一半才發現依賴沒定義**：返工。
- **完成後審查才發現架構決策有問題**：大改。

12 步流程的設計目標：**每一步都有明確的輸入、產出與暫停條件**，讓主代理知道「現在在哪、下一步做什麼、什麼情況必須停下來問人」。

為什麼是 12 步，不是 5 步或 20 步？

- 5 步太粗：光是實作的三個波段（Wave）就占了 3 步，壓縮之後，停等點沒辦法定位。
- 20 步太細：每個小決定都寫成一步，停等點反而失去意義。
- 12 步的粒度，讓每一步至少對應到一個有意義的產出。

## 12 步總覽

| 步驟 | 內容 | 誰做 | 是否停等 |
|---|---|---|---|
| 1 | 理解需求，建立任務產物目錄 | 主代理 | 否 |
| 2a | 對話式需求探索 | 主代理（子代理無法多輪對話） | Hard Gate（見下） |
| 2b | 委派規劃，產出規劃報告 | 規劃子代理 | **停等**：使用者確認規劃 |
| 3 | 架構設計（若需要） | 架構子代理 | 否（改記決策日誌） |
| 4 | 隔離工作區（大型功能建議）、建立範圍合約 | 主代理 | 否 |
| 5 | 測試策略分支（TDD／事後補測／不寫） | 主代理 | 否 |
| 6 | 委派實作（依路徑 A/B/C） | 執行型子代理 | 規劃外問題改記決策日誌 |
| 7 | 修復建置失敗 | 建置修復子代理 | **停等**：無法自動修復時 |
| 8 | 選擇審查等級 | 主代理 | 否 |
| 9 | 產資料流地圖、平行審查 | 審查型子代理 | 否 |
| 10 | 合併審查報告、驗證嚴重發現 | 主審子代理、主代理 | **停等**：使用者決定修什麼 |
| 11 | 端對端（E2E）驗證 | E2E 子代理 | 否 |
| 12 | 分支完成，確認任務是否結束 | 主代理 | **停等**：問使用者是否結束 |

下面挑幾個設計重點說明。

## 設計重點

### 重點 1：探索先於委派

步驟 2a 的對話式需求探索，強制放在委派規劃之前。原因在上一篇提過：子代理不能多輪對話。委派出去後需求還模糊，子代理只能猜，或者停下來問，而停下來問又要重新切換脈絡。

主代理先跟使用者確認這些維度：

1. 需求背景（為什麼要做）
2. 功能目標（完成後系統行為如何改變）
3. 方案選擇（有沒有多種做法，選了哪個）
4. 業務規則
5. 權限控制
6. 驗收標準（用 Given/When/Then 寫成場景）
7. 測試策略（**必問**）
8. 排除範圍（明確不做什麼）

### 重點 2：測試策略必問

第 7 項不是可選。TDD（先寫測試）路線與事後補測路線，會影響步驟 5 走哪條分支，也影響實作波段的節奏。等實作到一半才決定要寫測試，補進去的成本遠高於規劃前就確認。

### 重點 3：Hard Gate 防止帶著模糊需求進規劃

2a 到 2b 之間有一道閘門：

- **必須清晰**：需求背景、功能目標、方案選擇。
- **必須達標**：驗收標準的場景數（完整任務至少 3 個 Given/When/Then 場景）。
- **可以標「待確認」放行**：業務規則、權限控制、測試策略、排除範圍。

這道閘門看起來多了一個確認步驟，但它防止的是：規劃代理拿到模糊需求，用大量「假設」去填洞，結果規劃報告的「未驗證假設清單」爆炸，實作時每隔幾步就要回頭確認假設。

### 重點 4：停等點是「人類決策」的錨點，但不必一直停

我早期設了 6 個必須停等的點：規劃確認、架構取捨、規劃外問題、無法修復、審查結果、任務是否結束。跑了一段時間後我發現：

- 中間兩項（架構取捨、規劃外問題）雖然「AI 不該自行定案」，但**不必當場問**。只要留下可覆核的紀錄（決策日誌），事後在審查階段覆核，一樣能抓到錯誤的選擇，還省下大量「一直問人」的往返。
- 另外四項錯誤成本或不可逆程度更高，維持即時停等。

所以現在的制度是：

- **預設停等的五種情境**：刪除非臨時檔案、接入新的外部服務或 API、發現兩條合理的架構路徑、同一個錯誤嘗試兩種不同方案仍失敗、需要超出範圍合約的變更。
- **豁免段**：「實作 → 第一次提交 → 審查出結果」這一段內，上面五種情境改成「主代理裁決並記入決策日誌」，不停等。
- **豁免段不包含不可逆動作**：刪檔、正式環境變更、強制 push、對外送訊息，這類事沒有「事後覆核」的選項。遇到時不執行原動作，改走可逆的替代路徑，並在日誌寫下「原本要做什麼、改成什麼」；找不到可逆替代方案就停下來問人。
- **無條件硬停**（不分段、任何時候命中都停）：碰到特別敏感的環境之前、進審查前 context 已超過一半（先存檔再清空）、真正的阻礙（失敗預算用完、依賴被擋住）。

決策日誌長這樣（格式為示意）：

```markdown
| 時間 | 決策 | 選項 | 選擇與理由 | 嚴重度 |
|---|---|---|---|---|
| 14:20 | 快取層放哪 | A: Service 內 / B: 獨立 Cache 類別 | 選 B，與既有慣例一致 | high |
| 14:55 | 刪除舊 migration？ | 刪 / 保留並加新檔 | 不可逆，改保留並加新檔（原本想刪） | medium |
```

審查階段會把「嚴重度 high」的決策再看一遍，使用者在審查結果的停等點一併覆核。

## 三條實作路徑：A、B、C

不是所有任務都走同一種節奏。

- 小任務：「把第 42 行的 X 改成 Y」，不需要派子代理，派了協調成本就超過任務本身。
- 大任務：10 個有依賴關係的子任務全丟給同一個子代理，中間某個介面一改，已完成的部分就要返工。

選擇依據是「**子任務之間有沒有嚴格的前後依賴**」與「**需不需要探索才能定位**」。

### 決策表

| 情境 | 路徑 | 審查時機 |
|---|---|---|
| 已知精確位置、3 次工具呼叫內完成、不是審查後修復、不是規劃文件 | 主代理直接做 | 不需正式審查 |
| 需要探索定位、2–3 個子任務同模組、審查後修復 | **路徑 C**：派一個實作子代理 | 視需要 |
| 一組互相獨立的任務 | **路徑 A**：每個子任務各派一個 | 每個完成後立即審 |
| 有分層依賴的功能（資料表 → Model → Service → Controller） | **路徑 B**：Wave 流程 | 全部完成後批次審 |
| 大規模重構（10 個檔案以上） | 路徑 B，加分組平行 | 批次審 |

### 路徑 A：各任務獨立，即時審查

- 把任務拆成 N 個獨立子任務，每個有各自的「完成標準」。
- 每個子任務派一個實作子代理，可同批派出。
- 每個完成後立即做輕量審查，有問題馬上修，不讓錯誤累積到最後。
- 平行子任務建議不超過 4 個，否則報告很難追蹤。
- **如果中途發現 A 的產出被 B 使用，立即改走路徑 B。**

### 路徑 B：Wave 流程，完成後批次審查

以 Laravel 類型的後端功能為例：

| Wave | 內容 | 說明 |
|---|---|---|
| Wave 1 | Migration／Model／設定／路由 | 基礎層，必須先完成 |
| Wave 2（平行） | Service 與 Repository；Controller 與 Request／Resource | 兩者各自依賴 Wave 1 的 Model，彼此不互相依賴，可平行 |
| Wave 3（可選） | 單元測試與功能測試 | 要等 Wave 2 全完成，因為 Service 與 Controller 要先存在 |

為什麼 Wave 1 與 Wave 2 不能平行？Controller 依賴 Service 的介面，介面還沒定義，Controller 寫不出來，只會讓後面的子代理開始猜。

為什麼批次審查而不是每個 Wave 審一次？因為路徑 B 的核心問題是**跨層互動**（Controller 怎麼呼叫 Service、Service 怎麼呼叫 Repository），要所有層都做完才看得到整體。在中間插入審查，只會看到不完整的樣子。

**同一個任務只能選一種審查時機，兩者互斥。**

### 路徑 C：需要探索，或審查後修復

三種情境走路徑 C：

1. 需要探索才能確定實作位置，主代理無法在委派前預知影響範圍。
2. 規模 2–3 個子任務，在同一模組內。
3. 審查後的修復，**不論多小都走路徑 C**。

第 3 點為什麼？審查過程中，主代理已經累積了大量脈絡，如果再自己動手修，主 context 會越來越厚、越難追蹤。委派一個子代理，等於讓修復的 context 獨立出去。同樣道理，規劃報告再小也交給規劃子代理寫。

## 範圍合約（Scope Contract）

長任務的範圍蔓延，來源通常不是使用者加需求，而是**子代理「順便」做了規劃外的事**。典型場景：叫子代理修一個 Service 方法，它看到旁邊 Repository 寫得不好，順手重構。重構本身也許沒問題，但引入了沒審過的變更，破壞 diff 可讀性，還可能讓既有測試壞掉。

做法：規劃確認後、實作前，把範圍寫成一份 YAML 合約。

```yaml
task_id: add-order-query
objective: 新增訂單查詢端點，支援日期區間
verify_cmd: php artisan test --filter=OrderQuery   # 單行、45 秒內可跑完
in_scope:
  - app/Http/Controllers/OrderController.php
  - app/Services/OrderQueryService.php
out_of_scope:            # 至少 2 項，逼規劃者主動列邊界
  - 不重構既有 OrderService
  - 不調整資料表結構
max_files: 5
features:                # 任務有 3 個以上功能時才填
  - id: F1
    status: in_progress
    definition_of_done: 場景 SC-01 通過
last_checkpoint:
  wave: 2
  completed: [logic, api]
  in_progress: Wave 3 測試
  blockers: []
```

設計理由：

- **用 YAML 不用 Markdown**：Markdown 適合人讀，但 hook 或腳本不好解析。YAML 結構化之後，未來可以自動比對「子代理改的檔案是否在 in_scope 內」。
- **out_of_scope 至少 2 項**：人規劃時習慣想「要做什麼」，容易忽略「不做什麼」。強制列出，才會變成子代理判斷是否越界的依據。拿不準一個修改在不在範圍內，就看 `in_scope`，再看 `out_of_scope`，兩邊都沒提就上報，不要自己判斷。
- **features 3 個以上才填**：這個陣列要持續更新狀態，有維護成本。只有 1–2 個功能的任務不值得。
- **last_checkpoint 讓跨 session 接續**：session 不是永久的，新 session 不會自動記得上次做到哪。每個 Wave 完成後更新這個物件，新 session 讀它就知道從哪接。

接續流程：讀合約 → 看 `last_checkpoint` → 看各功能 `status` → 從未完成的繼續，不重做。

### 一個重要的反省：範圍清單是「假設」，不是「地形」

我有一次踩到的坑，值得獨立寫出來。

任務是「把某個寫死的常數搬到共用檔」。我先派了一輪唯讀調查，問「這個值在哪些地方被讀取」，據此列了 4 個檔案當作委派的 `ALLOWED_FILES`。實作跑到編譯階段才炸出第 5 個檔：它根本不讀那個值，只是 import 了相關的型別。子代理正確地拒絕改範圍外的檔案並回報。

接下來我犯了錯：**裁決時把那份 4 檔清單當成既定條件**，只在「不動第 5 個檔」的前提下找解法，結果做出一個折衷設計（兩份列舉加一張轉換表）。審查四個通道全部通過。使用者一看就問：「這兩個列舉不就是同一個東西？為什麼兩邊都定義？」正解是改第 5 個檔的一行型別註記。

教訓有兩個：

1. **調查的問題要和改動的維度一致。** 我問的是「誰讀這個值」，但改動動到的是「型別的成員集合」。改到型別或列舉時，影響範圍是「誰 import 這個型別」，兩個要分別查。
2. **子代理回報「必須越界才能完成」時，第一個要質疑的是範圍清單，不是設計。** 先問「這條邊界是技術限制，還是我自己畫的？」再決定要改設計還是擴範圍。擴範圍的做法是改寫 `ALLOWED_FILES` 重派，不是授權子代理自行越界。

另外，審查通道拿到同一份範圍合約，也會繼承委派者的盲點。我的修法是授權結構審查通道「可以質疑邊界劃分本身」，而不是拿掉合約（合約對審查者仍有防止範圍蔓延的正面作用）。

## 審查等級與流程位置

步驟 8–10 的審查依「修改規模、耦合度、風險」分三級（輕量、標準、深度），細節見〈AI 程式碼審查流程：資料流地圖、證據與盲點〉。

流程上的重點：

- 審查結果出來，就是「豁免段」結束，必須停等讓使用者決定修什麼。
- 主代理對每個最嚴重的發現（P0），要自己讀資料流地圖加至少一次 grep 交叉確認，不可委派給別人。
- 審查通過後，詢問使用者任務是否結束，確認後再跑事後流程稽核。

## 踩過的坑與教訓

1. **流程越細，越要注意「停等次數」。** 早期固定 6 個停等點，使用者被一直問。後來用「可覆核的決策日誌」取代其中兩個，品質沒掉、往返減少。
2. **不可逆動作不能搭便車進豁免段。** 豁免的前提是「事後能覆核」，刪檔、對外送訊息沒有這個性質。
3. **步驟粒度要能對應到停等點與產出。** 太粗定位不到，太細失去意義。
4. **範圍清單有時效性。** 它是委派當下依不完整資訊寫的猜測，不要讓 20 分鐘前的猜測剪掉正確設計。

## 可直接套用的檢查清單

- [ ] 進規劃前：需求背景、功能目標、方案選擇是否都清楚？驗收場景至少 3 個？
- [ ] 測試策略問過了嗎？（TDD／事後補測／不寫）
- [ ] 實作路徑：子任務有前後依賴嗎？有 → B；獨立 → A；要探索或審查後修復 → C。
- [ ] 範圍合約的 `out_of_scope` 至少 2 項嗎？
- [ ] 改動會動到型別、列舉、介面的成員嗎？有 → 另查「誰 import 它」。
- [ ] 子代理回報「必須越界」時，先質疑範圍清單。
- [ ] 豁免段內遇到不可逆動作：改走可逆替代路徑並記日誌。
- [ ] 審查結果出來後，停等使用者決定。
