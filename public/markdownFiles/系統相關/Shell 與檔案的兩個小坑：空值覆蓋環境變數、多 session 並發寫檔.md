# Shell 與檔案的兩個小坑：空值覆蓋環境變數、多 session 並發寫檔

> 兩個我踩過、看起來都很小、但一個會讓腳本莫名其妙失敗，另一個差點弄丟資料的坑：用 `source` 載入設定檔時，空值會蓋掉既有的環境變數；多個 AI 對話（session）同時寫同一個檔案，整檔覆寫會吃掉對方的內容。寫於 2026 年。

## 坑一：設定檔裡「有鍵沒值」會蓋掉環境變數

### 症狀

一個呼叫外部 API 的腳本，設計成「先讀 `.secrets.local` 裡的權杖，檔案沒提供時才用環境變數」。文件也是這樣寫的。

實際行為卻是：我明明 `export API_TOKEN_B="..."`，腳本仍然印出「找不到站台 B 的權杖」就結束。

原因在腳本無條件做了這件事：

```bash
. "$secrets_file"    # 把整個檔案 source 進來
```

而那個 `.secrets.local` 是從範本複製來的。範本為了完整，把所有站台的鍵都列出來，使用者通常只填自己要用的那一個，其他留成：

```bash
API_TOKEN_A=sk-xxxx
API_TOKEN_B=          # 鍵存在、值是空的
API_TOKEN_C=
```

`source` 之後，`API_TOKEN_B` 被設成空字串，**覆蓋**了呼叫端剛 export 的同名變數。接著腳本判斷「是空的」，就當作沒提供。

文件寫的是「檔案未提供該站台時，改用環境變數」，實際上「鍵在但值空」也算被檔案「提供」了，兩者不一致。

### 重現

```bash
# .secrets.local 內含 API_TOKEN_B=（空值）
export API_TOKEN_B="<有效權杖>"
bash scripts/call-api.sh --site b --endpoint report
# 印出權杖設定引導後 exit 1
```

### 臨時繞過

讓檔案判斷失敗、跳過 `source`：

```bash
export SECRETS_FILE=/nonexistent/path
```

這能用，但每次都要記得，所以還是要修腳本。

### 修法

在 `source` **之前**先把環境變數現值存起來，`source` 之後如果變數是空的，就還原：

```bash
resolve_token() {
  local site="$1" var="API_TOKEN_${site^^}"
  local env_tok="${!var:-}"          # source 之前先存起來

  if [ -f "$secrets_file" ]; then
    . "$secrets_file"
  fi

  # 檔案給的是空值：視為「沒提供」，還原環境變數
  if [ -z "${!var:-}" ]; then
    export "$var=$env_tok"
  fi
}
```

寫法上有一個小細節：**用 `if`，不要用 `[ -z ... ] && export ...`**。腳本若開了 `set -e`，`&&` 左邊的測試回傳非零時，在命令替換的子 shell 內可能被提前中止；`if` 不會有這個問題。

連帶要改的還有：

- 文件與引導訊息裡的優先序描述，從「檔案未提供時生效」改成「**沒有該鍵、或鍵在但值為空時生效**」。
- 範本檔的註解，說明留空等於沒提供。
- 規格文件裡對「腳本如何解析權杖」的那一條，同步補上。

### 驗證方式（不對真實服務發任何請求）

1. **函式層**：把 `resolve_token` 單獨抽出來跑，修前與修後各五個情境對照：檔案有值、檔案空值加環境變數有值、兩者皆空、只有檔案、只有環境變數。修前「空鍵加環境變數有值」失敗，修後取到環境變數；檔案有值時仍優先於環境變數；兩者都空照舊印引導並 `exit 1`。
2. **整支腳本層**：用 `PATH` 前置的假 `curl` 替身跑一次，檢查它收到的 header 是不是環境變數的權杖。修前根本走不到 `curl`；修後走完整個流程。
3. **語法檢查**：`bash -n script.sh`。

### 這個坑的通用教訓

- **`source` 設定檔會無條件覆寫同名變數**，包含設成空字串的。想要「環境變數優先」或「空值視為未提供」，要自己寫。
- **範本檔把所有鍵都列出來，使用者複製後多半只填一部分**，所以「鍵存在但沒值」是常態，不是例外。
- **「文件寫的優先序」要用腳本實測**，別只讀程式碼就相信。

## 坑二：多個 session 同時寫同一個檔案

### 症狀

有一個 JSON 檔（訊息紀錄），兩個 AI 對話 session 都會寫它。事故經過：

1. session A 用編輯工具改這個檔，**舊字串比對失敗**（因為 session B 剛好在一段時間前已經改過它）。
2. session A 為了確認現況重新讀檔，工具回「檔案自上次讀取後沒有變化」。這是**假訊息**：工具的檔案狀態快取沒偵測到另一個 session 的修改（偽陰性）。
3. session A 因此判斷「檔案還是我寫的那版」，於是**整個檔案覆寫**。
4. session B 剛寫進去的 3 筆紀錄全部消失。

所幸後來 session B 重寫救回，沒有造成永久損失，但這已經是「資料損毀等級」的事故。

重現路徑可以整理成：A 寫檔，B（另一個 session）改同一個檔，A 的編輯失敗，A 重新讀檔得到「沒變」，A 整檔覆寫，B 的資料就被蓋掉。

### 根因：先別怪快取，先看維護紀律

事後有人點出一個很準的定調：根因是**維護者在改共用檔案時，沒有先備份原檔，改完也沒有檢查並修復內容**。工具快取的偽陰性只是誘因，不是主因。就算快取沒有出錯，「改共用檔案卻不備份、不校驗」本身就是風險。

### 處置：把紀律寫成固定流程

- **編輯工具突然比對失敗，是「有人並發修改過」的訊號**，不是改用整檔覆寫的許可。
- **覆寫共用檔案前，用 shell 取得真值**：`cat` 或 `jq` 看一次現況，不信工具的快取訊息。
- **共用檔案維護 SOP**：

  ```bash
  cp shared.json shared.json.bak.$(date +%Y%m%d%H%M%S)   # 1. 改之前先備份
  # 2. 進行修改（盡量用精準編輯，不用整檔覆寫）
  jq '.messages | length' shared.json                    # 3. 改完逐筆校驗：筆數、關鍵欄位
  # 4. 發現缺漏，立刻從備份把缺的補回來
  ```

- **架構上更根本的做法**：多個寫入者共寫的檔案，改成**只追加**（append-only，例如 JSON Lines，一行一筆），或加上檔案鎖，或指定**單一寫入者**，其他人只能讀。

### 我考慮過但沒有裝的第二道防線

我當時寫好了一個 PreToolUse hook：如果寫入目標是這個共用檔案、而目前工作目錄不是它的擁有者目錄，就直接擋下（exit code 2）並提示改道；其他情況放行，壞輸入也放行（fail-open）。用模擬輸入測了 4 個情境全通過。

它管不到的邊界：用 shell 重導向（`echo > file`）的寫入不在這個 hook 的範圍內，而且只保護一個檔案。

最後裁決是**先不裝**，理由是「未來如果又出現相同問題再說」。維護 SOP 已經寫進記憶，不裝 hook 也有基本保護；腳本與測試保留著，同型事故再現時可以直接取用，不必重做。工具快取的偽陰性則列為上游行為，持續觀察，再現時整理最小重現回報（目前未再現）。

### 這個坑的通用教訓

- **「寫入失敗」本身是資訊**。編輯比對失敗，先想「是不是有人改過」，再決定怎麼做，不要用更大的動作（整檔覆寫）去「解決」它。
- **覆寫前的真值要自己取**，工具的「沒變化」訊息只是快取，不是事實。
- **會被多方寫入的檔案，先決定寫入模型**：單一寫入者、只追加、還是加鎖。沒決定就不要共寫。
- **改共用資料的三步**：備份、修改、校驗，缺一不可；校驗的目標是「筆數與關鍵內容」，不是「看起來沒錯」。
- **軟性紀律（寫在記憶或文件裡）有風險**，如果同型事故再發生，再考慮 hook 這類硬性防線；不要在還沒再發生前就過度設計。

## 兩個坑的共通點

兩個坑都是「工具或環境默默做了跟你預期不同的事，而且沒有報錯」：`source` 悄悄把空值蓋上去，快取悄悄說「沒變」。對付這種問題，共通的做法是**自己取一次真值再下判斷**：印出變數實際的值、`cat` 出檔案實際的內容。
