# 早期 AI 工具評估：superpowers、gbrain、markitdown 等

> 2026 年 4 月，我替九個外部 AI 工具與設定專案各寫了一份評估報告。這篇回頭整理：評估格式怎麼設計、每個專案我借了什麼、為什麼大多不整包採用，以及事後看哪些判斷站得住腳。

## 問題與背景

看到別人的 Claude Code 設定、plugin 或 skill 集合很容易手癢想直接裝。但整包安裝常常帶來三種代價：

- 規則與自己既有的規則**互相競爭**，風格漂移、誰說了算變成問題。
- 多一個常駐程序或 hook，**每次工具呼叫都多一點延遲與失敗點**。
- 工具的場景和自己的工作方式只有少量交集，**大部分功能用不到卻要付維護成本**。

所以我給自己訂了一個固定的評估格式，每個專案都用同一套尺度看。這篇是那一批早期研究的回顧，涵蓋：

| 專案 | 種類 | 我的結論 |
|---|---|---|
| superpowers | Claude Code plugin（工程紀律框架） | 已在用，抽出幾個沒繼承到的設計 |
| gbrain | 個人知識庫（MCP 加 skill） | 工具不採用，借鏡記憶結構 |
| claude-mem | 跨 session 自動記憶 plugin | 不採用，借鏡七個設計 |
| markitdown | 檔案轉 Markdown 工具 | 按需 CLI，不掛 MCP |
| learn-harness-engineering | 教學課程加一個 skill | 借鏡幾個模板與評估框架 |
| prompt-master | 單一 prompt 生成 skill | 借鏡模型專屬調校表等 |
| PUA | 用人格壓力驅使 AI 的 plugin | 只借 hook 機制，不要修辭 |
| caveman | 輸出壓縮 skill | 不整包採用，借鏡例外機制 |
| bu-ketao（不客套） | 繁體中文輸出壓縮規則集 | 擷取缺漏詞庫，不整包安裝 |

## 評估格式：三分法加三題自檢

### 決策分級

| 級別 | 意思 |
|---|---|
| D1 立即採用 | 填補明確空缺、而且高頻使用 |
| D2 按需觸發 | 有價值但頻率不明，寫好觸發條件，到了才裝 |
| D3 觀念借鏡 | 不裝工具，只把設計觀念內化到既有設定 |
| D4 不採用 | 明確列出理由，一行帶過 |

結果很有意思：九個專案裡，**沒有一個拿到「整包立即安裝」**；幾乎都落在 D3 與 D4。

### 每份報告結尾的三題自檢

1. **這個工具解決的痛點，我現在真的有嗎？** 要能指到既有的具體資產或事件，不能只說「看起來有用」。
2. **採用建議夠具體嗎？** 要寫到「改哪個檔、加什麼內容」，不是「值得試試」。
3. **我有沒有被表面功能吸引而忽略場景錯位？** 要估算場景交集。我習慣把交集低於 30% 視為紅燈，這個門檻是我自己訂的經驗值，不是什麼標準。

這三題救了我幾次。例如 claude-mem 的功能非常豐富，但第 3 題一算，交集只有「跨 session 找我過去怎麼處理過類似任務」約 20%。

## 逐個回顧

### superpowers：把「行為矯正」拆成可抽取的模式

我當時評估的是 v5.0.7，一個從 plugin 市集安裝的工程紀律框架（14 個 skill、1 個 agent、1 個 hook）。它不提供新功能，而是**矯正 AI 在壓力下的逃脫行為**：跳過測試、猜測式修復、沒驗證就說完成。因為我已經安裝它、也有自己擴充的規劃、實作、審查流程，所以重點是找出「我擴充時簡化掉的精巧機制」：

- **理由駁斥表**：預先列出 AI 會產生的藉口（「太簡單不需要測試」「手工測過了」），旁邊寫實際後果。這是對**思維模式**而非行為的攔截，比單純寫「不准跳過測試」有效。我只採精選的 5 到 7 項，避免 17 項全搬造成 token 浪費。
- **規格審查與程式品質審查分開**：一個子代理逐條比對需求，另一個看設計品質，兩者都過才算完成，避免注意力被分散。
- **實作者四狀態報告**：`DONE`、`DONE_WITH_CONCERNS`、`NEEDS_CONTEXT`、`BLOCKED`，消除「完成了但有疑慮」的模糊地帶。
- **證據優先於聲稱**：沒有新鮮的驗證輸出，就不能說完成；「應該」「大概」是紅旗詞。
- **參考文件伴隨**：主檔只留決策流程，技術細節放同目錄的參考檔，按需載入。

附帶一個我覺得很準的觀察：它的哲學是**不信任 AI 的自律**（用紅旗清單矯正行為），而「人工確認點」的哲學是**不信任 AI 的決策**（在關鍵決策處暫停）。兩者互補，最佳做法是在人工確認點加上「附驗證輸出才能回報」。

### gbrain：記憶要分「當前結論」與「演化軌跡」

[gbrain](https://github.com/garrytan/gbrain) 是給 AI 代理用的長期知識層，CLI 幾乎沒有業務邏輯，知識都寫在 `skills/*/SKILL.md`。**工具本體整個不採用**（它面向個人助理場景，與工程任務交集低於 10%，而且 30 個 MCP 工具會污染 tool schema 的 context），但學到一個結構：

**Compiled truth 加 Timeline 雙層記憶**。每個知識頁上半是「當前最佳理解」（可以重寫），下半是只增不改的證據時間線。我打算套到自己的記憶檔：

```markdown
## 當前規則（Compiled Truth）
一句話規則
**Why:** 當前為何這樣做
**How to apply:** 如何套用

---

## 演化紀錄（Timeline, append-only）
- 2026-04-04：初次提出，原因為「審查只看 diff」
- 2026-04-13：發現過度工程傾向，縮限為「先試最小改動」
```

它解決兩個痛點：過期判斷困難（單層結構分不清「現在的規則」與「促成規則的歷史事件」），以及規則演化失真（只留最終版，不知道為什麼長成這樣）。

這份報告裡有個我自己很認同的修正：原本寫「Timeline 超過 N 條就要重構」只是文字規則，後來改成 **SessionStart hook 強制提醒**。因為主代理寫記憶時不會主動去數條數，這種規則放在文件裡只是裝飾，要有觸發者才會被執行。

### claude-mem：不採用，但七個設計值得借

[claude-mem](https://github.com/thedotmack/claude-mem) 是跨 session 自動記憶系統：hook 被動捕獲每次工具呼叫，由本機 worker 壓縮後存進 SQLite 加向量庫，再用 MCP 工具搜尋。我評估時版本是 v12.1.6，維護極活躍。

**不採用的三重理由**：

1. 記憶哲學衝突：我走「主動精選」，它走「被動全量採集」，兩套並存會讓 context 注入重複、意圖不一致。
2. hook 疊加：每次工具呼叫都多打一次本機 HTTP 並觸發壓縮，延遲與成本都增加。
3. SessionStart 注入的內容與我精心安排的載入順序衝突。

**值得借的設計**：

- **三層節流搜尋**：先查索引（每筆約 50 到 100 token），再查前後文，最後才批次抓全文（每筆約 500 到 1000 token）。對任何「要在大量歷史資料裡找東西」的流程都通用，作者宣稱可省約 10 倍 token。
- **優雅降級的 exit code 哲學**：傳輸層錯誤（連不上、逾時、5xx）一律 `exit 0`，不阻擋主流程；用戶端 bug（4xx、型別錯誤）才 `exit 2`，讓 AI 看到錯誤並自修。**hook 不該因為外部服務掛了而卡住你的工作**。
- **領取確認佇列加自我修復**：處理中超過 60 秒就自動重置回待處理，避免某個子代理卡死後沒人接。
- **斷路器加指數退避**：連續重試三次後斷路，不無限重來。
- **子代理回報合約**：回報必須包含「讀了哪些來源、具體發現、可複製的片段位置、信心與已知缺口」，沒有來源就退回重派。
- **雙 session ID**：區分「整個 session 不變的 ID」與「worker 每次重啟就變的 ID」，也啟發我把「持久的任務識別」與「可重設的當前狀態」分開存。
- **每個階段後平行派驗證、反模式 grep、品質三個子代理，全過才提交**。

另有一個警示：它的更新日誌寫著「先前某個 Claude 實例在壓縮重構時，把商業 token 品牌字樣塞進注入標頭，已還原」。**讓 AI 自動修改專案時，品質監督不能省**。

### markitdown：按需 CLI，不掛 MCP

[markitdown](https://github.com/microsoft/markitdown) 把 PDF、DOCX、PPTX、XLSX、HTML、CSV、圖片、音訊、YouTube 網址等轉成 LLM 友善的 Markdown，有 CLI、函式庫、MCP server 三種介面。

- **結論**：不立即安裝，但記住它存在。觸發條件是「需要從 PDF/DOCX/PPTX 抽內容給 AI 讀」之類的情境出現至少兩次，再 `pip install 'markitdown[all]'`，直接用 CLI。
- **不掛 MCP 常駐**：工具 schema 會持續佔用 context，但實際使用頻率未必高，投資報酬不對稱。
- **借鏡觀念**：它的 OCR 外掛是把你既有的 LLM client 傳進去，用視覺模型做 OCR，**不新增任何傳統機器學習依賴**。以後遇到「從圖片或掃描檔抽文字」，先考慮視覺模型，不先裝 tesseract 之類。
- 場景交集只有約 30%（11 種格式中只有 3 到 4 種我會用到），沒有因為「支援格式多」就誇大價值。

### learn-harness-engineering：給既有做法一個行業術語

[learn-harness-engineering](https://github.com/walkinglabs/learn-harness-engineering) 是一門教學課程（12 堂課、6 個實作專案），附一個可安裝的 `harness-creator` skill，核心理念是「**模型不變，harness 決定可靠性**」。它不是個人設定樣本，所以重點在它歸納的 pattern：

- **`feature_list.json`**：機器可讀的功能清單，agent 一次只能挑一個 `not-started` 的項目做，完成後必須填證據。這是**功能級**的範圍邊界，和我任務級的 scope contract 互補。
- **Gotchas 一級文件**：每項固定「症狀、原因、修復」三段，記錄「看起來正確但會壞掉」的事，是事前預防，與事後檢討式的反模式紀錄互補。
- **五子系統評估**：指令、狀態、驗證、範圍、生命週期各評 1 到 5 分，找最低分改善。可當作新專案 onboarding 的第一步。
- **進度日誌模板**：做了什麼、進行中、下一步、阻礙、證據。與「對話脈絡壓縮」互補：一個記對話，一個記進度。

它的「從零到有」取向也提醒我：不是每個專案都需要一整套多代理設定，先用最小可行結構（例如 AGENTS.md 限 50 到 100 行）。

### prompt-master：把抽象原則變成可查表的規則

[prompt-master](https://github.com/nidhinjs/prompt-master)（v1.5.0）是單用途的 prompt 生成 skill。它與我既有的 prompt 設計 skill 在概念層大多重疊，真正的差異在「**知識的具象化程度**」：

- **模型專屬調校表**：不同模型需要不同策略。例如推理型模型加思維鏈反而降低品質；Claude 偏好加「只改被明確要求的部分」防過度工程；Gemini 容易幻覺引用，要加引用錨點。我只打算抽出自己實際用到的幾個模型，不抄三十幾個跨生態工具。
- **失敗模式診斷清單**：6 大類（任務、context、格式、範圍、推理、agentic）共 35 項，每項附一行 before/after。有分類，所以掃描時能系統性找問題，不是隨機命中。
- **幻覺型技術硬禁單**：思維樹、思維圖、自洽性投票、專家混合、prompt chaining，在**單次 forward pass 中是假的**（只是模型線性生成文字並假裝分支），列為明確禁止。
- **意圖萃取九維度**：把粗糙需求拆成任務、目標工具、輸出格式、限制、輸入、context、受眾、成功標準、範例，並標出哪些必問。這是「萃取端」，補足了「寫入端」只有模組化規範的缺口。

其中位置配重（開頭 30%、中間 55%、結尾 15% 放驗證清單）我標為**需要先驗證**：挑一個重要 skill 重寫並比較效果，有改善再擴散，不憑文獻直接套。

### PUA：只借 hook 機制，不借修辭

[PUA](https://github.com/tanweai/pua) 的核心主張是用「大廠績效考核文化」的人格壓力，推動 AI 窮盡方案才放棄。我評估的重點不是這個修辭，而是它背後的**hook 驅動行為強制**：

- **PostToolUse 失敗偵測**：用計數檔追蹤「連續」失敗次數（成功歸零、新 session 歸零），到門檻才注入分級指令，避免把正常試錯誤判成高壓。我只借「連續失敗到門檻就自動提醒換方案」這個機制。
- **PreCompact 保護狀態**：用 prompt 型 hook 要求模型在壓縮前把關鍵狀態（任務摘要、已試方案、待辦）寫到檔案，SessionStart 時再讀回注入，比手動存檔更可靠。
- **`additionalContext` 注入**：SessionStart hook 可以輸出一段上下文，注入為系統級內容，不佔用主設定檔空間。這是主設定檔瘦身的新路徑。
- **失敗模式差異化診斷**：「原地打轉」要質疑需求本身，「沒搜就猜」要強制先搜尋，「空口完成」要強制驗證，而不是一套診斷流程用到底。

它有一段觀察我覺得很關鍵：**語意觸發的 skill 觸發率大約 50 到 80%，而 hook 注入是 100%**。對「必須驗證」這種不能漏的行為規範，50% 觸發率等於一半時間在裸奔。核心行為用 hook 強制，進階方法論用 skill 按需載入。這個數字是我當時報告裡的推論，**沒有實測**。

我**不採用**的部分：13 種大廠文化語氣（與專業溝通風格衝突）、P7 到 P10 垂直職級（我偏向水平專業分工）、排行榜與遊戲化。

### caveman 與 bu-ketao：壓縮輸出，以及它撞上繁體中文的地方

這兩個放在一起看，因為它們走同一條路線：讓 AI 少說廢話。

[caveman](https://github.com/JuliusBrussee/caveman) 讓 AI 用「原始人」風格回答，宣稱省約 65 到 75% 輸出 token，另有壓縮輸入檔案的 `caveman-compress`。[bu-ketao（不客套）](https://github.com/notoriouslab/bu-ketao)是繁體中文專用規則集，主張「英文壓縮規則套中文不實用」：英文靠砍冠詞與縮寫省 token，中文沒有冠詞、每個字本身就很緊湊。它有 14 類文字冗餘分類（9 類刪除、5 類替換）、3 類行為冗餘觀察、三級強度，並標示在 14 組實測中平均壓縮 72%（用 cl100k_base tokenizer，這是它自己的數字）。依它的說明，它的繁中模式已被 caveman 上游合併。

**我的處理**：

- **不整包安裝**：會與我自己剛建立的精簡規則直接競爭，雙規則漂移。
- **只擷取我漏掉的詞庫**（bu-ketao）：模糊引用（「研究表明」無出處）、空洞宣稱（「至關重要」）、換句話說式重複、覆述問題開頭、條件式推銷（「如果你願意我可以……」）、否定對比框架（「問題不是 X，而是 Y」直接說 Y）。
- **借鏡 Auto-Clarity 機制**：遇到安全警告、不可逆操作確認、多步驟序列、使用者表示困惑時，**暫停精簡、切回完整句子**。精簡規則一定要有例外，否則「這會刪除五千萬筆資料」也被壓成電報體。
- **借鏡行為冗餘觀察**：推卸迴避（「不在這次範圍」）、催促收工（「可以 commit 了嗎」）、主動推銷（「我還可以幫你做更有價值的事」）不是 filler，但是常見的 AI 意圖信號，可以追問為什麼。
- **技術風險**：對 CJK 做字元級裁剪（把「計算機」壓成「計機」）可能破壞詞義，甚至命中 tokenizer 的罕見標記。我把「繁中語義保真檢查」列為任何壓縮方案的驗收條件，一出現字元級裁剪就放棄整個方案。

### 後續：這套壓縮規則我後來拔掉了

事後回頭看，這條路線**沒有走到終點**。2026 年 7 月，我把自己設定裡的壓縮規則整套拔除封存。原因是「壓縮」與「白話」兩個目標互撞：尤其是「去掉因果連接詞」這類結構性壓縮，讓讀的人要自己補回前因後果，反而更難讀。最後只保留兩件事：**禁止字元級壓縮**，以及**刪掉真正零語義的客套與填充**。

教訓：輸出壓縮的目標是「讀的人少花力氣」，不是「token 越少越好」。如果你的讀者是人，可讀性要放在省 token 前面。

## 這批早期研究的共同教訓

1. **整包安裝的成本常被低估**：規則競爭、hook 疊加、context 注入衝突，三種代價在 claude-mem、caveman 身上都出現。
2. **「按需」是很好用的中間選項**：markitdown 這種工具，寫好觸發條件（例如「同類情境出現兩次」）再裝，避免為了「以後可能用到」付常駐成本。
3. **評估時要同時問「它解什麼問題」與「這個問題我有嗎」**。工具再厲害，場景交集太低就是 D4。
4. **規則需要觸發者**。寫在文件裡的「請記得做 X」常常變裝飾；能用 hook 或固定流程觸發的，就別只靠自律。
5. **別直接複製別人的修辭風格**。PUA 的人格壓力與我的溝通風格衝突，能借的是機制，不是語氣。
6. **新規則落地後立刻拿它跑下一步**，是低成本驗證「規則可不可操作」的方法。

## 可直接套用的檢查清單

- [ ] 這個工具要常駐嗎？不用就先寫成「按需觸發」，附觸發條件。
- [ ] 它的規則會和我現有規則競爭嗎？會的話只擷取缺漏的部分。
- [ ] 它多掛的 hook，會讓每次工具呼叫多多少延遲、多一個失敗點？
- [ ] 它的 hook 在外部服務失敗時，會卡住我的主流程嗎？（應該 fail-open）
- [ ] 每個「借鏡」都寫得出「改哪個檔、加什麼」嗎？
- [ ] 場景交集估算過了嗎？（我的紅燈是低於 30%）
- [ ] 引用的數字（壓縮率、觸發率）是專案作者宣稱，還是我實測的？前者要標明來源。
