# 讀別人的 AI 代理設定學到什麼

> 看別人公開的 Claude Code 設定（`CLAUDE.md`、agents、skills、hooks），是比讀文件更快的學習方式，但也最容易學歪：README 的宣稱和實際行為常常不同。這篇整理我研究幾個公開專案（everything-claude-code、pilotfish、AI-company，以及一份 CLAUDE.md 最佳實踐的研究）得到的設計想法，以及「怎麼讀、怎麼驗證」的做法。2026 年寫成。

## 先講方法：怎麼讀才不會被騙

我讀別人設定的流程是固定的，因為踩過幾次「相信 README」的坑：

1. **先判定研究對象的類型**：是完整的 `.claude/` 設定、單一 skill 集合、還是工具型專案？不同類型要看的重點不同。自動掃描腳本的判定也會有假陰性（例如設定放在 `templates/` 而不是 `.claude/`），要人工覆核。
2. **窮舉設計亮點，不急著評價**。先列出「這個專案做了什麼、為什麼這樣做」，每一項附上 `檔案:行號`，再分類評估。先評價容易漏看。
3. **對每個宣稱找實測依據**。README 說的數字、功能，用 `ls`、`wc`、`grep` 自己數一次。
4. **區分「文字指示」與「機制強制」**。一份 Markdown 裡寫的規則，是靠模型自願遵守，還是真的有程式攔截？這個區別決定規則的可靠度。
5. **標明覆蓋度**：我實際深讀了多少比例？沒讀的部分列出來，避免被誤認為已全面評估。
6. **找對抗驗證**：我的報告會交給另一個模型（或另一個 session）逐條查核引用與數字。

這些步驟讓我抓到好幾個真實的誤解，下面會舉例。

## 案例一：everything-claude-code（ECC）

專案：[affaan-m/everything-claude-code](https://github.com/affaan-m/everything-claude-code)，一個可安裝、可投射到多個 AI 客戶端的工程化設定框架。我當時研究的版本是 v2.0.0，實測有 271 個 skill（用 `ls` 與 `find` 數的，與它的 AGENTS.md 自述一致，但其他自述檔的數字有漂移）。

我把焦點放在兩件事：「怎麼和 AI 討論」與「怎麼讓 AI 自我進化」。

### 「和 AI 討論」的三種模式

**1. 外部顧問模式**：把另一個模型拉進規劃、實作、審查，用嚴格的邊界讓討論不失控。最值得學的設計是「**一個主權寫檔者加多個顧問**」：

- 外部模型**沒有檔案系統寫入權限**，只回傳 diff 當成「髒原型」，所有改檔由主模型執行。
- 角色分權：誰是後端權威、誰是前端權威，寫成規則。
- 交叉驗證時，明確區分「共識」（強訊號）、「分歧」（要權衡）、「互補」。
- 套用 diff 前先在腦中模擬一遍。
- 規劃階段永遠不改正式程式碼；執行階段需要使用者明確同意。

要留意兩個「開箱即壞」的地方：

- 這整組命令都依賴一個**另外安裝的外部執行環境**，沒有安裝的話整條協議無法運作。「clone 下來就能用」是誤解。
- 除了「只有主模型持有寫檔工具」這一條是真的被強制，其他規則本質上是 Markdown 裡的指示，靠模型自願執行。

可移植的是**協議設計**，不是即裝即用的環境。

**2. 內部對立角色（類 GAN）**：把「生成端」與「評估端」刻意拆成兩個對立角色，一個產出、一個嚴格批評，迭代到品質門檻。核心洞見是：**模型評自己的產出時是「病態樂觀者」**，與其教生成端自我批判，不如工程化一個獨立且嚴格的評估端。這完全在同一個生態內運作，不需要外部環境，最容易直接採用。

**3. 內部多聲議會**：對「做或不做」的決策，召開四個聲音的議會（主模型加懷疑者、務實者、批評者三個子代理），先結構化異議，再選擇。

### 「讓 AI 進化」的學習生命週期

ECC 把「進化」做成一條生命週期：觀察、信心評分、聚類、升格、共享、過期清理。值得學的有：

- **觀察者自己不能被觀察**：它有五層過濾條件，其中一層排除所有子代理，確保只有「人類觸發的互動決策」進入學習語料，避免「觀察者觀察自己」造成無限自我強化。
- **信心評分是文件化的啟發式，不是程式精算**：初始 1 到 2 次出現給 0.3，3 到 5 次給 0.5，依此類推；確認加 0.05，矛盾減 0.1，每週沒觀察再減 0.02（軟淘汰）。這串數字是給一個小模型當觀察者讀的指示，程式只存值。**升格門檻才是程式硬性的**（信心 0.8 以上、至少 2 個專案、待處理 30 天過期）。
- **別把「評分演算法」寫成程式精算**。極簡的啟發式加時間衰減，比機器學習更好解釋。
- **快速訊號 hook 加昂貴的抽取 skill**，兩段解耦。
- **自我稽核**：交付前五軸自評，且「低於滿分必須引具體證據」；反模式禁止「全給 5 分」「拿範圍蔓延扣分」「用自評重翻已定案的決策」。
- **行為驗證優於評審打分**：有一個 skill 自動生成行為規格，用三種強度的提示（支持、中性、競爭）去跑代理、抓工具呼叫軌跡、分類，核心觀念是「**不被明示支持時還遵守，才算數**」。合規率低於門檻時，建議把軟約束 skill 升格為 hook 硬強制。

### 驗證時抓到的偏差

我的報告經過三個獨立的查核（另一個 session、Gemini、Codex 各查一遍），修正了這些：

| 初稿的說法 | 查核後 |
|---|---|
| 「每次工具呼叫 100% 捕捉」 | 實際是「啟用觀察者、且通過五層過濾的互動 session 內才 100%」，不是系統級捕捉率 |
| 學習迴圈是自動閉環 | 全自動觀察者**預設是關閉的**；預設體驗是 hook 觀察加手動指令，全自動是 opt-in 實驗 |
| 「防止重播」的警告是機制 | 它是注入 context 的純文字警告，依賴模型自願遵從，不是攔截器 |
| 支援約 10 個 AI 客戶端 | 只有 3 個有完整的 agents、skills、hooks，其餘多為薄殼 |
| 信心公式是程式運算 | 是給模型讀的文件化啟發式 |
| 引用的檔案行號 | 初稿把「repo 根目錄相對路徑」寫成「skill 內相對路徑」，修訂時又犯一次，經兩輪逐條從根目錄查核才全部補正 |

最後一列是個提醒：**引用規約要寫明，並且機械式驗證**（從根目錄 `sed -n` 能不能解析得到）。

## 案例二：pilotfish，三個純文字檔的委派設定

專案：[Nanako0129/pilotfish](https://github.com/Nanako0129/pilotfish)。實質內容是「三個純文字設定檔加一份寫給 AI 讀的安裝手冊加一份契約測試加兩組可重現的實驗」，作者在 README 明講沒有執行期程式碼。

最值得學的有幾點：

### 依「多久變一次」分層，而不是依功能分層

| 檔案 | 決定什麼 | 變動頻率 |
|---|---|---|
| `settings.json` | 誰主持（主模型別名與備援模型） | 帳號權限變動時 |
| `agents/*.md`（八個角色） | 誰執行什麼、用哪個模型層級 | 模型層級重新指派時 |
| `CLAUDE.md` 的一段政策 | 怎麼委派 | 工作習慣調整時 |

三種變動頻率分開存放，避免互相干擾同一份檔案。

### 角色數量克制

只設 8 個具名角色，並明文對照「100 個角色的目錄」是反例：角色數量本身是認知負擔，只覆蓋實際反覆出現的委派模式。

### 依「信任邊界加成本層級」分工

不是依架構層（資料層、邏輯層、介面層）分，而是依「這個角色能不能寫」「用多貴的模型」分。唯讀角色一律用正向的工具白名單（不含 Bash），可寫角色才用排除法。安全相關的工作：核准前只給唯讀角色蒐證，核准後才路由到可寫角色。

### 把政策當程式碼測試

它用 Python 的 `unittest` 對 `CLAUDE.md` 的自然語言文字與 agent frontmatter 做 `assertIn`、`assertNotIn` 字串斷言，把文字規則當成程式碼做迴歸測試。例如「驗證者只能回 CONFIRMED 或 REFUTED、規劃驗證者只能回 READY 或 REVISE」，並用交叉斷言確認兩個檔案不含對方的詞。

### 改規則之前先用實驗量測

`benchmarks/` 目錄保存「改一條委派規則前，先用受控實驗量測成本、時間差異」的完整證據鏈，**連被否決的政策草稿也全文保留**。CHANGELOG 逐版記錄「為什麼拒絕、用什麼實測或事故驗證」。

### 「刻意不做」要明寫

它有一張「Deliberately left out」表：逐項記錄「刻意不做什麼、為什麼」（不做 per-project 設定、不加強制 hook、不設某個環境變數、不釘死模型 ID）。讓讀者能分辨「沒想到」與「想過但決定不做」。

### 一句話值得抄

> 精確地回報「因為 X 卡住了」是成功的產出；猜測出來的實作不是。

這把「回報受阻」定義為成功，防止子代理在規格不明時用猜測填補空白。

## 案例三：AI-company，主檔只有 36 行

專案：[CronusL-1141/AI-company](https://github.com/CronusL-1141/AI-company)，把 Claude Code 包成「AI 公司模擬器」，有 22 個角色與一整套常駐服務，用資料庫做任務分配。

大部分機制（常駐服務、信任評分、看門狗）與我的使用情境不合，但有幾個小設計值得學：

- **根 `CLAUDE.md` 只有 36 行，幾乎全是指標**，指向架構文件與 skill，不內嵌細則。讓主模型讀一次就能定位。
- **「刻意決策，禁止悄悄回退」清單**：集中列出反常的設計，每條標註「機檢背書」或「事故史」，防止後來的人（或 AI）看到反常設計直覺想「修好」而回退掉有意的取捨。
- **同名檔案要求逐位元組一致，用 CI 檢查**：因為曾經發生「守衛邏輯只存在於從不發布的副本，修復沒有實際生效」的事故，改用機器檢查取代人記得維護。
- **分配邏輯寫成純函式**，檔頭明講「沒有 I/O，決策樹可以直接單元測試」。
- **把任務分配當成持續學習的最佳化問題**：每次結果回饋進資料庫，下次分配用歷史數據加權。我的委派是無狀態的（每次靠主模型當下判斷），這是兩者的根本差異；但我沒有採用，因為成本太高。

## 案例四：CLAUDE.md 最佳實踐研究

我另外做了一份「`CLAUDE.md` 怎麼寫」的研究，整理官方文件與社群討論（2026 年前半年）。權威層級是：官方文件最高，量化扎實的社群文章次之，一般社群指南更低。

### 社群的量化共識（標明是社群共識，不是官方數字）

- **指令預算**：前沿模型可靠遵循約 150 到 200 條指令；Claude Code 系統提示已佔約 50 條，所以 `CLAUDE.md` 可用空間約 100 到 150 條。
- **檔案長度**：40 到 80 行最佳，100 行以內為上限；300 到 350 字是高效檔的中位數，超過 500 字報酬遞減，超過 1000 字呈負相關。
- **每回合稅**：5,000 token 的 `CLAUDE.md`，每回合、每個 session 在開口前就先付 5,000 token。
- **長 context 中段注意力最弱**，準確率掉幅可能超過 30%，所以關鍵規則靠近結尾權重較高。

### 核心原則

1. **刪到痛**：每行自問「拿掉這行，模型會犯它本來不會犯的錯嗎？」不會就刪。
2. **不複製 linter**：能被格式化工具機械強制的，不要寫成文字。
3. **用檔案引用，不貼程式碼**。
4. **具體可測，不要口號**：「預設用 server component」可測；「寫乾淨的程式碼」是口號。
5. **三層框架**：一定做、先問、絕不做。取代扁平的長清單。
6. **有機成長**：從真實踩坑長出來的規則，勝過一次寫滿的臆測規則。

### 模型進化的角度

官方針對新一代模型的 prompting 文件（我引用的是報告中整理的內容）指出：**為舊模型寫的指令會反傷新模型**。幾個對應：

| 模型行為變化（官方描述） | 對舊指令的衝擊 |
|---|---|
| 更字面地遵循指令，不會默默推廣、不會推論你沒提出的請求 | 為了「會自行推論的舊模型」寫的防呆規則變成噪音；字數上限類規則會被過度照字面執行 |
| 如果你加了強制進度回報的鷹架，試著移除 | 強制進度回報可以拿掉 |
| 正面範例比負面範例有效 | 大量「禁止 X」效果差 |
| 龐大的系統提示會誘發過度思考 | 設定本身會讓模型想太多 |
| 「只回報高嚴重度」會被更忠實遵守，召回下降 | 保守措辭的審查規則可能壓掉真 bug |
| 預設少生子代理 | 強制委派的架構可能與新預設對打 |

### 我對自己設定的體檢結果

做這份研究時，我也用實測數據檢查自己的設定：

- 常駐載入量是 801 行（主檔加 6 個 `@import` 檔），是社群最佳值的 10 到 20 倍。
- **最大的結構問題**：我的設計哲學是「主檔是指標，不是圖書館」，細節放在其他規則檔。但 `@import` 是**常駐載入**，6 個規則檔每個 session 全進 context。模組化達成了可讀性與可維護性，**完全沒省 context 預算**。
- 「禁止」字樣出現 70 次，強調符號 16 次。強調符號通膨，等於全部都重要、也就全部都不重要。

不論模型怎麼進化，這些**應該保留**：不可逆操作的禁令（git 破壞性操作）、敏感資料脫敏、語言偏好、路徑規範。模型再強也不會自己知道你的偏好，而安全類規則不會隨模型進化過期。

## 幾個共通的學習

從四個案例整理出我自己的取捨原則：

1. **主檔是索引，細節按需載入**。但要確認「按需載入」是真的按需（不是 `@import`）。
2. **角色少而精，依信任邊界與成本分，不依架構層分**。
3. **規則要有可測試的形式**。用字串斷言測政策、用 CI 機檢取代人記得。
4. **刻意不做的事要寫下來**，並保留被否決的草稿與理由。
5. **文字指示與機制強制要分開看**。沒有強制的規則，可靠度是未知的。
6. **別人的宣稱先自己驗一遍**，而且要有第三方查核。
7. **功能強大不等於適合你**：常駐服務、信任評分這類機制，要看成本與你的使用情境。

## 可直接套用的檢查清單

讀別人的設定時：

- [ ] 我判定研究對象類型了嗎？自動掃描的結果人工覆核了嗎？
- [ ] 每個設計亮點都附了檔案與行號嗎？
- [ ] README 的數字，我自己數過了嗎？
- [ ] 這條規則是靠模型自願遵守，還是真的有程式攔截？
- [ ] 預設狀態是開還是關？
- [ ] 我標明了覆蓋度（讀了多少比例）嗎？
- [ ] 有第三方對報告的引用與數字做查核嗎？

寫自己的 `CLAUDE.md` 時：

- [ ] 每一行拿掉後，模型會犯它本來不會犯的錯嗎？
- [ ] 常駐載入的總行數與 token 數是多少？
- [ ] 有沒有複製 linter 能做的事？
- [ ] 規則是具體可測的，還是口號？
- [ ] 為舊模型寫的鷹架，新模型還需要嗎？
