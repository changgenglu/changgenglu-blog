# Skill 撰寫與維護

> Skill（技能檔）是程式代理的「按需載入的說明書」。這篇整理我寫、改、清理 skill 一年來學到的事：description 怎麼寫才觸發得準、什麼 skill 該讓人手動叫、內文有哪些會被工具默默破壞的寫法、通用知識為什麼要清掉，以及怎麼便宜地測試一支 skill。2026 年寫成，以 Claude Code 的 `SKILL.md` 為例。

## 先釐清：skill 是什麼、佔什麼成本

一支 skill 通常是一個資料夾，裡面有 `SKILL.md`（YAML frontmatter 加 Markdown 內文），可選的 `references/`（細節文件）與 `scripts/`（腳本）。

載入分兩階段，這決定了寫法：

- **description（一兩句話）常駐**：每一輪對話都在 context 裡，讓模型判斷「這個任務要不要用這支 skill」。
- **內文按需載入**：被觸發時才讀進來。

所以 description 是「每輪都要付的成本」，內文是「用到才付的成本」。寫 skill 的大部分取捨，都是在這兩種成本之間分配。

## description 怎麼寫：定位、觸發、替代

我看過幾個公開的 skill 集合後，歸納出比較穩的 description 結構（取材自研究他人設定的筆記，見〈讀別人的 AI 代理設定學到什麼〉）。有一組 11 支 skill 的 description 一律是三段：

1. **一句話定位**：這支 skill 做什麼。
2. **何時觸發**：含使用者常見的講法，不只寫抽象場景。
3. **替代方案指向**：何時該用別的工具而不是它。

第三段最容易被省略，但價值最大。當兩個能力重疊時（例如 skill 版的網頁抓取與內建的 `WebFetch`），模型需要明確的選擇依據，否則就是「兩個都能做，隨便選」。

我自己的 description 常見寫法：

```yaml
description: >
  省成本跑 skill 測試：新舊對照、評分、description 觸發率最佳化、任何 claude -p 迴圈。
  使用者說「跑 skill 測試」「量觸發率」「評分這幾份回答」時先進來。
  不觸發：寫改 skill 內容本身（改用 skill-creator）。
```

三個要點：

- **把使用者最可能說的話直接寫進去**。模型是靠語意比對決定觸發的，「幫我跑 skill 測試」比「評估工具鏈」好命中。
- **寫「不觸發」的情境**。相近的 skill 越多，這一段越重要。
- **極簡的 skill 也可以成立**。我看過一支只有 9 行本體的 skill，只做兩件事：鎖定輸出載體（一個 HTML 頁面）與風格（大圖少字），其餘全交給模型判斷，連輸出格式 schema 都不寫。代價是完全不可審計，沒有可勾選的檢查項。這適合「一次性、依主題自由發揮」的任務，不適合需要穩定品質的流程。

## 手動觸發 vs 模型自動觸發：一個成本模型

一個公開的 skill 集合（41 支）讓我印象很深：其中 22 支進入官方清單的 skill，有 17 支設了「禁止模型自動觸發」（`disable-model-invocation: true`），只能由使用者用斜線指令手動叫。作者把取捨講成兩種成本：

| 觸發方式 | 付出的成本 | 適合 |
|---|---|---|
| 模型自動觸發 | **context 成本**：description 每輪都在視窗裡 | 使用者不會記得它存在、但幾乎每次相關任務都該用 |
| 使用者手動觸發 | **認知成本**：你要記得它存在 | 流程型、低頻、你很清楚何時要用 |

我的做法偏向相反（大多數 skill 走語意觸發），但這個框架讓我開始問兩個問題：

- 這支 skill 的 description 每輪佔多少 token？60 支 skill 就是 60 段常駐文字。
- 它真的需要模型自己判斷時機嗎？還是「我自己知道什麼時候要用」？

手動觸發的 skill 數量多到記不住時，作者的解法是寫一支「路由 skill」專門當目錄，並規定任何 skill 新增、改名、移除都要回頭更新它，防止目錄與現實脫鉤（router 說謊）。這個維護規則比目錄本身更值得學。

> 未實測：我尚未把自己的 skill 改成手動觸發並量測節省多少 token，上面只是框架。

## 內文的寫法

### 只放流程，細節抽成 reference

重量級 skill 的做法是：`SKILL.md` 只留「流程」，模板、定義、字彙表抽成同目錄的具名檔案（`TEMPLATE.md`、`GLOSSARY.md`），按需展開。檔名就是索引，找東西不用整檔翻。

### 完成條件寫成可勾選的清單

「應該差不多好了」換成機械可判定的門檻，是防止代理過早宣稱完成的具體做法。例如除錯 skill 要求「能重現」「結果確定」「執行快」「代理能自己跑」四個條件同時成立，才算進入下一階段。

### 把「為什麼」留給能解釋的詞

有個技巧是用模型預訓練裡已經帶豐富含義的詞（例如「tight」）取代一整句解釋，並在全文一致使用，讓這個詞累積出「分散式定義」。省 token，也更穩。我沒有實測這個說法，視為值得嘗試的寫法。

### 自己人也要守的規則：引用要核實

我的註解規範 skill 裡有一句：

> 註解與程式碼不一致的改動，引入 bug 的勝算約 1.5 倍（某作者 2024）

這句寫進去時**出處從未核實**：只有姓氏和年份，沒有標題、期刊或連結。更尷尬的是，同一份檔的下一節正在禁止「寫『曾實測』這種無法查證的宣稱」。規則檔自己示範它禁止的寫法，是規則失效的已知形態。

後來補查：論文存在（arXiv 上有一篇研究註解與程式碼不一致對引入 bug 的影響），摘要原句與「勝算約 1.5 倍」一致，我另外抓了摘要頁獨立核對標題與字串。結論是數字正確，於是補上標題與連結，其餘內容不動。

查核的順序是「**查歸屬，不只查存在**」：

1. 這篇文獻存在嗎（作者、年份、標題、發表處）？
2. 它真的在講那件事嗎，還是被借去當佐證？
3. 數字是原文的嗎？量的是同一件事嗎（勝算比與風險比不同）？

為什麼要認真：被多支實作代理預載的 skill，裡面每個斷言都在指導實際行為。同月還有另一個例子：查外部 AI 研究報告時，三個 arXiv 編號有兩個錯置，論文存在，但連結指向別篇。

## 一個會默默破壞內文的坑：`$N` 被參數替換吃掉

Skill 在載入時可以帶參數，內文用 `$ARGUMENTS` 整段代入。踩到的坑是：**內文裡的 `$1`、`$2`、`$3` 這類 shell 或 awk 位置變數，會被 skill 參數當成「第 N 個參數」替換掉。**

事故樣貌：我的 worktree 管理 skill 內文有一行檢查用的 awk：

```bash
git worktree list --porcelain | awk '/^worktree /{print $2}'
```

帶著「建兩個 worktree：分支 A、分支 B」這類自然語言參數載入後，`$2` 被換成參數的第三個詞（參數以空白切分），指令變成語法錯誤。更糟的是失效方式是**靜默的**：照抄執行時 awk 印出的不是路徑，`while read` 拿不到有效路徑，檢查「跑完不報任何撞名」，看起來像「全部正常」。

後來用受控實驗整理出行為矩陣：

| 寫法 | 會不會被替換 |
|---|---|
| `$1`、`$2`、`$10`（`$` 加數字） | 會；`$10` 按兩位數整體解析 |
| `$2a`（數字後接字母） | 不會 |
| `${VAR}` | 不會 |
| `$NF` | 不會 |
| 參數個數不足時 | 原樣保留，不會被清空 |
| `references/` 與 `scripts/` 裡的檔案 | 不受影響 |

最後清點：3 支 skill 各有 1 行受影響，全部改寫成不用 `$N` 的寫法，並加一條政策測試防止復發。

**教訓**：

- 在 skill 內文放 shell 或 awk 位置變數前，先確認參數替換規則。
- 帶參數與不帶參數兩種載入方式都要測。
- 用 `$ARGUMENTS`（整段）而不是位置參數，天然避開這個坑。

## 模型換代後，通用知識要清

Skill 不是寫完就好。我在一次盤點中把全域 61 支 skill 逐支分成三類：

- **通用知識**（模型本來就會）
- **團隊專屬事實**（模型不可能知道）
- **行為約束**（要求模型照某種方式做事）

結果：保留 36、瘦身 18、棄用 6、合併 1。判讀由三個子代理平行讀完後給出，**屬於推論，不是行為量測**。

為什麼要清？通用內容有兩個成本：

- 每次載入都佔 context。
- 可能用舊做法誤導模型。寫給舊一代模型的提示詞，對新一代模型常常是多餘的。

做法：

- **只刪通用段落**，frontmatter 保持逐位元組相同。
- 被刪行掃一遍團隊專屬標記，人工確認只是通用範例。
- 瘦身前備份；用三驗（跨檔 grep、指標是否解析、URL 狀態碼）確認沒弄壞引用。
- 被封存的 skill 不是刪除，而是搬到封存資料夾，引用改指到替代品。

未驗：瘦身後的**行為層**沒有跑 A/B。如果之後表現變差，從備份還原。

### 用統計決定停用？樣本要夠

我曾想用 transcript 統計 skill 的實際觸發次數，找出可停用的。第一次掃了 41 個 transcript，結果 14 個 skill 全是 0 次。結論**不能**是「全部可停用」：

- 樣本只涵蓋約 25 小時、6 個主 session，不具代表性。
- 第一版有誤判：skill 文件載入後，內文提到的其他 skill 名稱被當成「使用者提到」。修正後才歸零。
- 我事前憑直覺估的「使用機率」（25% 到 40%），與實測 0 次對照，高估嚴重；但估 5% 的項目，25 小時樣本也**無法否定**它們存在。

做法修正：觀察期至少拉到 30 天，再決定停用。**統計的可靠性，取決於樣本期間能不能代表正常使用。**

## 便宜地測試一支 skill

測 skill 的基本流程（新舊版對照、評分、description 觸發率最佳化）本身沒問題，問題在於**用最貴的模型、不估量、不煙霧測就開迴圈**。

我自己的事故：用最高階模型跑 description 最佳化迴圈，開了 38 次以上的無頭（`claude -p`）session，一天的額度耗盡，結果是 0 bytes。後來把紀律固定成七條：

1. **執行端與評分員一律用最便宜的模型**（我用 haiku）。測的是「有沒有觸發」「有沒有命中斷言」，模型等級不改變量到的東西，只改變成本。
2. **啟動前先算總呼叫數**：題數、每題次數、輪數、再乘訓練與測試兩份。超過 20 次要先取得使用者同意。
3. **先煙霧測 2 題**：一題該觸發、一題不該。該觸發的那題必須**真的觸發**才開迴圈。0 觸發代表要先查偵測機制或額度，不是迴圈要修的對象。
4. **無頭迴圈獨跑**，不與其他子代理並行，同時最多 3 個 worker。並行撞到速率限制，結果是「燒了卻沒結果」。
5. **基線不重跑**：改 skill 後第二輪只重跑新版，舊版回答沿用、用新標準重評。
6. **先腳本、後模型**：能用字串判定的斷言，以及跨檔 grep、指標解析、URL 狀態碼、diff 消失句這類檢查，用腳本跑；模型只處理語意題。
7. **讀很多、答幾句的研究題**交給別家模型代讀，不吃主要額度（公開文件才適用，個資不外送）。

跑測試時還要限制載入，避免每次開場把整套個人設定都讀進去：

```bash
# 從沒有專案設定檔的目錄跑，限制載入來源與回合數
claude -p "<prompt>" --model haiku --setting-sources project --max-turns 3
```

這些紀律用 hook 機械化：指令含 `claude -p` 但沒有 haiku，就硬擋。

### 估算範例（我自己的實測，僅供估量）

| 項目 | 規模 |
|---|---|
| 對照測試一題一次（中階模型） | 約 10.5 到 11.3 萬 token |
| 評分 6 份回答（中階模型） | 約 11.9 萬 token |
| 三驗（中階模型） | 約 26 萬 token |
| 一次完整的 description 迴圈（20 題、3 次、5 輪、訓練加測試） | 最多 360 次開場；沒估量就開跑是事故主因 |
| 無頭一次開場（載入整套個人設定的最高階模型） | 數萬 token；限制載入後仍約 2 到 3 萬，有快取後便宜 |

## 可直接套用的檢查清單

- [ ] description 有定位、觸發語（含使用者常見講法）、替代方案（不觸發的情境）嗎？
- [ ] 這支 skill 該讓模型自動觸發，還是我手動叫？常駐的 description 佔多少 token？
- [ ] 內文有沒有 `$1`、`$2` 之類的位置變數？帶參數載入時測過嗎？
- [ ] 內文引用的數字、文獻，查過出處了嗎？
- [ ] 這段內容是模型本來就會的嗎？是就刪，只留團隊專屬事實與行為約束。
- [ ] 清理或瘦身前有備份嗎？有三驗嗎？
- [ ] 用觸發統計決定停用時，樣本期間夠長嗎（至少 30 天）？
- [ ] 跑測試前，有寫下總呼叫數、模型、煙霧測結果嗎？
