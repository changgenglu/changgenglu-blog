# 退役的 skill 與 agent

> 設定檔只會越長越多，不會自己變少。這篇記錄我實際退役過的 skill 與 agent、各自的理由，以及我整理出的退役判準與封存做法。2026 年寫成，以 Claude Code 的 skill（技能）與 agent（子代理定義）為例，「該不該留」的判斷與工具無關。

## 為什麼要退役，而不是放著

放著不用的 skill 與 agent 有實際成本：

- **常駐成本**：skill 的 description、agent 的定義，都會出現在開場的系統提示裡，每輪都付 token。
- **誤導成本**：寫給舊一代模型的做法，對新一代模型可能是多餘的，甚至用舊做法誤導它。
- **維護成本**：內容引用的檔案消失、依賴的服務停用，它就變成「寫著做得到、實際做不到」的說明。
- **決策成本**：清單越長，模型與我自己越難判斷「這個任務該用哪一個」。

但退役也有風險：刪太快會失去還原的機會。所以我的做法是「封存、不刪除」，並且把還原方式寫清楚。

## 案例一：一個審查用的 agent，因為額度長期不足而停用

### 背景

我的審查流程有一個「對抗位」：請另一家模型（透過 Codex CLI）當挑戰者，從不同模型的視角質疑審查結論，讓主審在多種聲音中判斷。

### 問題

它的定義指定了某一代 codex 模型，但執行環境的帳號未授權該模型：

1. 代理回報受阻（這是正確行為）。
2. 原本由它負責的三個查核點，變成主代理人工替補。
3. 每次深度審查都重複發生。

我記錄過兩次：每次人工替補估計花 15 到 20K token，累計約 30 到 40K token。當時列出了三個改善方案：

| 方案 | 做法 | 缺點 |
|---|---|---|
| A | agent 定義加 fallback：不可用就改用另一個模型以「對抗性批評者」模式執行 | 要維護兩條路徑 |
| B | 把固定查核點整合進主審的檢查清單 | 失去獨立第三方視角 |
| C | 委派前先測試模型是否可用，不可用就標記並由主代理人工處理 | 仍有 token 浪費 |

### 最後的決定

幾個月後，額度問題仍然長期存在，對抗位經常跑不起來。決定是：**停用，而且不補位**。

「不補位」是刻意的。我接受審查流程的「對抗性挑戰」這個維度，目前沒有專責通道，而不是用一個勉強能跑的替代品假裝它還在。

### 做了什麼

- 三個檔案（agent 定義、無頭呼叫的參考文件、報告模板）搬到封存資料夾。
- 審查流程中所有「呼叫它」的接線同步移除：流程文件、發現清單的規格、機械核對腳本、主審的定義、共用護欄、各審查員的分工表。
- 原檔還原點備份在對應的任務目錄。

### 為什麼要特別說明還原方式

封存資料夾不在 Claude Code 的掃描範圍內，所以封存的 agent 不會被載入，代理清單與開場系統提示都看不到。還原要做兩件事，而且缺一不可：

```bash
# 三個檔一起搬回原位（agent 定義內部引用報告模板的路徑）
mv _archive/agents/codex-reviewer.md agents/
mv _archive/agents/references/codex-headless.md agents/references/
mv _archive/agents/references/templates/report-reviewer-codex.md agents/references/templates/
```

搬回檔案之後，**還要把審查流程的接線加回去**。只搬檔案沒有呼叫端會派它，等於沒還原。而且代理清單要開新 session 才會重新掃描。

### 教訓

- **停用一個 agent，是在改動整條呼叫鏈**。找出所有引用它的地方，一起拿掉，否則流程裡會留下指向不存在代理的死指標。
- **「不補位」也是一種決定**。要寫明這個能力缺口是被接受的，免得之後有人以為是遺漏。
- **反覆出現的設施問題（額度、授權）要認真看待**。我在第二次出現時就已經有「加 fallback」的方案，但沒有執行；到了第三次、第四次才決定停用。如果第二次就問「這個設施問題會不會長期存在」，可以少浪費幾次。

## 案例二：一個回歸診斷 skill，因為依賴的檔案消失而退役

### 背景

我在某次大幅精簡常駐設定（把常駐的行數從 801 行砍到 215 行，部分規則從常駐改成按需載入，並放寬了委派門檻）之後，寫了一支專門的 skill，用來診斷「精簡之後行為變差」的回歸。它整支綁定那一次的精簡：說明、診斷步驟、還原路徑，都指向那次留下的變更清單、診斷腳本與備份檔。

### 退役理由

1. **它依賴的檔案已經不存在，做不了它自己寫的事**。實測那批備份檔已不在原位置，診斷的第三步「從備份還原出問題的那一段」無法執行。（內容在版本控制歷史裡仍找得回，但 skill 寫的是讀工作區的檔案，照著跑會直接撲空。）
2. **它自己寫了退役條件，而且早已到期**。原文寫「觀察期結束、確認穩定後可退役」，評估日是精簡後滿一個月。截至退役時，沒有新的確認回歸，且常駐層在期間被整個重構過一輪（約 38.7 KB 降到約 28 KB），原本的變更清單對現況已經不是有效的比對基準。
3. **刪 skill 要經使用者核准**，本件核准在案。

### 保存下來的通用診斷邏輯

這支 skill 本身退役了，但它的一個觀念我留了下來，歸檔在封存文件裡。行為異常時，先分清楚三種情況：

| 類別 | 變更性質 | 典型症狀 | 判定 |
|---|---|---|---|
| A1 | 行為改變（例如委派門檻鬆綁） | 該委派卻自己做 | 規則還在常駐層卻沒被遵守，多半不是「內容不見了」，要查門檻本身的措辭 |
| A2 | 常駐改成按需載入 | 規則像沒生效 | 規則還在，只是當下那個場景沒觸發讀取，這是**疑似根因**，補觸發條件 |
| A3 | 刪除 | 整段找不到 | **只還原出問題的那一段**，不要整檔回滾（會丟掉精簡效益） |

**最通用的一條**：行為異常時，先分清楚「規則不見了」與「規則在但當下沒載入」。後者在分層載入的架構下是最常見、也最容易被誤判成前者的失效。

### 教訓

- **一次性的診斷 skill，寫的時候就把退役條件和日期寫進去**，這支做對了。但更好的做法是**到期日當天就處理**，而不是等到好幾週之後才發現它依賴的檔案已經消失。
- **不要重建這個 skill 的通用版**。同一件事已經有常設機制承接：精簡前後的修訂程序、改完之後的輕量三驗（搬移後補掃專名引用）、以及自動化測試（約束句斷言與常駐鏈大小斷言）。新增一個 skill 去做已有機制做的事，是在重複建設。

## 案例三：七支 skill，因為「模型本來就會」而封存

我在一次全域盤點中，把 61 支 skill 逐支分成三類：通用知識（模型已會）、團隊專屬事實、行為約束。結論是保留 36、瘦身 18、棄用 6、合併 1。判讀是推論，不是行為量測。

被封存的七支（六支棄用加一支併入別處）與理由：

| Skill | 理由 | 去向 |
|---|---|---|
| Excel 專家 | 屬於 pandas 與 openpyxl 的通識，無腳本；官方 plugin 已涵蓋 | 引用改指官方 plugin |
| PDF 處理 | 與官方 plugin 重複 | 引用改指官方 plugin |
| pre-commit 設定 | 是 Husky 與 lint-staged 的標準步驟，而團隊後端是 PHP，用不到 | 封存 |
| Python 資料自動化 | 通用 Python 範本 | 封存（有三條紀律未搬遷：全量比對禁抽樣、乾跑後才寫入、不一致超過一成就停下） |
| 儀表板設計 | 儀表板設計通識，與內建的資料視覺化 skill 重疊 | 引用改指內建 skill |
| 部署顧問 | GKE、CI、Docker 的檢查表通識；團隊約束已在常駐的安全規則裡 | 封存 |
| 反過度工程審查 | 唯讀診斷「能砍什麼」，功能與審查員的過度工程維度、內建的簡化功能重疊 | 併入審查員的維度 |

做法：

- **移到封存資料夾，不刪除**；引用它的地方改指向替代品。
- 封存清單變動，同步更新安裝紀錄。
- 有價值但沒搬的內容（上表標「三條紀律」的那種）留在封存目錄，並寫進處置紀錄，之後要用時查得到。

### 這一類退役的判斷訊號

- 內容主要是「模型本來就會的通識」。
- 有官方或內建的替代品，且功能重疊。
- 屬於其他技術棧（我的團隊用 PHP，卻有 Husky 的 skill）。
- 與另一支 skill 的功能高度重疊，可以併入。

## 退役判準

從三個案例整理出我現在用的判準，命中任一項就進入評估：

| 訊號 | 例子 |
|---|---|
| 它依賴的東西不存在了（檔案、服務、額度） | 診斷 skill 指向已消失的備份檔 |
| 它自己寫的退役條件已經到期 | 觀察期結束、評估日已過 |
| 反覆被設施問題擋住，修復成本超過價值 | 對抗位因額度長期無法執行 |
| 內容是模型本來就會的通識 | Excel、PDF、儀表板設計 |
| 有官方或內建替代品 | 官方 plugin、內建視覺化 skill |
| 與其他 skill 功能重疊 | 反過度工程審查與審查員維度 |
| 屬於不再使用的技術棧 | Husky 之於 PHP 後端 |

## 退役的做法（我的流程）

1. **先評估，不要憑感覺**。列出每支的分類、依據、信心。判讀是推論的，要標明。
2. **取得核准**。刪除或停用 skill、agent 屬於需要使用者拍板的動作。
3. **備份**。動手前備份原檔，備份位置寫進處置紀錄。
4. **封存，不刪除**。搬到不在掃描範圍的資料夾，並附一份簡短的 README：為什麼封存、怎麼還原。
5. **清理引用**。搜尋所有提到它的地方（agent 定義、skill、流程文件、清單、安裝紀錄），改指向替代品，或一起移除。
6. **跑一次檢查**。引用都解析得到嗎？自動化測試全綠嗎？
7. **寫明「不補位」或「補位在哪」**。
8. **記下還原條件**。例如「某指標在兩週內出現兩次以上」就考慮還原。

### 一個還原機制的設計範例

另一次退役（舊一代模型時代的驗證閘門，因為新一代模型會自行驗證，官方也建議移除）我留了一份完整的還原文件，結構是：

- **裁撤邊界**：裁了什麼、**留了什麼**（留下的是反捏造的證據格式、停點、修訂程序、審查流程，因為它們管的不是「再驗一次」）。
- **還原觸發條件**：例如「宣稱完成但實際未完成」型事故，在任意兩週內發生兩次以上，或審計發現無證據的完成宣稱被採信。
- **還原步驟**：整檔還原（附備份路徑）與精準還原（貼回原文）兩條路。
- **逐段封存原文**：裁撤前逐字保存，標明檔案與章節。

這種做法的價值是：**退役的決定可以被推翻，而且推翻的成本很低**。這讓人更敢退役。

## 可直接套用的檢查清單

- [ ] 這個 skill 或 agent 依賴的檔案、服務、額度，現在還在嗎？
- [ ] 它有沒有自己的退役條件？到期了嗎？
- [ ] 它的功能，官方或內建已經涵蓋了嗎？
- [ ] 它是不是屬於我已經不用的技術棧？
- [ ] 退役前有備份嗎？封存而不是刪除嗎？
- [ ] 所有引用它的地方都清理了嗎？
- [ ] 停用一個 agent 時，呼叫它的流程接線一起拿掉了嗎？
- [ ] 這個能力缺口是「補位」還是「刻意不補」，寫明白了嗎？
- [ ] 還原的步驟與觸發條件，寫在封存資料夾裡了嗎？
