# Hooks 當強制層：攔截、放行與護欄漏洞

> 規則寫在提示詞裡，AI 不一定會照做；把規則交給 hook（事件掛鉤）執行，才有不依賴 AI 記憶的強制力。這篇整理 hook 的 exit code 設計、幾個實際踩過的護欄漏洞，以及上線時「先記帳、後硬擋」的做法。2026 年，以 Claude Code 為例，概念同樣適用於其他有事件掛鉤機制的程式代理。

## 為什麼規則不夠，需要 hook

只靠提示詞約束 AI，有三個結構性弱點：

- **推理鏈出錯時，承諾同時失效**：AI 判斷「這個情境下執行 `git reset --hard` 是合理的」，然後照做。它不是在違規，而是在照自己的推理行事。「我會記得不做這件事」的承諾，在推理出錯時一起失效。
- **注意力衰減（attention decay）**：長任務裡，開頭寫的「不要改 ALLOWED_FILES 以外的檔案」，到第 50 次工具呼叫時的約束力遠不如第 1 次。
- **沒有 LLM 之外的驗證**：AI 說「測試通過了」，如果沒有人真的跑測試，這句話沒有任何外部錨點。

Hook 的關鍵價值是：**它在 LLM 推理之外執行**。不管模型怎麼想，事件發生時（例如「即將執行 Bash 指令」），固定的腳本會固定地檢查一次。

以 Claude Code 為例，常用的事件有：

| 事件 | 時機 | 典型用途 |
|---|---|---|
| PreToolUse | 工具執行前 | 攔截危險指令、改寫指令 |
| PostToolUse | 工具執行後 | 偵測連續失敗、記錄用量、回饋格式問題 |
| SubagentStop | 子代理結束時 | 檢查子代理有沒有交出產物 |
| UserPromptSubmit | 使用者送出訊息時 | 注入提醒、掃描上一則回覆 |
| SessionStart | 開新 session | 恢復上次的任務脈絡 |

## 核心設計：exit 0 與 exit 2 二分

Claude Code 對 hook 結束碼的語意是：

| 結束碼 | 意思 | 什麼時候用 |
|---|---|---|
| 0 | 放行，不阻斷主流程 | 網路逾時、工具沒安裝、環境變數缺失、payload 解析失敗 |
| 2 | 阻斷，並把 stderr 回饋給模型 | 明確違反禁令：破壞性 git、覆蓋設定檔 |

為什麼不用 exit 1？在這套機制裡 exit 1 和 exit 0 一樣不阻斷。bash 慣例的「一般錯誤」在這裡沒有阻斷效果，如果 hook 作者誤以為 exit 1 會擋，就會出現「寫了護欄但根本沒生效」的狀況。所以乾脆只用 0 和 2 兩種。

這個二分法帶出一個原則：

- **外部不可控的失敗一律放行**（fail-open）。hook 自己壞掉，不能讓整個 agent 卡死。
- **明確的安全違反才阻斷**，並在 stderr 寫清楚 `BLOCKED: <原因>`，讓模型知道為什麼被擋、該怎麼改。
- 即使放行，也要在 stderr 說明原因，避免靜默失敗。

### 通用的防禦性開頭

非安全閘門類的 hook，開頭都放同一段，確保 hook 自己的錯誤不會中斷主流程：

```bash
#!/usr/bin/env bash
set -euo pipefail
trap 'exit 0' EXIT ERR   # 任何錯誤都靜默退出，不阻斷主流程
```

硬性安全閘門（例如擋 `git reset --hard` 的 hook）是例外：它只對「明確違反的指令」exit 2，其他狀況仍然放行。

### 三類 hook

| 類型 | 有沒有阻斷力 | 做法 | 例子 |
|---|---|---|---|
| 安全閘門 | 有（exit 2） | 命中就擋，stderr 寫原因 | 擋破壞性 git 指令 |
| 軟性注入 | 沒有 | 用 `additionalContext` 把提示塞進下一輪 | 連續失敗 3 次，提醒換個角度排查 |
| 背景維運 | 沒有 | 改寫、通知、保存狀態 | session 開始時恢復上次的任務脈絡 |

「連續失敗偵測」刻意不用 exit 2：PostToolUse 時工具已經執行完了，阻斷沒有意義；而且連續失敗可能是正常探索，例如 `grep` 找不到字串回傳 1 並不是真的失敗。所以只用 `additionalContext` 軟性提示，讓模型自己決定下一步。

## 開發規範：幾條被事故逼出來的守則

1. **stdin 的 JSON 要容錯**。解析不出來就 exit 0，不要讓壞 payload 卡住主流程。
2. **白名單先於黑名單**。偵測類 hook 先排除預期情境（`grep` 無結果、`find` 無輸出），再計入真實失敗。
3. **計數器別用 PPID 命名**。hook 透過 pipe 啟動時，子 shell 的 PPID 不穩定，同一個 session 會看到不同的計數器。改用「工作目錄的 hash」命名，並加 10 分鐘 TTL，避免上一個 session 的計數污染新 session。
4. **注入的提示用強硬措辭**。軟性的「建議你……」容易被注意力衰減吃掉，注入內容寫成 `ACTION_REQUIRED` 這種格式更有效。
5. **多筆提醒合併成一段**。同一次呼叫觸發好幾則提醒時，合併輸出，不要每則各自輸出。

## 實例一：護欄只要有一個漏洞，等於沒有

### git 全域選項繞過整道防線

擋破壞性 git 指令的 hook，最直覺的寫法是用正規表示式比對 `git reset --hard`、`git clean -f`、`git push --force` 等字串。實測發現：

```bash
git -C sub reset --hard
```

整條放行。因為 `-C <dir>`、`-c k=v`、`--git-dir=`、`--work-tree=`、`--no-pager` 這些全域選項插在 `git` 與子指令中間，每一條比對式都失配。**一個選項就繞過整道防線**，而且這個洞從第一版加固起就存在，直到實測才發現。

修法：比對前，先在「比對用的字串副本」上剝除 git 全域選項；原指令不動。

另一個類似的洞是 `git checkout <path>` 省略 `--`。原本的比對式全部要求出現 `--`，實測直接放行，但破壞力和 `git checkout -- <path>` 完全相同（都會覆蓋未提交的工作樹內容）。字串分不出「分支名」和「檔名」，所以改判「工作區裡存不存在同名路徑」：存在就擋。同名時會誤擋，代價是改用 `git switch`。這是**取誤擋而非漏擋**的取捨。

### 誤判一：worktree 內的分支被當成 master

規則是「在主分支上不准直接 commit」。結果在一個 git worktree（工作樹）裡、HEAD 明明是 feature 分支，commit 卻被擋，訊息說「你在 master 上」。

根因：Bash 工具每次呼叫的起始目錄都會被重設回主 checkout，而主 checkout 當時確實是 master。指令是 `cd <worktree> && git commit ...`，hook 判斷分支的時機卻是在 `cd` 之前，用的是 hook 啟動時的目錄。

修法：分支判定改看**指令內最後一個 `cd`／`-C`／`--work-tree` 目標**，不把 hook 啟動時的目錄算進去；沒有 `cd` 時行為不變。

### 誤判二：hook 掃到指令的「文字內容」

用 heredoc 寫一份文件，內容裡提到了被管制的指令字串（例如在文件中說明 `git reset --hard` 為什麼危險），整條 `cat > file` 被擋，儘管那條指令根本沒執行任何 git 操作。

修法：比對前先剝除 heredoc 內文。heredoc 內文是資料，不是指令。

這兩個誤判有同一個教訓：**hook 要看「真正會被執行的指令」與「真正的 HEAD」，不是看字串長得像什麼**。三層 workspace 制下，一個 repo 同時有 master checkout 與多個 feature worktree，這種形狀是常態，不是特例。

### 管線與 heredoc：黑名單必漏

另一個護欄是「既有的環境 pod 只准唯讀」。hook 的做法是：段首錨定 `kubectl`、解析第一個非旗標 token 取子指令，只管 `exec` 與 `cp`，只要 pod 內那段帶寫檔或安裝行為就擋。

對抗性測試時發現兩條漏網路徑：

```bash
# 一、管線餵進 kubectl：段首是 cat，整段被跳過
cat probe.js | kubectl -n ns exec -i some-pod -- tee /app/probe.js

# 二、pod 內用 curl -o 落檔：curl 不在寫檔指令清單內
kubectl -n ns exec some-pod -- sh -c "curl -o /app/x http://example/x"
```

修法也有取捨：

- 「段首必須是 kubectl」本身有必要，否則「文字裡提到 kubectl」會被誤擋。要修的是讓錨定也認得**管線右側**的 kubectl。
- `curl` 不能整個指令名放進寫檔清單，因為單純 `curl <url>` 是唯讀觀察。要判旗標：`-o`、`--output`、`-O`、`--remote-name`（curl），`-O`、`--output-document`（wget）。

驗收時同時列「照擋」與「放行」兩組案例，最後兩條放行案例是修管線錨定時最容易誤傷的：

```bash
# 照擋
cat probe.js | kubectl -n ns exec -i some-pod -- tee /app/probe.js
kubectl -n ns exec some-pod -- sh -c "wget -O /app/x http://example/x"

# 放行
kubectl -n ns exec some-pod -- sh -c "curl -s http://example/health"
kubectl get pods -n ns | grep -v cp            # 段首非 kubectl，但整段唯讀
kubectl -n ns exec some-pod -- cat /app/x | tee local.txt   # tee 跑在本機，不在 pod 內
```

### 這類 hook 的共通設計

- **比對一律用 token 邊界，不用裸子字串**。否則 `kubectl get pods | grep -v cp` 會被當成 `kubectl cp`，`gcp` 裡的 `cp` 也會誤中。
- **引號感知**：引號外的 `>`、`|`、`;`、`&` 由本機 shell 解讀，寫的是本機檔案；只有引號內交給 pod 端 `sh -c` 的才在 pod 內生效。
- **`>` 不等於重導向**：`2>&1` 是 fd 複製，`length($2)>0` 是比較運算子。重導向的判準是右側目標長得像路徑。
- **直譯器內寫檔也要擋**：`node -e` 的 `writeFileSync`、`python -c` 的 `open(..., 'w')` 不含任何 shell 寫檔 token，卻是最順手的繞法。
- **回歸測試用真實環境**：用真實的 git repo 與真實的 worktree 組合成測試 payload；修前先重現誤判，修後確認全綠，再確認既有的硬擋案例仍然成立。

## 實例二：規則要讓「讀得到它的人」看到

子代理在 worktree 內用了不帶標記的 `git stash` 與 `git stash pop`，來驗證「這個測試紅燈是既有的，不是我改出來的」。

為什麼危險：git 的 stash 堆疊是**整個 repo 共用**的，所有 worktree 與所有並行 session 共用同一疊。`git stash pop` 永遠彈出最上面那筆；如果在 push 與 pop 之間，另一個 session 也 push 了一筆，pop 就會把別人的東西彈進自己的工作樹。

這次沒有出事，但同一天另一個子代理又用了同樣手法。兩次都命中同一個風險，說明這不是單一代理的個別行為，而是「要退回基線重跑」這個常見需求缺少正確做法時的共同反射。

根因有兩個：

- 這條禁令只寫在主代理的環境說明裡，**子代理讀不到**。
- 子代理繼承的常駐規則檔，反而寫著「有 modified 先 `git stash push -u` 備份再操作」，等於默許。

正確修法有兩個方向，而且要成對給：

```bash
# 禁令（附唯一標記的 push，並用標記找回）
git stash push -u -m "<unique-tag>"
git stash apply stash^{/<unique-tag>}

# 替代做法：根本不碰共用堆疊，改用檔案備份
cp path/to/file "$SCRATCH/file.bak"
git show HEAD:path/to/file > path/to/file   # 換成基線版本
# ... 跑測試 ...
cp "$SCRATCH/file.bak" path/to/file          # 還原
```

教訓：只寫禁令不給替代做法，AI 會反覆回到禁令想擋的那條路，因為需求還在。

## 實例三：上線順序，先記帳、再決定要不要硬擋

某條規則是「子代理單次最多 60 次工具呼叫、整個任務最多 200 次」，寫在文件裡，從來沒有任何機制強制。事後實測：

- 有一個任務逾額一倍以上（實際 427 次），兩個子代理各跑了 80 多次，全程沒有任何停下確認的紀錄。
- 同型違規三次復發，趨勢惡化。

直覺是「那就加硬擋」。但這裡的決定是**先記帳、後擋**：60 與 200 這兩個門檻從來沒有用數據校準過。任務跑到 87 次，既可能是嚴重超支，也可能代表門檻訂得不切實際，這兩種解讀導向相反的修法，而當時沒有任何數據能分辨。

於是做了一個「記帳器」hook：

- 只記錄中繼資料（時間、session、代理編號、工具名稱、三種計數、耗時），不記 `tool_input` 與 `tool_response`。
- 逾門檻時提醒一次，不阻斷。
- 預留 `ENFORCE=0` 開關，一個環境變數就能在日後切成硬擋。
- 永遠 exit 0，jq 缺失、payload 壞掉、目錄不可寫，一律靜默放行。

做記帳器時順手發現兩個實作坑：

1. 原本用不可見的控制字元當欄位分隔，被編輯器正規化或複製貼上弄掉時，會走進 else 分支，**靜默停止計數**。改成逐行輸出。
2. 原本計數是「讀→加一→寫回」，平行子代理會互相覆蓋、系統性少算。改成 append 一個位元組再用 `wc -c` 數大小（利用 `O_APPEND` 的原子性）。

壓力測試：50 次同時呼叫，計數恰為 50、月檔恰 50 行。

### 另一個教訓：只記帳不執法，等於軟性宣告

記帳器上線後，累積了三萬多行紀錄，而卡片自己訂的「第二階段分析」觸發條件（累積 3 到 5 個實作任務）早就滿足，卻沒人去看。結果硬擋一直沒做。這張卡後來被退回「規劃中」，因為「進行中」的狀態是假的。

另外還有一個更尷尬的發現：**原本判死這條路的知識庫記載是過期的**。舊記載斷言「子代理工具不會觸發 hook，所以做不了這種閘門」，依據是某個舊版本的實測。換新版重測，結論相反：

- PreToolUse 掛在 `Task`／`Agent` 上，委派當下會觸發。
- 子代理內部每次工具呼叫都觸發 PreToolUse／PostToolUse，payload 帶 `agent_id` 與 `agent_type`，可以逐一歸屬。
- 主代理與子代理共用同一個 `session_id`，跨波段累計天然成立。

教訓：**平台能力的負面結論要附版本號**。「不能」常常只是「某個版本當時不能」。

### 計量單位本身也要質疑

後來又發現，記帳器只計「次數」，但這個任務真正在意的是成本。新版本的子代理完成通知已經帶有 token 用量與耗時，而記帳器沒有 token 欄位。結果是「量得到，但沒有任何環節把它寫下來」，事後審計只能永遠記「無法確認」。

兩條候選修法（都未裁決）：在 SubagentStop 事件記 token（要從 transcript 算，有非同步延遲，必須 fail-open），或要求主代理收尾時抄錄通知裡的數字（無延遲，但靠自律）。

## 實例四：用 hook 強制「驗證後才宣稱完成」，值不值得？

想用 SubagentStop hook 強制子代理「驗證後才能宣稱完成」，評估了三案：

| 方案 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| A：關鍵字提醒 | 報告不含「驗證／測試／verification／test」任一字就印警告，仍 exit 0 | 零阻擋風險、30 行以內 | 偽陽性高（隨手寫「測試覆蓋」也算過） |
| B：結構化欄位加阻擋 | 報告 frontmatter 強制 `verified: passed\|partial\|failed`，缺欄位或 failed 就 exit 2 | 機械可信、可量化追蹤 | 要改十多個子代理定義，初期可能干擾正常流程 |
| C：先 A 後 B | 先上 A 跑 2 到 4 週，偽陽性超過 30% 再升級 B | 風險可控 | 要等 |

結論選 C。有一個重要的判斷依據：當時量測「完成驗證遵循」的指標本來就偏高（九成上下），強制阻擋的邊際效益低。B 的真正價值是「跨任務量化追蹤」而不是「即時阻擋」，後者可以另外用事後審計解析欄位來做，與 hook 解耦。

教訓：**先量測現況再決定要不要硬擋**，不要看到有規則被違反就直接上硬擋。

## 其他實用的小 hook

- **block-once**：第一次命中就擋，並給出三種正確寫法；同一條指令第二次放行。適合「誤報情境存在，但硬擋會變成過不去的牆」的情況（例如偵測 zsh 對純量變數不做字詞分割的 `for X in $VAR`）。key 用「session id 加指令的 sha1」。
- **ask 而非 deny**：某些情況要的是「讓使用者確認」而不是硬擋，可回傳 `permissionDecision: "ask"`。注意多個 hook 的合併順序是 deny 優先於 ask 優先於 allow，而 `ask` 會結束腳本，所以所有 exit 2 的阻擋要排在 ask 之前，否則「commit 加 stash drop」會只跳確認框、後半的破壞不被檢查。
- **糾正型而非硬擋**：偵測到測試名稱含任務編號，PostToolUse 時以 stderr 回饋請 AI 改名，不阻斷。理由是既有程式碼裡還有大量殘留，過渡期硬擋會誤傷。
- **事後偵測**：有些違規無法事前攔截（例如測試腳本在背後悄悄開出新 session），改在執行前後比對檔案清單，有新增就回報。只回報不阻擋。
