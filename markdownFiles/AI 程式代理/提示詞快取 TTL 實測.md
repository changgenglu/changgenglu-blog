# 提示詞快取 TTL 實測

> 提示詞快取（prompt cache）到底多久過期？網路上傳的「定時送保溫 ping 可以省 8 倍」適不適用我的環境？這篇記錄我 2026 年 8 月在 Claude Code 2.1.235（WSL2、訂閱制）上的實測，以及最後「不加保溫機制」的判斷與理由。重點不只是結論，而是怎麼自己驗證、哪些說法只能打折引用。

## 一分鐘版

- **主代理走 1 小時快取，子代理走 5 分鐘，兩者不同**。這是實測，不是推測。
- 因為主代理已經是 1 小時，我**不需要也不應該**加保溫機制。
- 真正該注意的是兩件事：**中途換模型**會讓整段歷史失去快取（比閒置嚴重得多）、**別讓子代理執行單一阻塞超過 5 分鐘的操作**。
- 要省成本，優先查「前綴是否穩定」。這比保溫的槓桿大得多。

## 先講機制

提示詞快取是伺服器端幫你把「已經算過的對話前綴」存起來。前綴指的是每次請求都重複送的那一大段：系統提示、規則檔、對話歷史。下一次請求如果前綴一樣，就不必重算，價格只要輸入價的十分之一。

存放有期限，這個期限叫 TTL（time to live，存活時間）。

官方文件的定價倍率（原文引用）：

| 項目 | 倍率（相對基本輸入價） |
|---|---|
| 5 分鐘快取寫入 | 1.25 倍 |
| 1 小時快取寫入 | 2 倍 |
| 快取讀取 | 0.1 倍 |

寫入 1.25 倍、讀取 0.1 倍，**差 12.5 倍**。這個比值是後面所有成本推導的基礎。

官方文件還有三個重點：

1. **命中會免費續期**：每次用到快取內容，期限就重新算，不額外收費。這是「保溫」可行的機制基礎：到期前碰它一下，只要 0.1 倍。
2. **TTL 從請求「開始」算，不是從回應結束算**。回應生成的時間也吃掉壽命：5 分鐘方案下，一個串流 4 分鐘的長回應，只留約 1 分鐘給下一輪。
3. **官方明文建議保溫**：預設 5 分鐘快取，每 5 分鐘內至少送一次預熱請求；間隔更長就改用 1 小時快取。所以保溫不是社群自己發明的偏方，是第一方建議的做法，文件裡也沒有反對保溫的段落。

## 實測：怎麼驗證 TTL

### 方法

翻 session 的逐字記錄（transcript，JSONL 格式）裡每一筆 `cache_creation`，看 token 落在哪個欄位：

- `ephemeral_1h_input_tokens`：1 小時桶。
- `ephemeral_5m_input_tokens`：5 分鐘桶。

方法來自 Claude Code 官方 repo 的一則 issue（#84253）。

### 結果

| 層 | 記錄數 | 1 小時桶 | 5 分鐘桶 | 判定 |
|---|---|---|---|---|
| 主代理（互動 session） | 30 | **30** | 0 | 1 小時 TTL |
| 子代理 1 | 40 | 0 | **40** | 5 分鐘 TTL |
| 子代理 2 | 75 | 0 | **75** | 5 分鐘 TTL |
| 子代理 3 | 70 | 0 | **70** | 5 分鐘 TTL |
| 子代理 4 | 47 | 0 | **47** | 5 分鐘 TTL |

乾淨的二分，沒有混合。這與 Claude Code 團隊成員在 Hacker News 的說法吻合：主代理通常用 1 小時快取（API 客戶可以開啟 1 小時，但因為成本較高預設不開），子代理通常用 5 分鐘。

### 社群回報的「降級」，在我的版本上不成立

有兩張 issue 說主代理的 1 小時被靜默降成 5 分鐘：#46829（已關閉，指 2026 年 3 月初）、#84253（開啟中，指某個版本之後）。我用 GitHub API 查過，編號確實存在，標題內容相符。

但在 2.1.235 上，主代理測出來是 1 小時，**測不到降級**。#84253 的作者提供了新舊版本的對照數據（舊版 157 筆全 1 小時、新版 347 筆全 5 分鐘），所以他遇到的狀況應該是真的，只是我當下沒有。

這給我一個通則：**社群的版本相依回報，要用自己的版本重測一次**，別直接當成自己環境的事實。

## 一個要打折的說法：「保溫省 8 倍」

我讀了一篇主張「保溫 ping 的成本被高估 8 倍」的文章，還有同一作者的 arXiv 論文。先用比喻建立直覺，再套回本案。

### 直覺：投幣寄物櫃

想成健身房的投幣寄物櫃：投一次幣租 5 分鐘。你每 4 分鐘補投一次，東西一直在裡面，每次只付投幣的小錢。但你改成每 8 分鐘投一次，櫃子在第 5 分鐘就被清空了，你第 8 分鐘投的幣不是續租，而是**重新租一個空櫃子、把所有東西再搬一次進去**，付的是全額搬運費。你以為拉長間隔在省錢，其實每次都在付最貴的那筆。

| 比喻裡的角色 | 對應到什麼 |
|---|---|
| 寄物櫃 | 伺服器端替這條對話存的提示詞快取 |
| 櫃子裡的東西 | 已經算過的對話前綴：系統提示、規則檔、對話歷史 |
| 投一次幣 | 一次讀取快取的請求，價格是輸入價的 0.1 倍 |
| 5 分鐘被清空 | 預設 TTL；作者實測斷點就落在 5 分整 |
| 重新搬進去 | 寫入快取，5 分鐘方案 1.25 倍、1 小時方案 2 倍 |

### 文章的兩個核心主張

1. 最省的 ping 間隔不是常見的 30 秒，而是**貼著 TTL 下緣**（5 分鐘方案約 4 分鐘、1 小時方案約 50 分鐘）。
2. **間隔一旦超過 TTL，成本比完全不保溫還高**，因為每次 ping 都在全額重寫一個已經死掉的快取。

損益兩平公式是 `idle ≈ τ(w/r − 1)`，τ 是 ping 間隔，w 是寫入倍率，r 是讀取倍率：

- 5 分鐘方案：`w/r = 1.25 / 0.1 = 12.5`，間隔 4 分鐘，`4 × 11.5 = 46 分鐘`（文章給的數字）。
- 1 小時方案：`w/r = 2.0 / 0.1 = 20`，間隔 50 分鐘，`50 × 19 = 950 分鐘`，約 15.8 小時（**我自己推算**，文章沒算）。

閒置時間超過這個值，保溫就不如放它死掉重寫。

### 可信度怎麼打折

【驗證過】公式與倍率自洽。我用官方文件的倍率反推，46 分鐘這個數字算得出來；機制描述（命中免費續期、5 分鐘斷點）也與官方文件對得上。

【要打折】**兩張成本表的絕對金額，我無法從敘述重建**。例如 10 分鐘暫停的「讓它死」是 0.667 美元，30 分鐘暫停卻只有 0.333 美元，暫停更久反而更便宜，文章沒有解釋這個落差。建議只引用正文的推導，不要引用表格數字。

【要打折】**同一位作者發表兩次，不是獨立佐證**。部落格與 arXiv 論文是同一人，我查過頁面確認。

【要留意】**標題的 8 倍與論文的 12.5 倍是兩回事**。8 倍是 30 秒間隔對 4 分鐘間隔的 ping 次數比（實測 7.8 倍）；12.5 倍是 `w/r` 比值，理論上限。

【未複現】作者的實測（四家供應商、閒置到 40 分鐘、三次獨立跑），我沒有複現，也沒有第三方複現。

## 社群實際怎麼做

文章把「每 30 秒 ping」當成通行慣例，但去看真的有實作的專案，**沒有人在 30 秒**：

- aider 有 `--cache-keepalive-pings N` 旗標，**預設 0（關閉）**；開了是每 5 分鐘 ping 一次、最多 N 次。官方範例是 `--cache-prompts --cache-keepalive-pings 12`，涵蓋約 60 分鐘閒置。
- 另有幾個實作落在 TTL 的六到八成。

有一個歸屬修正：子代理調查把 aider 的間隔記成 240 秒，但官方文件寫的是**每 5 分鐘**，我在文件裡找不到 240 秒。如果實作真是嚴格 5 分鐘，那剛好卡在 TTL 邊界，正是文章警告的位置（雖然官方文件自己的措辭也是「at least every 5 minutes」）。

**競爭的做法方向相反**：靠重排提示詞讓前綴穩定（某篇報告稱節省 41% 到 80%）、用便宜模型跑保溫 ping、修結構性的快取正確性問題。官方在 changelog 裡做的也是這個方向，例如讓自動模式的權限檢查重用已快取的前綴、子代理進度摘要補上快取。

## 查不到證據的說法（刻意保留）

這節是為了避免未來把沒驗證的東西當事實引用：

- **「訂閱制按滾動 5 小時窗的請求數計費，所以每個保溫 ping 都吃一次配額」**：如果成立，這是反對保溫最強的理由。但只出現在搜尋引擎的綜合摘要，抓不到單一可歸屬的來源。**未證實，不當決策依據。**
- **「保溫 ping 類似 Slowloris 攻擊模式」的倫理框架**：讀起來像搜尋引擎跨來源合成的，不是任何單一頁面的原文。**未證實。**
- **反對保溫、主張數學算不過來的論述**：找不到可歸屬的來源。也就是說，沒有看到有人從成本角度反駁保溫。
- **「續用 session 會不會毀快取」**：有一張 issue 的標題這樣說，但我只看過標題，沒讀內文。**線索，非事實。**
- **訂閱制的配額如何折算 token 與快取**：官方沒有完整公開，所以文章的美金數字換算不到訂閱制。

## 我的決策與理由

**決定：不在我的環境加任何保溫機制。**

三個理由，按重要性排序：

1. **主代理實測就在 1 小時 TTL**。而 Claude Code 的排程喚醒工具，延遲被夾在 60 到 3600 秒之間，區間內不存在要閃避的斷崖。該工具的說明也明文寫著，為了保溫而額外排喚醒是純浪費。這條是硬證據，不是推論。
2. **子代理雖然走 5 分鐘，但我沒有對它加 ping 的介面**。可行動的替代做法是：**別讓子代理執行單一阻塞超過 5 分鐘的操作**（跑整套測試、等一個超長下載），寧可拆成幾段。參考值：那支子代理 29 次工具呼叫、338 秒，平均 11.7 秒一次，不會撞到；但如果它去跑一個 10 分鐘的測試套件就會，而且是全額重寫。
3. **換模型的殺傷力大一個數量級**。changelog 寫了，`/model` 中途切換會「不經快取」重讀整段歷史，連 0.1 倍的讀取折扣都沒有。相較之下，閒置只是重付 1.25 倍的寫入。

### 兩害相權

| 做法 | 壞處 | 嚴重度 |
|---|---|---|
| 加保溫 | 白燒配額；可能撞上未證實的請求數計費；而且主代理本來就在 1 小時內 | 較重 |
| 不加保溫 | 子代理長阻塞時多付一次重寫 | 較輕，而且拆小任務就能避掉，不需要新機制 |

### 真正值得留下的一條

**把穩定內容放前面、動態內容放後面。** 前綴一變動，付的不是 0.1 倍讀取，而是 1.25 倍寫入，差 12.5 倍。這個槓桿遠大於保溫。這件事我本來就在做；文章的貢獻是給了它量化理由。

具體的寫法（以下是依「前綴一變就重寫」推出的通用做法，我沒有逐項實測）：

- 系統提示與規則檔放在最前面，不要在開頭放時間戳、隨機值這類每次都變的內容。
- 對話中途不要修改前面的內容（例如在中間改規則）。
- 工具定義的順序保持穩定。

## 自己怎麼重新驗證

升版後如果懷疑被降級，直接對當前 session 的逐字記錄跑：

```bash
python3 -c "
import json,sys
n1=n5=tot=0
for line in open(sys.argv[1],encoding='utf-8',errors='replace'):
    try: d=json.loads(line)
    except: continue
    cc=((d.get('message') or {}).get('usage') or {}).get('cache_creation')
    if not isinstance(cc,dict): continue
    tot+=1
    if cc.get('ephemeral_1h_input_tokens',0): n1+=1
    if cc.get('ephemeral_5m_input_tokens',0): n5+=1
print(f'recs={tot} 1h={n1} 5m={n5}')
" ~/.claude/projects/<專案-id>/<session-id>.jsonl
```

子代理的逐字記錄在 `~/.claude/projects/<專案-id>/<session-id>/subagents/agent-<id>.jsonl`，同一支指令換路徑就能驗。

**判讀原則**：先跑指令看當下的真實 TTL，再回答「我的快取多久過期」，不要憑版本號或社群 issue 推測。

## 這次研究的做法本身，值得帶走

- **先看自己的資料**（實測），再看官方文件，最後才看社群與文章。證據層級由強到弱。
- **引用文章時，把「公式」與「數字」分開評估**。公式能自己驗算，絕對金額往往不能。
- **同一作者的部落格加論文，算一份證據，不是兩份**。
- **數字的口徑要分清楚**：同一篇文章裡的「8 倍」與「12.5 倍」，量的是不同的東西。
- **查不到的說法，單獨列一節**，標明「未證實」，避免日後被當事實。
