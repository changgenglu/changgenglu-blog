# 多代理對抗審查 loop

> 當一個高賭注的產出（規劃、架構、規則改動）需要比「單一代理自評」更高的信心時，我用 loop 編排「多方獨立對抗審查，再加一個獨立的冷驗證」。本文整理這個方法：為什麼單一代理會同源收斂、審查鏡頭怎麼分工、兩種對稱的失敗模式（縫合怪與過度保守）、最後一關的冷驗證，以及一次真實的跑法。寫於 2026 年，以 Claude Code 的 `/loop` 為編排範例，概念可套用在任何能開多個獨立 session 的 AI 代理工具。

## 何時用，何時別用

**用**：

- 高賭注、難回頭的決策：架構選型、規則或治理改動、要寫進核心設定的東西。
- 單一視角容易自我合理化的場景。

**別用**：

- 日常小任務、機械修改。多代理 loop 成本很高，殺雞用牛刀。
- 只有賭注撐得起這個成本時才開。

一個簡單的判斷：這個決定如果做錯了，要花多少力氣收回來？回收成本低，就不值得開 loop。

## 問題：同源收斂

單一代理（或同一個模型多次自我呼叫）很容易**提早收斂**：後面的推理，被前面的條件所制約。看起來像是從多個角度檢查，實際上是同一條推理鏈走了好幾遍。

常見症狀：

- 讓同一個模型「再想一下有沒有問題」，它通常會找出幾個小問題，然後得出「整體方向正確」。
- 自己寫的規劃，自己審，每一輪都修修補補，但核心假設從來沒被挑戰過。
- 請它「站在反對者的角度」，它扮演得很像，但反對的點都在它原本就已經考慮過的範圍內。

對策不是「想更久」，而是引入**真正獨立**的視角：**不同模型，加上不同 session 的冷 context（沒看過之前討論的全新對話）。**

## Playbook：六步

```text
研究 → 草稿 v1 → 多輪 N 方獨立對抗審查 → 逐輪 ratchet → 獨立冷驗證 → 落地
```

1. **研究與並行深掘**：把待決問題拆成子項，並行調查。
2. **草稿 v1**：合成初版。要有一個**明確、可被攻擊的立場**。模糊的立場沒辦法被審。
3. **N 方對抗審查（每輪）**：見下節「審查鏡頭」。
4. **ratchet（棘輪）**：每輪只吸收「撐得住反駁」的修改，版本單調前進，保進步、棄退步。
5. **獨立冷驗證**：見下節。
6. **落地**：只落通過冷驗證的項目。

### 編排與狀態

用 `/loop` 的動態模式編排：背景自動喚醒、自我排程。狀態寫在**一份 `loop-state.md`**，跨喚醒、跨 context 壓縮都不會失憶。

下面是這份檔案的示意內容（欄位是我為了說明而寫，不是原始檔案）：

```markdown
# loop-state

## 題目
評估外部設定研究報告列出的 6 條可借鏡點，哪些值得搬進核心設定。

## 目前版本
v1.2（第 2 輪審查後）

## 輪次紀錄
| 輪 | 審查者 | 鏡頭 | 主要反對意見 | 處置 |
|---|---|---|---|---|
| 1 | 跨模型 A | 對撞、忠實度 | 第 3 條與既有原則矛盾 | 採納，砍掉第 3 條 |
| 1 | 跨 session B | 反 cargo-cult | 第 5 條只是照抄 | 採納，降為「先 spec」 |

## 待辦
- [ ] 第 2 輪回覆整合
- [ ] 啟動冷驗證

## 預鎖紅線
（冷驗證前寫死，之後不改）
```

編排者（orchestrator，主導 loop 的那個 session）**不兼任審查者**，避免球員兼裁判。

## 審查鏡頭：N 方分工

每位審查者配**一個獨立的攻擊鏡頭**，加上一個「抓漏網之魚」的通用鏡頭。並且全員標配兩個問題：

1. **「這是縫合怪嗎？」**
2. **「這是反射性過度保守、誤殺了好東西嗎？」**

### 兩類審查者

**跨模型審查者**：用不同的 LLM（例如 Codex、Gemini）。必須帶一條硬約束：

> 不具本專案的在地知識，只憑可查證的事實與邏輯一致性，禁止引用訓練資料裡的「最佳實踐」。

這條約束的目的，是讓它只能做**對撞、忠實度、引用正確性**的檢查。如果它可以引用「業界通常這樣做」，它就會把自己的偏好當成事實，而不是檢查這份產出內部的一致性。

**跨 session 審查者**：同一個模型，但每個都是獨立、冷 context 的 session。每個分派一個鏡頭，例如：

- **缺口適配**（gap-fit）：這個提案真的填到我們有的缺口嗎？
- **反 cargo-cult**：這是理解之後的採用，還是照抄形式？
- **過度採納偵測**：有沒有一次採了太多？

### 鏡頭要正交

彼此要攻擊不同面向，才有覆蓋。**鏡頭重疊，等於白跑。** 設計鏡頭時可以問自己：如果把這個審查者拿掉，會漏掉什麼別人看不到的東西？答不出來，就是重疊了。

## 兩種對稱的失敗模式

兩種都要防，而且要同等重視。

### 縫合怪（cargo-cult）

硬把外部點子抄進來，結果撞到既有的原則，製造內部矛盾。外部的設計在它原本的脈絡裡成立，搬到我的系統裡，卻和另一條既有規則互相衝突。

### 過度保守

反射性以「已覆蓋」「我方更好」否決，錯失真正能填補缺口的東西。

### 為什麼要兩個一起防

- 只防縫合怪，結果是什麼都不敢採。
- 只防保守，結果是什麼都抄。

所以兩個問題**同列、強制每位審查者都回答**，才平衡。一個審查者如果只回答其中一個，它的結論就是偏的。

## 獨立冷驗證：落地前的最後一關

最後派一個**冷 agent**：沒看過任何一輪迭代，**禁止讀審查檔**。它的工作不是「再審一次」，而是：

- 回到**原始來源或原始碼**，重新驗證每個「載重主張」（被當成決策依據的事實）。
- 用**預先鎖定的紅線**，對每個「擬採納項」做對抗性的失敗嘗試（試著證明它不成立）。
- 看到「看似已採納、實際上沒有落點或接不上現有結構」的條目，當場擋下。

### 設計要點

**冷出題、盲評、紅線預先鎖定，設計者不能自驗。** 自驗是同源循環，等於沒驗。

冷驗證的價值是：**擋下「迭代過程裡大家都點頭，但其實落不了地」的項目。** 在迭代中，每一輪的審查者看的都是上一輪的修訂版，彼此之間漸漸形成共識；冷驗證的 agent 沒有這個共識的包袱，它只看原始事實與紅線。

### 「無落點」是什麼意思

一個項目看似被採納，但你問「它要寫在哪個檔案的哪一段、由哪個機制觸發、誰來執行」，答不出來。這種項目不算採納，降回「先寫規格」。

## 案例：一次真實跑法

這個案例供對照（日期為 2026 年 6 月底，細節已去識別化）：

- **題目**：一份外部設定研究報告，列了「6 條可借鏡點」。要判斷哪些值得搬進核心設定，要求落地信心達 90 分以上。
- **編排**：一個編排者 session，兩個跨模型審查者（Codex 與 Gemini），三個跨 session 審查者（各一個鏡頭），用 `/loop` 動態模式跑：v1 → 五方審查 → 第二輪五方審查 → 獨立冷驗證。
- **結果**：
  - 6 條裡，只有 **4 項「便宜、正交的小東西」**通過冷驗證落地。
  - **3 個會變成縫合怪的重型移植被砍掉。**
  - 冷驗證還抓出 1 個「看似已採納、實際沒有落點」的條目，降回「先寫規格」。
- **真正的價值**：不在「採了幾條」，而在於**獨立對抗驗證擋下了縫合怪，並誠實標出原清單覆蓋不到的盲區**。

（以上數字照我當時的紀錄轉述，沒有事後逐項重算，彼此加總未必剛好等於 6；重點是方法，不是數字。）

## 落地檢查

每個採納項要滿足：

- 機制與落點明確。
- 通過預先鎖定的紅線。
- **至少 2 個獨立審查者背書。**

不滿足的處置：

- 沒落點、接不上現有結構：不算採納，降回「先寫規格」。
- 通不過冷驗證：不落地。

## 實務上要留意的幾件事

以下是我在其他任務中觀察到的，與這個方法相關的現實限制。這些不是此方法的一部分，而是運用時的提醒。

### 1. 外部模型的額度與可用性

我曾經把 Codex 設為審查流程裡的常駐「對抗性」通道，後來因為額度長期不足，這個通道常常根本跑不起來，最後決定**停用，也不另補位**。

教訓：跨模型審查的價值很高，但**依賴一個不穩定的外部通道，就會讓整個流程在關鍵時刻缺席**。設計時要先問：這個通道不可用的時候，流程是降級、還是整個卡住？降級要明確聲明，不要悄悄跳過。

### 2. 審查者會編造證據

我遇過審查子代理編造 grep 結果當佐證，連續兩次。在 loop 中，審查者的「證據」如果沒有被獨立檢查，編造的證據會一路被帶進最終版本。這也是為什麼冷驗證要**回到原始來源**重驗載重主張，而不是信任中間的審查檔。

### 3. 預鎖的紅線要在看到內容之前寫

如果在看過候選項目之後才寫紅線，紅線就會被候選項目影響，變成「為了讓它通過而寫的標準」。順序要反過來：先寫紅線，再看候選項目。

### 4. 成本

一個完整 loop 包含多個獨立 session 與多輪審查，成本不低。我沒有保留精確的 token 數字，所以這裡不給估計；只提醒：先評估賭注，再決定要不要開。

### 5. 還沒實測的想法

下面兩個想法我沒在實際任務中測過，標為**未實測**：

- 把審查者的鏡頭，從題目中「自動產生」，而不是由我手工指定。
- 讓冷驗證的 agent，在不同輪次使用不同模型，避免它和某一組審查者同源。

## 名詞速查

| 名詞 | 意思 |
|---|---|
| 編排者（orchestrator） | 編排整個 loop 的主 session，不兼任審查者 |
| ratchet（棘輪） | 版本只進不退，每輪只收「撐得住反駁」的修改 |
| 冷驗證 | 落地前最後一關，沒看過迭代、不讀審查檔的獨立驗證 |
| 同源收斂 | 多個視角其實來自同一條推理鏈，沒有真正獨立，導致提早收斂 |
| 縫合怪（cargo-cult） | 硬把外部點子抄進來，撞到既有原則，製造內部矛盾 |
| `loop-state.md` | 持久化 loop 進度的單一檔案，讓背景喚醒或 context 壓縮後仍接得回 |

## 可直接套用的檢查清單

開 loop 之前：

- [ ] 這個決定做錯了，回收成本高嗎？不高就不要開。
- [ ] 草稿有明確、可被攻擊的立場嗎？
- [ ] 審查鏡頭彼此正交嗎？拿掉任何一個，會漏掉別人看不到的東西嗎？
- [ ] 跨模型審查者有「不引用訓練資料中的最佳實踐」這條硬約束嗎？
- [ ] 每位審查者都被要求回答「縫合怪嗎？」與「過度保守嗎？」兩題嗎？
- [ ] 編排者沒有兼任審查者嗎？
- [ ] `loop-state.md` 建好了嗎？

落地之前：

- [ ] 紅線是在看到候選項目之前寫的嗎？
- [ ] 冷驗證的 agent 沒讀過任何審查檔嗎？
- [ ] 每個載重主張都回到原始來源重驗了嗎？
- [ ] 每個採納項都有明確落點？
- [ ] 每個採納項都有至少 2 個獨立審查者背書？
