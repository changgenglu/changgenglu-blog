# GitLab Issue 驅動的 AI 自動開發（三）設計教訓與 glab 踩坑

> 本篇是三篇系列的最後一篇，整理這套「不信任 AI session」的自動開發流程裡，我覺得最值得帶走的設計決定，以及用 glab（GitLab 命令列工具）與 GitLab API 時踩到的坑。2026 年寫成。glab 的坑會標明「我自己實測過」或「他人回報／文件所載、我尚未實測」。

系列目錄：

- （一）架構
- （二）狀態機與卡單處理
- （三）設計教訓與 glab 踩坑：本篇

## 總原則：不信任 AI session

這套流程的設計出發點是：實作用的 AI session 可能犯錯、可能偷懶、可能越權，也可能被中途砍掉。所以所有「是否完成」的判斷，都由 worker（一般程式）依外部證據下，不採信 session 自己的說法。

下面每一節都是這個原則的一個具體落實。

## 一、租約加心跳

### 問題

兩台 worker 同時看到同一張待認領的單，怎麼避免重複做？worker 認領之後當機了，單怎麼不會永遠卡在「進行中」？

### 做法

把認領當成「租約」（lease）：

- 認領時貼一則認領留言，內含租約到期時間。
- 持有者每 5 分鐘**改寫同一則留言**當心跳，延長到期時間。
- 15 分鐘沒更新，其他 worker 可以回收這張單。
- 有一個清掃器，每輪輪詢順便回收過期的單，並標出「久等不回」的單。

一個小細節：**session id 在認領時先產生、先寫進留言，之後才啟動 session。** 因為如果順序反過來，session 啟動後當機，留言裡沒有 id，之後就無法續接原 session。

### 好處與限制

- 好處：不需要中央鎖服務，GitLab 留言本身就是鎖。
- 限制：時鐘要準。我讓 worker 讀自己機器的時鐘，與 GitLab 時間差超過 60 秒時啟動就印警告。所有逾時都以留言建立時間起算，不看 issue 更新時間，因為更新時間會被其他操作影響。

## 二、歷史守衛（session history guard）

### 問題

我讓 AI session 在獨立的 worktree 裡寫程式並提交。但如果 session 自己執行 `git push`、`rebase`、`reset`、`commit --amend` 或換分支，會發生什麼事？它可能改寫歷史、推出不該推的東西，或悄悄丟掉自己搞砸的提交。

### 做法

規則很簡單：**session 只准 `git add` 與 `git commit`。** 其他動作一律不准。

session 結束後，worker 檢查這段 session 產生的 git 歷史：

- 有違規動作（歷史被改寫、分支被切換等）：不推送、丟棄這些提交、標成人工處理。
- 沒有違規：才由 worker 自己推送。

推送這個動作永遠是 worker 做，不是 session 做。

### 演進軌跡

這個設計是逐步長出來的，不是一開始就想清楚的：

1. 初版：worker 在 session 結束後，把所有變更整包提交。
2. 改成：session 依 issue 的任務拆分，一個任務一筆提交（先做成選用）。
3. 再改成：修復輪也一樣，審查提出的每一項意見各自提交。
4. 守衛過了，才推送。

教訓：「整包提交」看起來省事，但事後無法知道哪個變更對應哪個任務，也無法判斷 session 有沒有偷偷做了規劃外的事。逐項提交讓審查與回溯都變容易。

## 三、被砍接力（partial handoff）

### 問題

實作 session 有時間上限（我設 45 分鐘）。時間到了被強制中止，但它已經做了一部分。這一部分怎麼辦？

### 做法

被砍時分三種情況：

1. **已有提交：** 沒提交的尾巴一律丟棄（因為不知道寫到一半的程式是什麼狀態）；已提交的部分，先貼一則標記留言，再**只推「檢查當下看到的那個 SHA」**。label 退回待認領，由下一位 worker 接手。
2. **沒有任何進度、或推送失敗：** 標成人工處理。
3. **連續被砍退回達上限（預設 5 次）：** 也標成人工處理，避免無限空轉。

下一位 worker 接手有條件：**遠端分支的頭，必須等於最新有效標記裡記的 SHA**。對不上，代表有人動過分支，不能自動接，要人處理。

### 走過的彎路

這個設計之前有一版是「逾時就把進度交接到 `wip` 分支、讓下一位繼續做」。後來我把逾時交接與續做整個移除，改成上面這版。原因是：續做半成品要處理的邊界太多（不確定上一位的工作狀態、不同 session 的脈絡不連續），簡化成「只保留已提交的、其餘丟掉」反而更可靠。

### 一個已知缺口

worker **行程本身**被殺掉（機器重開、記憶體不足被終止）時，已提交的任務還只在本機的 worktree 裡，不會自動救回。這個缺口我知道但沒補，因為發生頻率低、手動救援很容易。

## 四、信任模型

### 問題

任何人在 GitLab 上貼 label 或留言，都可能影響 worker 的行為。而且 issue 內文與測試指令，最終會在 worker 的機器上執行。

### 做法

- 只有「專案成員，且權限等級不低於門檻」的人貼的 label 與控制留言才採用。門檻預設是 Developer 等級（數值 30）。
- 取不到成員清單時，一律忽略（fail closed，預設拒絕）。

### 前提

這個模型**只適合成員都可信的私有專案**。因為內文與測試指令會被執行，等於有開單權限就有在 worker 機器上執行指令的能力。不要把它接到對外開放的專案。

### 同一精神的其他設計

「寧可不動作」貫穿整套設計：

- 成員清單取不到：拒絕。
- 列表超過分頁上限（我設 2000 筆）：拒絕動作，不是只處理前面的。
- 留言標記格式不明：拒絕，不猜。

## 五、權限白名單與環境

- 無頭 AI session 被權限擋下時，把指令加進 worker 設定裡的允許清單，並重啟 worker。
- 白名單只放行「指令本身」，如果前面加了環境變數（例如 `FOO=1 pnpm test`），會被擋。所以我把 `WORKTREE_SLUG` 改成由 worker 注入 session，不讓 session 在指令前面自己加。
- session 內的前景 `sleep` 也會被擋，等待的工作交給測試指令。
- worker 只在**啟動時**載入程式與設定檔。改了設定沒重啟，就是白改。

## 六、版本一致性基線

### 問題

每個人的機器上裝的操作手冊、worker 程式版本不一樣，怎麼辦？

### 做法

做一份「基線清單」（manifest），記錄各檔案的雜湊、必要的設定鍵名（只比名稱，不印值）、權限規則。三個時機會比對：發單時、環境檢查時、worker 啟動前。

寬嚴不同：

- 發單端：不一致就擋，不准發單。
- worker 啟動端：雜湊不同只警告，比較寬鬆。

這解決了「同一張單，在不同機器上跑出不同結果」的老問題。

## 七、測試與成本的兩條紀律

- **測試一律不啟動真的 AI session。** 我把測試改成用假的 AI 執行檔與假的通知指令，並寫了一支測試守門，一旦有測試偷偷呼叫真的，就失敗。原因是無頭 session 會花真實額度，而且結果不穩定，不適合進單元測試。
- **通知腳本預設指定最便宜的模型。** 通知腳本每次發通知，都可能開一個 AI session；沒指定模型就會用預設的最強模型，很貴。

## 八、已知限制（誠實段）

我實測的範圍比設計的範圍小。這一點在公開寫之前要講清楚：

- 真實的小模型驗收，我只實測了「正常完成」這一條路徑。
- 「被砍」與「接手」兩條路徑，只有單元測試與靜態讀程式的依據，沒有真實機器上的重現。
- 跨擁有者、多台 worker 同時競爭的整體行為，還沒驗證（我把它排在第二階段）。
- GitLab 成員權限與標籤事件的端點，只用替身（mock）測過，沒有打過真實服務。

以上全部屬於「未實測」。

## glab 與 GitLab API 踩坑

標記說明：

- 【自測】：我自己用 glab 實際跑過、重現過。
- 【他人回報／文件】：來自文件或他人回報，我還沒有實際重現，使用前請自行驗證。

### 【自測】環境變數優先於設定檔

glab 的 token 環境變數（`GITLAB_TOKEN`，以及 `GITLAB_ACCESS_TOKEN`、`OAUTH_TOKEN`）**優先於** glab 自己的設定檔。如果環境裡有一個過期的值，所有主機都會回 401，即使你已經用 `glab auth login` 登入。

除錯時：

- 不要用 `--show-token`，也不要直接印環境變數，會把憑證輸出到螢幕與紀錄。
- 暫時繞過：`env -u GITLAB_TOKEN glab ...`。

### 【自測】`--field` 會把 `[` 開頭的值當 JSON

`glab api` 的 `--field`（`-F`）參數，遇到以 `[` 或 `{` 開頭的值，會嘗試當 JSON 解析。結果是：如果留言內容以 `[claim:…]` 這種標記開頭，會被拒收，錯誤訊息像 `Error parsing "body" value`。

這與我的留言協議直接衝突，因為協議要求標記行必須是留言第一行。解法：

```bash
# 錯誤：標記開頭的內容被當成 JSON 解析
glab api projects/example%2Fapp/issues/1/notes -F "body=[claim:implement]"

# 正確：自由文字用 -f（--raw-field）
glab api projects/example%2Fapp/issues/1/notes -f "body=[claim:implement]"
```

規則：**自由文字一律用 `-f`，只有數字與布林才用 `-F`。**

### 【自測】`--raw-field key=@file` 不會讀檔

在 curl 裡 `key=@file` 表示讀檔，glab 的 `--raw-field` 不會。它會把字面字串 `@note.md` 當作內容貼出去。

```bash
# 錯誤：貼出去的是字串 "@note.md"
glab api projects/example%2Fapp/issues/1/notes -f "body=@note.md"

# 正確：先用 shell 讀進來
glab api projects/example%2Fapp/issues/1/notes -f "body=$(cat note.md)"
```

### 【他人回報／文件】帶不存在的 label 會靜默新建

第二篇已提過。API 呼叫帶了不存在的 label 名稱，不報錯，而是建立新的。防法是啟動時比對 label 清單。

### 【他人回報／文件】改 label 用增減，不要整組取代

改 label 有兩種方式：

- `add_labels` 與 `remove_labels`：伺服器端原子地增減。
- 直接 `PUT labels=...`：整組取代。

兩個程式同時改，整組取代會讓「後寫的蓋掉先寫的」。我的 worker 用增減方式。

### 【他人回報／文件】列表預設只回 20 筆

要用 `--paginate`，或自己用 `per_page=100&page=N` 並看回應標頭 `X-Next-Page`。不分頁的程式在資料量大時會默默漏資料。我的流程另設了 2000 筆的分頁上限，超過就拒絕動作。

### 【他人回報／文件】指派要用單數欄位

指派人要用 `assignee_id`（單數）。`assignee_ids[]` 據說會靜默無效，不報錯但沒效果。

### 【他人回報／文件】token 結尾換行會 401

存 token 時用 `printf '%s'`，不要用 `echo`，後者會多一個換行，導致 401。另外：

- 排程器或圖形介面啟動的程式，要自己設定 `GLAB_CONFIG_DIR`。
- 自動化程式找不到 glab，先確認 PATH。

### 【他人回報／文件】`--hostname` 的使用

- `glab api` 一律帶 `--hostname`。
- `glab issue`、`glab mr` 沒有這個旗標，改用 `-R <完整 URL>`，或固定在專案目錄執行。
- `--hostname` 要填的是網頁與 API 的網域，不是 git SSH 遠端的主機名，兩者可能不同。

### 【他人回報／文件】長內容別放命令列

描述或留言很長時，不要塞在命令列參數裡，用 `--description-file`，或 `glab api --input`。

### 【他人回報／文件】先 push 再建 MR

如果分支還沒推到遠端就建 MR，會得到 `source_branch does not exist`。我的流程偶爾會看到暫時性的發布重試留言，下一輪輪詢會自動恢復。

### 【他人回報／文件】`Closes #N` 只在預設分支生效

MR 描述寫 `Closes #1`，只有合併到**專案預設分支**時才會自動關閉 issue。如果 worker 的 MR 目標分支不是預設分支，要手動關單。

### 【他人回報／文件】權限與版本差異

- token 需要 `api` 範圍；`git push` 另需 `write_repository`。
- 社群版沒有 scoped label 互斥，也沒有 work item 的 Status 欄位（付費功能）。

## 帶得走的檢查清單

如果你也想做類似的流程，我會建議逐項確認：

- 狀態是不是只存在一個外部、可檢視的地方？
- 每個元件重啟後，能不能只靠外部狀態恢復？
- 「完成」是由外部程式依證據判斷，還是採信 AI 自己說的？
- AI session 能不能改寫 git 歷史？有沒有事後檢查？
- 認領有沒有租約、心跳、過期回收？
- 被中止的工作，只保留「已確認」的部分嗎？
- 取不到資料時，預設是拒絕還是放行？
- 測試有沒有確保不會呼叫真的 AI？
- glab 的 `-f` 與 `-F` 有沒有分清楚？

## 小結

- 不信任 AI session，是這套設計的總綱：租約處理競爭、歷史守衛處理越權、被砍接力處理中斷、信任模型處理外部輸入。
- 簡化往往比補強更可靠，被砍接力就是從「續做」簡化成「只留已提交」。
- 誠實標明實測範圍：只實測了正常路徑，其餘是「未實測」。
- glab 的坑多半是「靜默失敗」，不報錯但沒效果，所以每個動作做完都要重新讀取確認。
