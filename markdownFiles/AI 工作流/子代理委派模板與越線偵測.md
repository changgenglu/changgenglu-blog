# 子代理委派模板與越線偵測

> 把任務丟給子代理（sub-agent）時，臨場組裝的 prompt 會造成越界修改、重開已結案議題、行為不一致。本文整理我使用的標準委派模板、委派前的停止條件、prompt 膨脹的處理，以及主代理自己「越線」時的偵測方式。寫於 2026 年，以 Claude Code 為例，概念適用於任何支援子代理的 AI 開發工具。

## 問題：沒有模板的委派會怎麼壞

委派 prompt 如果每次都臨場新寫，會反覆出現三種問題。

### 問題 1：子代理越界修改

沒有明確的「可修改檔案」清單，子代理會「合理推斷」受影響範圍，可能順手改了規劃外的 helper、測試資料、甚至設定檔。驗收時主代理必須逐行比對 git diff 才發現，這不是驗收，是重新審查一次。

### 問題 2：已關閉的討論被重開

子代理不繼承對話歷史。使用者上一輪已經豁免的審查發現、已選定的架構路徑、已被否決的方案，如果沒寫進 prompt，子代理會重新提出，浪費 token，還造成混亂。實際發生過：某次審查中，使用者早已決定「這個脫敏要求豁免」，但沒前置告知，三個平行的審查子代理都有可能各自重提一遍。

### 問題 3：模型行為不一致

大、中、小模型對 prompt 結構的反應差很多。用中階模型的寫法去委派小模型，容易超出它的處理能力；對大模型省略限制語，它可能「善意地」多做幾件沒被要求的事。

標準模板是這三個問題的一次性解法：**強制填邊界、強制前置已決策項目、強制依模型調整格式。**

## 核心做法：派工三件套與六個欄位

三個核心欄：

1. **目標加動機**：一句做什麼，加一句為什麼。動機讓子代理在邊界情況做對取捨。
2. **驗收條件**：可判定、至少一條。
3. **回報格式**：回傳什麼、多長。

再加三個範圍欄，就是標準模板的六個必填欄：

| 欄位 | 必填 | 內容 |
|---|---|---|
| 任務目標加動機 | 是 | 動詞開頭一句話，再加一句理由 |
| ALLOWED_FILES | 是 | 明列可改的檔案，用明確路徑，不寫「相關檔案」 |
| FORBIDDEN_ACTIONS | 是 | 反向邊界：不改範圍外、不刪測試、不全域格式化、不用破壞性 git 指令 |
| 驗收條件 | 是 | 「指令加預期輸出」，或「檔案加必含內容」 |
| OUTPUT | 是 | 報告落檔的位置，避免子代理自選路徑或根本不寫 |
| 回報格式 | 是 | 回傳行數上限、狀態碼 |
| 參考範本、驗證指令 | 建議 | 「仿照 X 的風格」「完成後跑 Y」 |

兩個關鍵細節：

- **ALLOWED_FILES 必須是明確路徑清單。** 「受影響的 Service 層」這種模糊說法，等於把邊界判斷責任丟給子代理，等於沒有邊界。
- **驗收條件不可以是「品質良好」。** 不能判定的句子，等於沒寫。

### 一個填好的範例

```text
## 前輪決策（放在最前面）
- 已選定：快取放在 Service 內，不新增獨立類別
- 已豁免：request middleware 的欄位脫敏，不要再提
- 已試過失敗：用 DB 觸發器做（效能不可接受）

## 任務
新增 OrderService::getFrozenAmount()，回傳使用者凍結中的金額。
動機：結算頁需要顯示可用餘額，目前缺這個值。

ALLOWED_FILES:
- app/Services/OrderService.php
- tests/Unit/OrderServiceTest.php

FORBIDDEN_ACTIONS:
- 不重構其他方法、不全域格式化、不碰 ALLOWED_FILES 以外的檔案

驗收:
- php artisan test --filter=OrderServiceTest 全數通過
- grep -c "function getFrozenAmount" app/Services/OrderService.php 輸出 1

OUTPUT: reports/impl-frozen-amount.md
回報: 結論 10 行內 + 證據（檔案:行號）+ 狀態碼（DONE / PARTIAL / BLOCKED / ESCALATE）
```

### 設計原則：前輪決策放 prompt 前三分之一

長 prompt 的後段，更容易在多步工具呼叫之後被忽略。我引用過一篇關於長 context 的研究（arXiv 2307.03172，"Lost in the Middle"）：中段內容的遵循率明顯低於開頭與結尾。數字我只照原文轉述，沒有在自己的環境重現，所以請當作「方向正確」的參考。

因此「前輪決策摘要」放在任務描述**之前**，分四項：

- 技術選型
- 架構選擇
- 已確認的約束與豁免項目
- 已試過但失敗的方案

這不只是「提醒」，而是讓已決策事項變成子代理整個任務過程的背景條件。

## 回報合約：避免把子代理的報告全文倒回主 context

- 回傳進主 context 的部分**不超過 30 行**：結論（10 行內）加證據（檔案與行號）加狀態碼。
- 長產物（報告全文、diff、log、超過 30 筆的清單）落檔，只回傳路徑與 3 行摘要。
- 超過限制就是違約：不讀全文，要求它落檔重回。
- 驗證類的委派，要求逐條格式：

```text
CLAIM: <宣稱> | EVIDENCE: <驗證指令與關鍵輸出> | STATUS: VERIFIED / FAILED / UNVERIFIED
FINAL: <整體判定加一句摘要>
```

沒有實際跑過的推論，一律標 `UNVERIFIED`。

## 委派前五項停止條件

在把任務丟出去之前，先確認這件事不該由子代理自行決定。命中任何一條，就停下來回報使用者，不自行委派：

1. 即將刪除檔案（migration、entity、測試、設定）。
2. 即將整合新的外部服務或 API（新依賴、第三方、MCP）。
3. 發現兩條合理的架構路徑（取捨影響架構方向）。
4. 同一個錯誤嘗試兩種不同方案仍失敗。
5. 任務需要超出範圍合約的變更。

這是「事件」層的主動防線；另一個「次數」層的防線是工具呼叫上限（Hard Cap）。兩者不同：前者管「這件事該不該決定」，後者管「做太多次了」。

## 重派的升降級路徑

子代理失敗後，不要「同模型、同 prompt 盲試第 N 次」。

1. 小模型失敗 1 次：升中階模型重派，prompt 不變。只改參數重試小模型，不算修復。
2. 中階模型失敗第 1 次：可同級重派一次，但要**先減後加**地改 prompt。累計失敗 2 次：升大模型，prompt 附**完整失敗軌跡**（每次的 prompt 摘要、產出摘要、驗收失敗點各一行）。
3. 升級輪仍失敗：停下來，回報使用者並附全部失敗軌跡，不開第 3 輪。
4. 降級：同一種解法連續 2 次在同型子任務通過驗收，後續同型任務降回中階（純機械套用降到小模型）批次執行，prompt 附已驗證的解法當範本。

反例：小模型漏了 2 個項目，改寫 prompt 再派小模型三次。能力不足時改 prompt 是白費輪次。

## Prompt 膨脹：為什麼越補越長反而更差

我曾經有三次連續的規劃委派全部失敗。prompt 長度分別是約 2500、530、1500 字元，第三次膨脹到 20 層標題。每一次失敗，我都加一段「這次要特別注意…」，結果 prompt 越來越長、越來越雜亂，成功率沒有上升。

根因分析（我當時整理的結論）：

- **提示詞型的硬閘門不可靠。** 在長 prompt 與多步工具使用下，越後面的指令越容易被忽略。
- **想用「DRY」把規則全部搬到別處，也是反模式。** 儲存可以 DRY（規則只存一份），但**執行時必須重複**（委派 prompt 要帶上必要規則），否則子代理根本看不到。
- 我的做法是「儲存一份、執行重複」兩層設計，並且對失敗採取「**先減後加**」的反射：失敗後先比較各次 prompt 的差異、找共同因子、**先刪不必要的內容**，再考慮補什麼，最後反問自己「失敗是不是來自我沒講清楚的目標」。

幾條實用規則：

- 委派 prompt **不寫變更理由**。例如「X 已經改成 Y」這種新舊對照句，子代理讀不到舊版，只會把這句抄進產物，造成擴散。只寫現行要求。
- 中階模型的 prompt 建議不超過約 1500 字，超過容易偏題。
- 委派前先做「合約檢視」：讀目標子代理的定義檔，列出它**已規範**的約束，prompt 只寫**未規範**的部分，避免重複與矛盾。

> 以上字數為我的經驗值，沒有嚴格量測。

## 另一個陷阱：思考類 skill 的輸出被當成交付物

有一類 skill 的輸出長得像完整交付物，例如會吐出風險清單、信心分數、決策矩陣的批判性思考工具。被委派的規劃子代理，容易把這個輸出當成「已完成的主報告」直接回傳，跳過真正的寫檔步驟。

我踩到連續 3 次：規劃子代理呼叫批判工具後，把一千五百字的自審當成最終回傳，但磁碟上規定的報告根本沒被寫出。第 3 次時，我在 prompt 結尾已加了最重的警告，仍然發生。結論：**提示詞層的強化無效**。

修法有兩條：

1. **skill 端**：去掉「完整交付物」的外觀，讓輸出看起來就是中間資料。
2. **流程端**：把批判拆成另一個獨立的子代理，並規定「**以 Edit 落地為完成**」。批判分析是中間過程，只能透過 Edit 寫進報告既有章節，不寫在回覆文字裡；而且無論有沒有新發現，都必須遞增版號，這是唯一允許「沒新發現也算完成」的出口。

可類推的判斷標準：**主代理拿到這個 skill 的輸出時，是否可能誤以為任務完成了？** 如果會，就需要「交付定義綁定檔案變更」這類約束。

另外，批判類應該落地的子代理，派完之後用 `git diff --stat <檔>` 確認真的有變更；無變更就是空轉，重派一次仍空轉就停下來回報。

## 越線偵測：主代理自己的紀律

前面都在講子代理，但主代理自己也會越線：明明命中委派門檻，卻自己下場。

### 事件

主代理親手重寫一個 549 行的服務檔，又改了 9 處 Controller、整檔重寫一個測試輔助類別、新增單元測試。它的推理過程顯示它**清楚知道**門檻已命中，仍以「我掌握最深、委派溝通成本高」為由自己做。

### 為什麼規則失守

兩個原因疊加：

1. 措辭給了自我說服的空間（「優先但非自動」）。
2. 違規沒有即時的偵測，防線只有「主代理自律」這個單點。

### 處置：三層

| 層 | 做法 | 備註 |
|---|---|---|
| 文字層 | 「越線前明示」：任務中第一次對程式碼檔 Edit 或 Write 之前，若已命中門檻，先寫「命中哪條、為何不委派」並停下來等回應。**沒有自授例外** | 觸發綁在「可觀察的動作」上，不是「思考中有沒有權衡」 |
| 記帳層 | hook 即時記錄主代理對程式碼檔的寫入 | 只記不擋 |
| 審計層 | 事後稽核量測 transcript 實際規模，違規自動開卡進入處理流程 | 抓門檻低估與範圍蔓延 |

最強的一層是 **PreToolUse hook 硬擋**（偵測主代理對程式碼檔的 Edit/Write 加門檻，動手前攔截）。它的優先序後來被我主動降低，原因是 hook 屬安全層，較大的變更我選擇先留提案、等使用者另行核可。

### 「只記帳，不執法」的陷阱

還有一次類似的教訓：工具呼叫次數上限（Hard Cap）的記帳器上線了，累積了三萬多行紀錄，但**執法分支從來沒寫**，開關固定為關。紀錄顯示三次逾額（檔案數與工具呼叫數都超過合約，其中一次超出一倍），全程沒有停下來。

教訓：

- **只記帳不執法，等於軟性宣告。**
- 卡片自己訂的「第二階段分析觸發條件」早就滿足，但沒人看，卡片就失效了。我後來的做法是：卡片隔一段時間要做「現況覆核」，條件已滿足就拉回待辦池，不要留在「進行中」裝作有人在推。
- 上限值本身也要校準。兩個子代理各跑了 87 與 85 次，既可能是嚴重超支，也可能是上限訂得不切實際；沒有量測，這兩種解讀的修法相反。所以先記帳、累積資料，再決定要不要擋。
- 一個記錄上的補充：當初知識庫寫「Agent 與 Task 工具不會觸發 hook」，依據是 2026 年 4 月的實測。後來重新測，這個結論已經過期，hook 可以接在子代理呼叫前後。**寫進規則或知識庫的「平台限制」，要有複測日期，並定期重驗。**

### 唯讀分析型越線

前面兩種偵測都看「寫」。但還有一種越線：主代理跨 3 個檔案讀碼診斷、產出完整的方案比較，一行都沒寫。我評估讀取計數（誤判率高，因為讀 3 個檔是日常）與輸出內容偵測（需要語意判斷，hook 拿不到回覆內容）之後，採取最保守的方向：**只記錄，不設門檻**。累積一到兩個月的真實分布，再決定要不要加提醒。

## 可直接套用的檢查清單

委派前：

- [ ] 六個必填欄都填了嗎？ALLOWED_FILES 是明確路徑嗎？
- [ ] 驗收條件可以用「指令加預期輸出」判定嗎？
- [ ] 前輪決策（選型、架構、豁免、失敗方案）放在 prompt 最前面了嗎？
- [ ] 有沒有寫「X 改成 Y」之類的變更理由？有就刪掉。
- [ ] 五項停止條件有命中嗎？
- [ ] 要不要看目標子代理的定義檔，只寫它沒規範的部分？

回報後：

- [ ] 回傳超過 30 行嗎？超過就要求落檔重回。
- [ ] 它宣稱寫過檔，我有 `grep -c` 或 `wc -l` 驗收嗎？
- [ ] 失敗要重派時，我是升級了模型，還是在同一個模型盲試？
- [ ] 批判類子代理，有 `git diff --stat` 確認真的改了檔嗎？

主代理自己：

- [ ] 我要對程式碼檔動第一次 Edit 前，有沒有先寫「命中哪條、為何不委派」？
