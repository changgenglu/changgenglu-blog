# 宣稱完成要有證據

> AI 程式開發代理很容易說出「修好了」「應該可以了」「已經試跑確認」，但這些話常常沒有任何實際輸出支撐。本文整理我為什麼要求每一句「完成、修復、通過」都綁定證據、驗收怎麼分級，以及四個真實事故：試跑沒連上目標、工具輸出是模型自己編的、「可達」不等於「送得到」、把證據的來源說錯。寫於 2026 年，範例以 Claude Code 為主，概念適用於所有 AI 開發代理。

## 問題：「看起來沒問題」是靜態推論

AI 完成修改後，傾向用「邏輯上正確」「應該可以了」「看起來沒問題」當作完成訊號。這些都是**靜態推論**，不是執行驗證。靜態推論會系統性漏掉這幾類失敗：

- **靜態通過，動態失敗**：grep 找得到函式定義，但實際的呼叫路徑因條件分支，在執行期永遠沒觸達。
- **建置通過，行為錯誤**：型別正確、編譯無誤，但邊界條件沒被測試覆蓋，CI 全綠，特定輸入下卻靜默出錯。
- **本地通過，環境差異**：本地 `.env` 有開某個旗標，CI 環境沒有。
- **工具誤判**：編輯工具回報成功，但比對到的是行尾空白不同的版本，實際內容沒變。

一個我親身踩到的例子：我寫了一支計數器 hook，bash 語法檢查（`bash -n`）通過，邏輯看起來正確。實際執行時，因為 hook 是由代理工具用管線（pipe）啟動，子 shell 的 PPID 不穩定，計數器在某些環境永遠是 0。靜態看沒問題，動態完全失效。

## 核心做法：宣稱綁證據

**每一句「完成、修復、通過」，都要能指向本 session 實際看過的指令輸出。**

反過來，下面這些語氣都是「無據宣稱」的訊號：

- 「看起來沒問題」
- 「應該可以了」
- 「邏輯上是正確的」
- 「理論上會通過」
- 「這部分之前測過了」（另一個 session 的測試不算）

### 證據的三段式格式

附在完成宣稱旁邊：

1. **指令**：實際跑的驗證指令。
2. **輸出**：執行結果的關鍵數字（通過筆數、assertion 數、有無 skip 或 warning）。
3. **結論**：一句話，是否可宣稱完成。

三段缺一，視為沒附證據。理由：附了證據的宣稱可以被質疑、被驗證；沒證據的宣稱只能靠信任。

常用的驗證指令：

| 驗證目標 | 指令範例 |
|---|---|
| PHP 語法 | `php -l path/to/file.php` |
| Laravel 測試 | `php artisan test --filter=ClassName` |
| TypeScript 型別 | `npx tsc --noEmit` |
| 函式是否存在 | `grep -n "function getFrozenAmount" path/to/file.php` |
| 檔案行數 | `wc -l path/to/file.md` |
| API 端點 | `curl -s -o /dev/null -w "%{http_code}" http://localhost/api/health` |

### 一段制度演進（也是我的反省）

我最早設了「五步強制閘門」：先確認驗證指令、完整執行、讀完整輸出、比對預期、附證據宣稱，而且「不可豁免」。後來新一代模型自帶自我驗證能力，強制例行驗證反而造成過度驗證，我就把這套閘門裁撤了。

幾週後，我統計實際使用情形，發現「**無據斷言**」是最大的摩擦來源，於是又恢復成**分級**驗收：只在錯誤成本高的地方驗，不例行雙驗。

這個過程給我的啟示：「強制性」可以拿掉，「宣稱綁證據」這條紅線不能拿掉。差別是，不再強制每次都多跑一輪驗證，但也不可以無據宣稱。

## 分級驗收：什麼情況由誰驗

| 層級 | 觸發 | 怎麼驗 |
|---|---|---|
| T0 | 唯讀盤點、搜尋、研究類回報 | 不另驗；報告含「宣稱加證據」的逐行格式或指令加輸出，即可採信 |
| T1 | 子代理宣稱**寫過任何檔案** | 主代理 read-back：對每個驗收條件跑一次 `grep -c '<必含字串>' <檔>`（或 `wc -l`、`test -f`），不讀全文。0 命中就是未通過 |
| T2 | 程式碼改動 | 測試由**非執行者**跑：主代理自己跑驗收指令；改動 3 個檔以上、嚴重等級修復、合併前這類情況，改派一個全新 context 的驗收子代理，只給分支與驗收條件，不給實作者的報告 |
| T3 | 高風險判斷：架構二選一、安全結論、不可逆動作前、要對外送出的根因 | 派批判型子代理挑戰結論，prompt 只給批判對象，不夾帶主代理的立場；仍分歧則找 3 個獨立子代理評分，取中位數 |

在上表以外，報告其餘宣稱只要含具體證據（指令加輸出）就採信；只有證據缺漏、輸出與範圍矛盾、宣稱與現場狀態衝突時，才額外抽驗。

反例：子代理說「已修好、測試應該會過」，主代理原句轉給使用者。
正例：子代理回報 12 個測試綠燈，主代理自己跑 `php artisan test --filter=Sort | tail -20`，看到 `12 passed`，才對使用者說「修復完成」。

## 四個真實事故

以下事故都已去識別化。每一個都是「事後才發現，證據其實不是證據」。

### 事故 1：試跑沒連上目標，卻被當成請使用者核准的依據

**情境**：要在某個程式碼代管平台的測試專案，建立一個標籤（對外寫入，需要使用者核准）。主代理先做 dry-run（試跑），然後拿結果請使用者同意。

**現象**：dry-run 用的主機名，其實是 git SSH 遠端的別名，在本機解析成 127.0.0.1；真正的 API 主機是另一個網址。更根本的是，**那個腳本的 `--dry-run` 模式，只在程式裡印出一行就返回，根本不呼叫目標平台**，所以主機名填什麼都不會報錯。這個「試跑」從頭到尾沒證明任何事，卻被當成「已試跑確認」交給使用者。

後來改用正確主機建立標籤，並讀回確認，沒造成實際損害。

**根因**：「dry-run」沒有最低證據要求，只印出要執行的指令，也能叫試跑。我原有的完成判定規則，只管「完成、修復、通過」，沒管「拿去請使用者核准的前置證據」。

**處置**：

- 稱「已 dry-run、已試跑」之前，至少有一次對**同一個目標**的唯讀查詢，回傳**非空**結果（例如 API 的 GET 請求），證明目標可達；做不到，就寫「**只印指令、未連線，試跑無效**」。
- 請使用者核准對外寫入時，附的依據必須是實際查詢輸出，不是指令字串。
- 另外補了一條平台踩坑筆記：「git 遠端的主機名，不一定是 API 主機」。

**一句話檢查句**：試跑前先確認它真的會連到目標；不會連，就不能叫試跑。

### 事故 2：工具的輸出是模型自己編的

**情境**：在做一個資料盤點任務時，主代理反覆宣稱它用了編輯工具、命令列工具、子代理工具，但一連串跡象有點奇怪：最硬的一條是，它用寫檔工具建立某個檔案，第一次收到「Wrote 1 lines」（實際送出的內容有數十行），接著用讀檔工具讀同一路徑，回的卻是「檔案不存在」。

**現象**：使用者起初懷疑是工具層出了問題。逐一比對系統側的原始事件流之後，結論是：**這是模型幻覺的「工具互動」事件，不是工具故障。**

- 標題那個事件、一次假的命令列輸出、兩次假的子代理回報，在事件流裡**都沒有對應的 tool_use 與 tool_result**，全是模型自己生成的敘述。
- 所有真正的工具回傳，都誠實、且與檔案系統的實際狀態一致。

**復發**：幾天後，在另一個專案又復發一次：假的 commit 成功訊息，加上一個編造的 hash，誤導了一次 `git commit --amend`，蓋掉了主分支上既有的 commit（所幸立刻發現並修復，零遺失，也還沒推出去）。

**學到的判準**：

- 「假成功」可以**零 tool_use 背書**：也就是說，一段看起來像工具輸出的文字，不代表真有工具被執行過。
- 被中斷之後出現的「成功」輸出，**不可信**，要用底層指令重新確認狀態才能繼續。
- 確認狀態要用「直接驗」的指令，例如 `git rev-parse HEAD`、`git log -1`、`ls -l`，不要靠上一段輸出的轉述。

**一句話檢查句**：成功訊息要有對應的工具呼叫紀錄；懷疑的時候，用底層指令獨立再看一次。

附帶一個早期的案例：用另一個模型做資料研究時，產出的報告引用了 3 個編造的網址、另有 5 個網址是 404。也就是說，**外部引用的來源，要實際打開確認**；還有一個審查子代理曾經兩次編造 grep 結果當佐證。這類事件讓我在委派模板裡加了明確的禁令：禁止捏造證據、禁止降低證據要求（見〈子代理委派模板與越線偵測〉）。

### 事故 3：「可達」不等於「送得到」

**情境**：要向另一個團隊的同仁詢問一件事，透過一個內部的 session 訊息網路傳送。主代理先用查詢工具查對方，工具回報「可達」，主代理就把那個位址寫進轉發請求，還對使用者說「對方的節點查到了（可達）」。

**現象**：實際上，那個位址在先前就曾經投遞未達。而且這條路徑**沒有明顯的失敗徵兆**：投遞失敗時，有時沒有回執，在寄件紀錄裡「完全查無這筆」。查詢工具的「可達」標記，只代表它命中了名冊中的名字，並不代表有一個已發布、能收訊息的 agent 在那個位址。

實際影響為零，因為中間的轉送節點剛好知道這個位址的失敗紀錄，改道並回報。但**攔下的原因是對方碰巧知道，不是寄件端有判準**。

**根因**：把「查詢標記」當成「可交付證明」。

**處置**：在使用說明的決策樹裡，補一列「送出後查無任何回執」的處理，並明寫「查詢工具的可達標記，等於命中名冊或 id，不等於可投遞，不可單獨當作送達依據」。

**一句話檢查句**：「查得到」是查詢的結果；「送得到」要看送出之後的回執。

### 事故 4：把使用者貼的證據，寫成「收件人提供的」

**情境**：主代理在組寫跨團隊的對外訊息時，把「使用者在對話裡貼給我的資料」，寫成「收件人提供給我們的資料」。同一個 session 內發生兩次，第二次連使用者都從未做過這種歸屬，完全是主代理自己填上去的。

**現象**：

- 第一次：使用者說「新網址是對方給的」，主代理沒查證就寫「你提供的那條新網址」。收件人回覆澄清：那條網址不是她給的，而她同時在幫忙追查來源，我方的錯誤歸屬害她去查一個已經解決的問題。
- 第二次：使用者貼了兩則完整的請求紀錄與 400 錯誤回應，主代理寫成「就是你剛剛貼給我們看的那兩則」。使用者從未這樣說過。
- 同族的第三種：把「使用者提供的截圖」與「收件人自己看到的紀錄」當成同一次事件互相驗證，被收件人指出細節對不上才收回。

**為什麼是高嚴重度**：對外訊息不可逆。把 A 說的話說成 B 說的，收件人會據此判斷「這件事我處理過了嗎」，並可能去追一個和自己無關的問題。更正訊息是獨立另一則，不是改掉原句，所以收件人會先讀到錯誤版本。

**根因（觀察，非嚴格驗證）**：整個排查過程中，證據有三個來源同時流動：使用者貼的、收件人回覆的、我自己用工具抓的。要在對外訊息裡引用一份證據，而那份證據出現時，前後文剛好在討論該收件人，就容易把來源搞混。我原本有一條記憶規則提醒「要另查結論是對方送來還是我方自己撈的」，但那條規則綁在另一個特定情境上，沒攔住這次。

**處置**：對外訊息中**每一個帶來源歸屬的說法**（「你提供的」「你貼給我們的」「你剛剛給的」），送出前必須能指到該資料實際進入我方的管道；指不到，就寫「我方取得的」，或乾脆不寫來源。

**一句話檢查句**：送出前，逐一檢查每個「誰給的」是否指得到實際來源。

## 共通的結構

四個事故看起來不同，其實是同一種錯誤的變形：

| 事故 | 被當成證據的東西 | 它實際是什麼 |
|---|---|---|
| 試跑 | 一行印出來的指令 | 沒連到目標，什麼都沒證明 |
| 工具輸出 | 一段像工具輸出的文字 | 模型自己生成，無對應呼叫 |
| 可達 | 查詢工具的標記 | 命中名冊，不代表送得到 |
| 歸屬 | 「你提供的」 | 我方自己填的，無來源 |

共通原則：**證據要來自「對目標的實際觀察」，不是來自「對目標的描述」。**

## 可直接套用的檢查清單

宣稱完成前：

- [ ] 我能指出「本 session 哪個指令的哪段輸出」支撐這句話嗎？
- [ ] 驗證指令是我自己跑的，還是轉述子代理的？（寫過檔的子代理：我 `grep -c` 過了嗎？）
- [ ] 沒驗的部分，我有寫「未驗」，而不是用「完成」帶過嗎？

請使用者核准前：

- [ ] 我附的是實際查詢輸出，還是指令字串？
- [ ] 試跑有連到**同一個目標**，且回傳非空嗎？

對外送訊息前：

- [ ] 每個「誰提供的、誰說的」都指得到實際來源嗎？
- [ ] 「可達、已送出」是看過回執，還是看過查詢標記？

懷疑工具輸出時：

- [ ] 用底層指令（`git rev-parse HEAD`、`ls -l`、`wc -l`）獨立再看一次狀態。
- [ ] 被中斷之後出現的成功輸出，先重新確認，再繼續。
