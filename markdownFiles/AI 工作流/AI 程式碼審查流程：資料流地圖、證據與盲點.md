# AI 程式碼審查流程：資料流地圖、證據與盲點

> 讓 AI 代理審查程式碼，最容易出的兩種問題是：掃描式誤判（看到可疑點就喊最嚴重）與盲點（流程全綠，上線後才出事）。本文整理我用的分級審查、先畫資料流地圖再審、嚴重發現附證據的做法，以及一次「完整審查零嚴重問題、三個問題卻漏網」的事故復盤。寫於 2026 年，範例以 Claude Code 為主，審查的概念不綁定特定工具。

## 問題：兩種失衡

如果所有變更都用同一套審查流程，會有兩種失衡：

- **小改動被過度審查**：改一個錯字或參數名稱，也要跑完整的多通道審查，等待時間遠超過修改本身，審出來大概也只是幾份「沒什麼問題」的報告。
- **大改動審查不足**：一個跨 Controller、Service、Repository、Migration 的新功能，如果只讓一個審查者快速掃一遍，很容易漏掉跨層的資料流問題。例如 Controller 怎麼把參數傳給 Service，Service 在快取失效後有沒有回頭查資料庫。這類問題要追完整呼叫路徑才看得到。

另外還有一種更隱蔽的失敗：**審查流程本身通過了，但問題在審查看不到的地方。** 下面的事故復盤會講。

## 核心做法

三個機制，各自對應一種審查失敗：

1. **分級審查**：依修改規模與風險決定投入多少。
2. **先畫資料流地圖（Pass 1），再平行審查**：所有審查者從同一份路徑圖出發。
3. **嚴重發現附證據**：最嚴重的發現（P0、P1）必須附上完整證據，缺了就降級。

再加上第四層，也是最後一層：**主代理自己驗證每個 P0**，不可委派。

### 分級：Lite、Standard、Deep

| 等級 | 適用 | 審查者 | 資料流地圖 |
|---|---|---|---|
| Lite | 小任務；或 3 個檔案以內且耦合度不超過 1 | 單一主審 | 不做 |
| Standard | 一般情況，或有跨層互動 | 4 個通道平行（安全語意、結構語意、異模型反證、執行驗證） | 做 |
| Deep | 高風險（安全、金流）或跨多層架構變更 | 6 個通道平行（Standard 的 4 個加上架構、效能） | 做，用更強的設定 |

**Lite 的兩個條件要同時滿足**：檔案數 3 個以內，且耦合度不超過 1。耦合度的判斷是：修改是否跨越 Controller、Service、Repository、Model 任意兩層？跨了就不適用 Lite。為什麼加這個條件？因為一個檔案的修改也可能跨層（例如一個 Service 同時包了業務邏輯與資料庫操作），這種修改即使只有一個檔案，也需要資料流地圖才能正確分析。

**規模縮放要聲明**：Deep 或 Standard 命中，但變更很小（diff 在 50 行內、2 個檔案以內）時，維度覆蓋不砍，但執行縮編：地圖改由主代理自己畫，外部模型審查省略並在報告聲明偏離，審查者縮成雙審。**縮編一律要聲明，不能悄悄跳過。** 其中「品質維度」不可省，因為我遇過一個邊界 bug 只被風格維度抓到。

### 為什麼我廢除了「工具呼叫次數上限」

早期我對審查代理設定「最多 60 次工具呼叫」。後來廢除了，原因是**次數是錯誤的計量單位**：一次讀檔，與一次請外部模型做大範圍資料流分析，token 成本可以差到 100 倍，但次數上限把它們當成一樣。用次數管品質，會在「便宜的操作用完」時被迫停止，而不是「充分的審查完成」時才停止。

取代它的是四層結構性的品質保障（每層針對一種具體的審查失敗）：

| 層 | 機制 | 針對什麼失敗 |
|---|---|---|
| 1 | Pass 1 資料流地圖 | 多個審查者各自追呼叫路徑，結果不一致、重複工作 |
| 2 | 發現的證據要求 | 缺乏根因定位與反證的掃描式誤判 |
| 3 | 主審過濾（Judge） | 平行審查者廣播式過度標高嚴重度，雜訊太多 |
| 4 | 主代理驗證每個 P0 | 最後防線，回報使用者前自己驗，不因時間壓力豁免 |

## Pass 1：資料流地圖

### 為什麼要先畫

如果讓 6 個審查者各自從零追蹤呼叫路徑，會出現兩個問題：

- **重複工作且版本不一致**：6 個人產出 6 個版本的呼叫路徑，主審合併時要先花時間確認「你們說的是同一條嗎」。
- **孤立節點誤判**：只看單一函式，容易得出錯誤結論。例如「這個函式沒有資料庫補查」就標最嚴重，但實際上上游的呼叫端已經有補查邏輯了。

Pass 1 集中跑一次，產出一份 `data-flow-map.md`，所有審查者從這份地圖出發，主審合併時也能用路徑編號（例如 `DF-003`）索引，而不是靠描述性文字猜「這兩個人說的是同一件事嗎」。

### 只畫地圖，不下結論

這是刻意的設計。如果 Pass 1 就下結論，結論會變成「背景知識」，污染後面審查者的判斷，讓他們傾向確認 Pass 1 的說法，而不是獨立分析。Pass 1 只提供地圖，哪條路徑有問題由審查者自己判斷。

### 地圖必要的段落

缺任何一段，不能啟動平行審查：

| 段落 | 內容 |
|---|---|
| 端點清單 | 每個 API 端點或入口函式與 HTTP 方法（排程類要包含實際的啟動指令字串） |
| 呼叫鏈 | 入口 → Service 方法 → 外部副作用（資料庫、快取、網路、佇列），**標到「檔案:行號」** |
| 跨邊界傳遞點 | 資料跨越進程、序列化、輸入解析邊界的地方（字串拼成 shell 參數、HTTP 查詢字串轉型別、佇列 payload 反序列化、環境變數插值），**記「展開後的實際值」，禁止只記 `{placeholder}` 的模板形式** |
| 狀態轉換點 | 有狀態寫入的節點 |
| 分支點 | 條件判斷導致路徑分叉的位置 |
| 風險路徑標記 | 金流、冪等、併發、錯誤傳遞相關路徑用「高風險」標示 |
| 驗證問題清單 | 給審查者的疑問清單，不是結論 |

**跨邊界傳遞點特別重要**：「展開後的實際值」這個要求，是因為很多注入或格式問題，只在模板被實際展開之後才看得到。

### 完成條件

1. 地圖檔存在於約定的任務目錄。
2. 必要段落齊全。
3. 每條呼叫鏈都標到「檔案:行號」（不接受「大約在某方法裡」）。
4. 至少一條路徑標為高風險（如果沒有，要明確說明理由）。

主代理收到後，快速確認段落完整，再並行派出審查者。

### 用哪個模型畫地圖

地圖需要一次讀完整個變更範圍並追蹤跨檔案呼叫鏈，我的設計是用長 context 的模型（例如 Gemini）一次讀完幾十個檔案；若這條路徑不可用，才降級由 Claude 子代理自製，並**明記降級**（不悄悄換）。

不過地圖畫得快，不代表畫得對：我在一次審查中，地圖階段把一處「沒有鎖」寫錯了，是後面的執行驗證通道推翻的。所以地圖是假設的起點，不是事實。

## 嚴重發現的證據要求

### 掃描式審查的問題

審查者看到一個可疑函式或條件，直接標最嚴重，沒追完整路徑，也沒確認有沒有其他攔截機制。

真實案例（已去識別化）：三個審查者同時把某個查詢函式標為最嚴重，理由是「沒有資料庫補查，快取失效後可能重複扣款」。理由乍看很充分：快取的存活時間，與外部系統的重試窗口之間，確實有空隙。

實際上：入口端點在快取未命中後，會直接去查子表，這個查詢函式**不是唯一防線**。三個審查者都沒追入口端點的完整呼叫鏈，只從這個函式往下看，忽略了上游已有補查。

### 證據欄位

所有 P0 與 P1 必須附以下證據，**缺任何一項，自動降為 Question 或 P2**：

| # | 名稱 | 要求 |
|---|---|---|
| 1 | 根因位置 | `檔案:行號` 精確定位，加完整呼叫鏈 |
| 2 | 路徑引用 | 地圖中的路徑編號（Lite 沒有地圖，就引實際呼叫鏈） |
| 3 | 具體陳述 | 禁止「可能導致」「應該考慮」，改用「觀察到 X（事實），因為 Y（佐證），導致 Z（影響）」三段式；關於呼叫鏈或常數值的聲明，要附實際執行過的指令與輸出 |
| 4 | 反證嘗試 | 窮舉候選的攔截機制，逐一說明為何在此情境失效 |
| 5 | 信心與邊界 | 0–100 的信心分數，加上「無法確認的邊界」（沒有就寫「無」） |
| 6 | 發生機率（前例） | 這類問題有沒有前例？有或無都要查證留痕 |

第 6 項是後來加的，原因是我發現審查找出來的問題，很多是「低機率、低風險」卻被標成必修，使用者被淹沒。

### 反證嘗試要涵蓋的四類機制

- **上游驗證**：middleware、DTO validator、hash 檢查。
- **冪等保護**：快取、資料庫唯一約束、狀態機。
- **下游 fallback**：資料庫補查、補救路徑、錯誤處理。
- **外部約束**：資料庫 constraint、外部 API 的行為保證。

實際寫法是逐一列出候選、標記是否失效並附查證依據，再收斂到結論。三層全部確認失效，才算真正的 P0；如果發現有任何一個機制有效，就要降級（不是問題消失，而是嚴重度不到那一級）。

### 為什麼要「反證」而不只是「根因位置」

根因位置只說明「問題在哪」，但真正決定嚴重度的是「有沒有別的機制可以攔截」。強迫審查者在標 P0 之前，**主動嘗試反駁自己**，就是對治掃描式誤判的結構性矯正。

### 路徑引用的實質作用

審查者標了 P0 卻填不出路徑編號，通常表示這個發現不是從路徑圖追出來的，而是掃描式得出的結論。這時主審可以要求補充，或直接降為 Question。

### 主審的過濾（Judge）

平行審查者的策略是「廣播型」：儘量找，寧多勿少。這是對的，漏掉真正的 P0 比誤標更嚴重。但如果沒有過濾層，最終報告會充滿「看起來有問題、實際沒問題」的發現。

主審（Judge）對每個發現評估：

- 根因可定位（`檔案:行號` 真的能找到）。
- 路徑圖一致（編號對得上，描述一致）。
- 反證有嘗試（四類機制都討論了）。
- 三段式陳述。

任何一項不合格就降級。**每個 P0 必須對應地圖上至少一條路徑**；沒標風險路徑卻被標 P0 的，主審必須獨立驗證。

## 事故復盤：完整審查，零 P0，三個問題漏網

### 經過

一個功能任務，從規劃、實作（測試先行）、到標準審查（地圖、六個角度平行審查、主審合併與過濾）完整走了一遍。首輪判「需要修」（7 項 P1），逐項修復後，最終審查判**通過，86 分，0 個 P0，0 個 P1 殘留**。

結果：三個問題全部通過審查。

| # | 問題 | 審查有攔下嗎 | 實際後果 |
|---|---|---|---|
| 1 | 一個「退化守衛」把某個**導出值欄位**也納入「只會變大」的假設，大額事件一發生就誤判為資料退化、整列永久拒寫 | 沒有，六個角度都沒提；是被對方 repo 擁有者的 code review 攔下 | 修正沒及時併入，正式環境跑了 21 分鐘，一列資料被凍結 245 次 |
| 2 | ORM 的 upsert 在 MySQL 的回填路徑拋錯（INSERT 已提交之後才拋）| 沒有 | 43 分鐘內約 500 筆錯誤，每輪一次假失敗，會掩蓋日後真正的寫入失敗 |
| 3 | 還沒上線的站台，仍每 10 秒被抓取，空回應告警每輪觸發 | 沒有 | 43 分鐘內 557 筆告警，全部同一站台，原本用來抓真異常的告警被淹沒 |

### 後來釐清的根因

這三件事，**靜態讀程式碼很難看出來**：

1. **欄位語意**：那個欄位其實是「導出值」（等於另兩個欄位相減），會因事件而下降。這個語意在專案的業務紅線文件裡有明確記載，但六份審查報告中，只有一份引用過領域文件。**審查者沒有讀到、也沒被要求對照領域文件。**
2. **ORM 的實際行為**：8 個測試全部以 mock 替身注入 repository，ORM 與 MySQL 的實際行為在測試中從未被執行。第 2 個問題發生在「我方物件、ORM、MySQL」三者的介面。
3. **環境狀態**：「這個站台有沒有上線」是執行期事實，不在程式碼裡。

另外，我原本以為「完全沒人提到 mock 風險」，複驗後發現：架構審查其實有提到，但**這個提醒在後續傳遞中消失了**。於是根因的判斷從「偵測層失敗」改為「傳遞層失敗」。這是我第三次遇到類似模式（偵測到了，但沒傳到做決定的人手上）。

### 我做了什麼修正

- **新增「執行驗證通道」**：一個專責的子代理，吃資料流地圖的「假設帳」，去對真實世界驗證：在測試環境跑測試、對正式資料庫做唯讀查詢、用日誌佐證，逐項回「已證實、已反駁、有爭議、無法驗證」。靜態讀碼看不出的欄位語意、ORM 實際行為、環境狀態，由它來攔截。
- **領域紅線文件納入審查輸入**，並對時間、時區、貨幣、快取鍵這類高風險主題設機械式觸發（追到資料存取層，包含未改動的下游）。
- **機械核對腳本**：核對審查帳本的格式與一致性（見下）。
- **回放測試**：把修復前的 commit 拿來，用新機制盲測重跑，三個漏網的阻斷級問題攔下了 3 個。其中欄位語意那個，主代理用**一次唯讀查詢**就直接反證：資料表內恆等式全成立、負值筆數非常多（查詢本身數字略）。
- **自己也要被審**：新機制設計好之後，我讓另一個模型獨立診斷、再讓審查模型對抗檢視，兩輪批判共修了二十多處，其中包括我自己的修訂閘漏抓的舊版殘留。

### 一個我沒料到的細節

那次回放中，執行驗證代理把一個「可以直接反證」的假設，錯標為「無法驗證」，原因是它以為要看歷史快照才能判斷，卻忽略手上證據欄已經有負值樣本。後來我把「驗證配方」與「順手證據義務」寫進它的定義。**驗證者本身也會偷懶，需要明確的做法指引。**

## 審查太慢怎麼辦：先找最長的串行段

另一個問題是審查等待太久。我用一次三輪審查的實際時間做了鑑識，第三輪從派出地圖到主審完成共 72.5 分鐘，可完全拆成串行段：

```text
地圖 22.4 → 縫隙 2.7 → 六通道平行（最慢的一條 22.0）→ 縫隙 5.3 → 主審 20.2
（單位：分鐘）
```

三個發現，推翻了我原本的直覺：

1. **通道數不決定時間。** 五條較短的通道，都在最慢那條（安全通道）的陰影下結束，砍掉架構、效能通道對時間零貢獻。
2. **裁決列數不決定主審時間。** 從 27 份歷史紀錄撈 33 筆回歸，列數只解釋 12.5% 的變異；同樣 35 列的三次主審，耗時從 9.3 到 18.3 分鐘不等。主審時長與它讀寫的 token 量相關性較高（r = 0.80），與列數較低（r = 0.35）。
3. **Deep 的時間代價，幾乎全在地圖階段使用的模型。** 兩輪相比，標準審查用較快的設定，地圖 8.0 分；深度審查用較強的設定，地圖 22.4 分（含一次逾時重試）。更強的模型沒換到正確性：它還把一處寫錯了。

結論：**找最長的串行段下手**，而不是砍平行段。落地的三項改善：

- **尾段機械化**：開卡由腳本完成，不再派子代理（原本約 10 分鐘）；主審自己讀各通道報告尾端的交接摘要，不再由主代理手工彙整。
- **地圖階段減重**：單次呼叫、設逾時、逾時就降級而不是重試；地圖依分支快取，同分支且祖先關係成立時走差量補丁，增量太大才退回全圖。
- **嚴重度紀律**：前述的「前例」欄位；主審升級嚴重度時要寫新證據；低嚴重度的發現批次落卡，不逐列寫理由。

估計等待從約 88 分鐘降到約 45–50 分鐘，P0 與 P1 從 8 項降到約 2–3 項。**這兩個數字是推估，要等下一次深度審查實跑才有真實對照**；而「前例」欄位本身，也可能被審查者敷衍，要抽查品質。

我也記下了**沒採用的方案**以及原因：

- 「風險評分分級」：它的省時賣點，建立在「主審時間與列數成正比」「通道時間與通道數成正比」兩個後來被否證的假設上。
- 「通道合併」：合併後單通道更慢，淨效果是更慢，還會把唯一一組真正的交叉驗證（異模型反證加安全通道）降格。
- 「差量審查」：潛力最大，但當時的 `git diff` 看不到工作樹，且帳本沿用會靜默刪掉「接受風險項下次觸及同檔要重審」的護欄，所以留到第二階段。

## 機械核對腳本的小教訓

審查發現會寫進一份 Markdown 表格（帳本），我用腳本機械核對格式與一致性。踩到一個坑：**表頭欄名被粗體包住時**（寫成 `| **ID** | **位置** |`），腳本認不出這是一張發現表，整批列不被收。如果同一檔案還有另一張正常的表，腳本**回傳全綠、一個字都不報**，這是靜默漏算，不是報錯。

我最初的卡片還寫錯了一半：宣稱「資料列的編號被粗體包住」也會漏算，實測不成立，編號用的是寬鬆比對，粗體不影響。**我用六組測試資料逐項重現，才訂正自己最初的說法。** 修法是比對前剝除儲存格內的強調標記（星號與反引號；底線不剝，因為合法識別碼與檔名裡有底線），而且剝除結果只拿來比對，不流進輸出。

教訓：

- 解析 LLM 產出的 Markdown，要先處理強調標記。
- 最危險的失敗形態是「不報錯，只少算」。
- 事故卡自己的「原宣稱」也要實測，不要假設寫下來的就是對的。

## 可直接套用的檢查清單

選等級：

- [ ] 檔案數 3 個內，且沒跨任何兩層？是 → Lite。
- [ ] 高風險（安全、金流）或跨多層？是 → Deep。
- [ ] 其餘 → Standard。縮編了，有聲明偏離嗎？

資料流地圖：

- [ ] 每條呼叫鏈都標到「檔案:行號」？
- [ ] 跨邊界傳遞點記的是「展開後的實際值」？
- [ ] 至少一條高風險路徑？
- [ ] 地圖只有路徑與假設，沒有結論？

審查發現：

- [ ] P0、P1 都有根因位置、路徑、三段式陳述、反證、信心與邊界、前例？
- [ ] 反證涵蓋上游驗證、冪等保護、下游 fallback、外部約束四類？
- [ ] 缺任何一項，已降級？
- [ ] 主代理自己對每個 P0 讀了地圖並至少 grep 交叉確認一次？

盲點：

- [ ] 欄位語意、ORM 實際行為、環境狀態這類靜態看不到的，有執行驗證通道嗎？
- [ ] 測試是否全用 mock 替身？有，就要列為風險。
- [ ] 領域文件有被納入審查輸入嗎？
- [ ] 審查通過後，有沒有拿真實資料或日誌再抽驗一次最重要的假設？
