# 給 AI 的行為準則比較

> 2026 年 6 月到 9 月，我陸續讀了六份公開的「給 AI 的行為準則」：四條寫程式原則、七步驟做事迴圈、佛教六原則、八條工程格言、六階梯子、以及一份主張把設定改寫成虛擬碼的提案。這篇比較它們的共通點、哪些在簡單任務沒用、以及查證文獻時踩到「兩篇研究結論相反」的經驗。內容以 Claude Code 為例，其中的觀念多半也適用於其他程式助手。

## 問題與背景

網路上有一大堆「讓 AI 變聰明」的指示檔：幾條格言、一份流程、一個 skill。每份都說自己有效。但它們到底在管什麼？互相有沒有重疊？放進自己的設定會不會反而變差？

我的做法是用同一套框架逐份評估：

1. 先把設計亮點窮舉出來，不急著評價。
2. 再對照自己現有的設定，找出「已有等效」「互補」「正面衝突」。
3. 最後決定是整份採用、改造既有、只借觀念，還是不採用。

六份評估下來，結論高度一致：**多數準則的核心內容，我已經有等效且更嚴格的做法；真正值得帶走的，是少數可以獨立抽出來的、帶量化門檻的判準句。**

這個結論不代表那些準則不好，而是準則的價值高度取決於「你現有的設定缺什麼」。對沒有任何規範的新專案，下面幾份都值得整份採用。

## 六份準則速覽

| 名稱 | 形態 | 一句話 | 我的結論 |
|---|---|---|---|

| fable-method | 4 個 skill，7 步驟迴圈，附 15 輪評測 | 價值集中在「陷阱情境」，簡單任務幾乎沒提升 | 借觀念 |

以下逐份說明。

## 1. karpathy-guidelines：四條原則，極簡常駐

這是一個公開專案，把一位知名研究者對「LLM 寫程式常見缺陷」的觀察濃縮成 4 條：

1. **先想再寫**（Think Before Coding）：先表態假設再動手；有歧義就列出來，不要默默選一個。
2. **簡單優先**（Simplicity First）：不過度工程。
3. **外科手術式修改**（Surgical Changes）：只動該動的；看到無關的死碼只提出來、不刪。
4. **目標導向**（Goal-Driven Execution）：先定可驗證的成功標準，再 loop。

### 設計亮點

- **全部 inline、不拆檔。** 行為準則屬於「常駐要遵守」型，拆開會讓部分規範漏載；極短才保證被完整讀入。範例另外放一個檔，按需讀，避免稀釋規則密度。
- **開頭就宣告取捨。** 「偏謹慎而非速度；瑣碎任務用判斷。」主動承認規則有成本，並給逃生口，對抗「對瑣碎任務過度套用」。
- **命令式改宣告式。** 「加驗證」改成「先寫測試、再讓測試通過」，把模糊指令轉成可獨立 loop 的成功標準。
- **多步驟任務強制三行格式**：步驟加驗證點綁在同一行，杜絕「列了步驟卻沒驗證點」。
- **一個單句啟發式**：「資深工程師會說這太複雜嗎？」零成本的過度工程自檢。
- 同一份內容並存多種載體（技能檔、根指示檔、Cursor 規則檔），其中 Cursor 規則用「永遠套用」的設定，對照 Claude 的 skill 是按需觸發。

### 我的評估

四條原則逐條對上我既有的做法（停點、最小變更、範圍合約、測試先行），而且我的版本更嚴格。直接加入還會讓「寫程式、審查、重構」這組觸發詞與既有流程 skill 重疊。

**值得借的是包裝，不是內容：**

- 明文承認規則成本，加一句「瑣碎變更用判斷，不強套全流程」。我的規則多用絕對句，缺這個逃生口。
- 單一來源、多平台分發的做法，我已經用「規則單一來源＋引用」涵蓋。

## 2. fable-method：七步驟迴圈與一份誠實的評測

這是一個完整的 Claude Code plugin，把「中等模型照固定流程做事，會比更強的模型自由發揮更可靠」這個主張，拆成四個 skill：`fable-method`（規則本體）、`fable-loop`（誰做）、`fable-judge`（對抗式驗證）、`fable-domain`（領域轉接器產生器）。

要先提醒：README 開頭的故事（模型在被移除前蒸餾自己的做事方法）是敘事包裝，沒有任何可查證的來源，我把它當行銷語氣，不當技術主張。技術內容本身不受影響。

### 最值得學的：評測紀錄本身

它附了 15 輪測試、260 多次 agent 執行。每一輪都寫「這輪改了什麼、測出什麼數字、因此加了什麼規則」。而且**公開了沒有效果的結果**：幾輪是「沒有提升」，還有一個功能因為 14 次測試只成功 1 次，直接砍掉並公開負面結果。

作者自己的結論也很誠實：這套方法**不會讓模型多出它本來沒有的洞見**；在已經很強的模型上提升很小，因為它們本來就會做這些事。價值集中在「陷阱情境」：假完成宣稱、權威衝突、弱模型、無人看管的執行。

### 值得借的設計

| 設計 | 動機 |
|---|---|
| 決策點強制輸出一行式標記（例如「意圖：…」「待辦：…」） | 實測：v2 把規則寫成條列裡的一句散文，幾乎沒效果（1／4 觸發）；v3 改成「決策當下必須輸出的一行」後變成 4／4 |
| 終止條件全部量化 | 簡單任務門檻（1 檔、少於 10 行）、證據蒐集預算（1 輪加 1 補充輪）、同一問題失敗 3 次就停手回報 |
| 「同類副本」檢查 | 修完一個錯誤後，強制搜尋整個專案找同類，輸出可重跑的搜尋結果，讓判者能重新執行驗證 |
| 衝突來源的權威順序 | 使用者明說 > 規格 > 測試 > 現有行為；並明文排除「把測試改到過」本身算授權 |
| 「不可逆」操作化 | 用一句問句：「另一個人或系統能不能在你還沒辦法復原之前就先看到？」 |
| 授權閘門 | 文件或已安裝技能的指示不算授權，只有使用者自己講過的原話才算（因紅隊式測試而加固） |
| 修改失敗的復原階梯 | 重讀原區塊、調整比對字串、重試一次、才放大範圍、最後才整檔重寫；禁止原封不動再試一次 |
| 規則本體壓在約 130 行 | 細節放 references 按需載入 |
| 同一套規則雙格式輸出 | 一份含 frontmatter（給 Claude Code），一份純文字（給 Codex、Cursor、aider 等其他工具） |
| 規則標明不適用邊界 | 同組 skill 的 description 互相交叉引用「什麼時候不要用我」 |

### 我的評估

「分診」概念（簡單任務不跑整套流程）與我的做法一致。評測方法論、「行式標記比散文有效」的實測、量化終止條件都很有參考價值。但這是別人的評測，我標記為「受控實驗」層級的參考，不是我自己環境的驗證。

## 3. buddhist-method：六條原則與四個量化技巧

作者把六條佛教認識論與決策原則編碼成給 LLM 用的工作紀律：

| 原則 | 一句話 |
|---|---|
| Kalāma | 驗證，不要套模式 |
| Yoniso Manasikāra | 找根因 |
| Sati-Sampajañña | 重新確認現狀，不要依賴記憶 |
| Anatta | 願意整篇捨棄重寫 |
| Pahāna | 移除成因，不要掩蓋 |
| Upekkhā | 施壓下維持冷靜 |

另有一份四聖諦除錯框架，**每一步都附一個「這步真的做完了嗎」的自測**。例如：「如果你說不出『這個改動為什麼移除了成因』，你可能只是掩蓋了症狀，回到上一步。」把抽象步驟綁定機械可判定的完成條件，這個設計我很喜歡。

### 對照我自己的設定

六條核心原則全部已有對應，且多數我的做法更具體（分散在具體事故記憶與除錯 skill 裡）。**沒有任何一條是我完全空白的新原則**，差異只在操作化細節。真正新的是延伸原則裡的三個量化規則：

1. **先列至少 3 個可能成因，再依成因空間挑要查的**，不是挑第一個「看起來合理」的。這是把「找根因」從模糊指示變成具體程序。
2. **方向性停損測試**：每次重試後問「這次是不是比上次更接近」，連續兩次沒有更接近就停。我原本只有「同一工具同參數連續失敗 2 次」的計數式規則，這條管的是趨勢，兩者互補：一個管次數，一個管方向。
3. **問與不問的時間門檻**：「如果錯誤假設會浪費對方超過幾分鐘複核時間，就先問。」把「歧義先澄清」變成可操作的判準。

另外一個設計提醒：四聖諦這種重量級框架，作者自己寫明「小而清楚的錯誤，只要找根因加移除成因就夠」，只有「不清楚、反覆、假修好」才上完整框架。**重量級流程一定要寫「什麼時候不要用」，否則瑣碎問題會被過度儀式化。**

### 為什麼不整份裝

- 巴利文與泰文術語有 24 個，每個都要補中文定錨。對沒有這套術語背景的讀者，作者設計的「短詞喚回完整模式」記憶術沒有效益。
- 觸發語句與既有的除錯 skill、收到審查意見的 skill 高度重疊，會出現「同一句話命中兩三個 skill」的衝突風險。
- 專案本身是一次寫定：建立後程式碼沒有實質修訂。

## 4. 八條工程格言：極簡無條件教條

一位開發者累積約 600 億 token 的 side project 開發後，沉澱出一份個人 AGENTS.md：7 條主要加 1 條補充，全檔不到 200 token 的祈使句。例如：

- 不要保留向後相容，移除過時路徑，不要加相容層、fallback 或遷移。
- 選擇完整滿足當前需求的最簡實作，避免投機性的抽象、設定、間接層。
- 一層一層長系統，從端到端可用的最小版本開始，絕不拿可用的產品換未完成的複雜度。
- 優先用成熟、維護良好的函式庫；先用專案現有的依賴，不要不查文件就斷定函式庫缺能力。
- 做長期的架構決策，不接受「只管現在、之後要換掉」的權宜方案。

### 設計亮點

- **衝突對夾擠。**「最簡實作」與「長期架構決策、不收權宜方案」並存。只講簡單，會被拿去合理化權宜 hack；補上長期條才封住漏洞。
- **「禁令加替代動作」句式**：不要做 X，而是做 Y。只說禁止、不給替代行為，模型會亂猜。
- **依賴決策梯**：專案現有依賴 → 成熟外部函式庫 → 最後才自寫，並附一個可執行的驗證動作（查文件與型別後才能斷定缺能力）。
- **適用邊界外置**：檔案內是無條件教條，「只用於 side project、別上正式環境」的場景閘門寫在檔案外，由人把關。

### 我的取捨

整份不收，理由是場景錯位：我的專案是多人維護的正式後端，第一條「不要保留向後相容」對有外部協議的系統是紅線級的反面。另外「無條件教條」與我自己的反膨脹原則（通則要帶逃生口）牴觸。

**只借一條：生成端的「先用現有依賴、不要不查文件就造輪子」。** 我在審查端（有審查維度抓造輪子）與 skill 建置端（建前先搜）都有，唯獨寫程式的當下沒有。這是三端裡唯一的缺口，而且是這八條裡唯一「行為具體、可驗證、不是哲學宣言」的。

「適用邊界外置」手法與我的做法相反：我把「管到哪、管不到哪」寫進條文，因為多人團隊不能靠口頭免責聲明把關。兩者服務不同場景，沒有對錯。

### 查證：兩篇研究的結論相反

這份格言附帶引用了三篇研究，我請子代理逐篇讀過。**其中兩篇的主實驗方向相反**，所以引用時必須並陳，不能挑一篇當證據：

- 一篇受控實驗（報告中所引編號為 arXiv 2602.11988，我沒有重新核對編號）指出：「架構總覽、哲學宣言」型的專案指示檔，對 agent 成功率幫助有限，甚至為負。
- 另一篇以真實 PR 為資料的研究（報告中所引編號為 arXiv 2601.20404，同樣沒有重新核對）方向相反，兩篇結論沒有收斂。

我從中帶走的共識只有一條：**專案特有的具體事實，比通用哲學更有價值。** 這也驗證了我既有的做法：主檔寫指標、專案紅線放 references、細則按需載入。

另外要注意：「41% 降到 11%」這類社群流傳的數字是行銷語言，我不採信。

## 5. ponytail：六階梯子與「先擋再寫」

ponytail 把「看過所有過度工程的資深工程師」塞進 AI：寫任何程式碼前，先爬一條 6 階梯子，停在第一個成立的階：

1. YAGNI（現在真的需要嗎）
2. 標準函式庫有嗎
3. 原生平台有嗎
4. 專案既有依賴有嗎
5. 一行能解決嗎
6. 最小可行版本

### 設計亮點

- **短路求值**：停在第一個成立的階，把模糊的「寫簡單點」變成可逐階判定的決策樹。
- **兩階都成立就取較高階**：防止梯子本身變成研究專案。
- **審查輸出強制單行**：「行號、標籤、什麼問題、替代做法」。對抗審查時寫「你是否考慮過…」的軟性長篇，逼出可執行結論。標籤是固定的列舉，同時是指令也是輸出格式。
- **「沒事可做」是合法終態**：沒有可砍的就寫「已經夠精簡，出貨」，避免硬湊發現。
- **解釋比程式碼長就刪解釋。**
- **刻意簡化的行內註解約定**：註解寫天花板與升級路徑，可以用 grep 收割成技術債帳本。
- README 罕見地誠實標注：在簡潔推理型模型上反而更貴。

### 我學到的一個陷阱

評估時我發現：它的常駐規則是由「開場 hook」注入主 session。但寫程式的是子代理，子代理不繼承主 session 的 hook 注入。**原樣安裝，省程式碼紀律打不到真正寫程式的子代理。** 要生效，必須把梯子放進子代理的定義裡。

我最後的做法：把梯子寫進子代理的寫程式紀律，並在最上面補一階「本專案是不是已經有了」（補足它沒涵蓋的內部重複問題）。

## 6. OOP 虛擬碼提案：查證比採用更有價值

這份報告主張把整個設定從自然語言 Markdown 改寫成偽 TypeScript 的物件導向結構：用 `BaseAgent` 繼承消除規則重複，用 `ASSERT`、`ENUM`、`SWITCH` 把模糊語意變成可判定的布林，宣稱省 30–60% token 並大幅提升遵從度。

這份報告價值在「查證」。我逐筆實查它引用的來源：

| 報告引用 | 查證結果 |
|---|---|
| 某語言「實測節省 20–30% token」 | 該專案 README 原文是「often be written with 20%-30% fewer tokens」，**明確沒有實測**；「實測」二字是報告自己加的 |
| 一篇 2024 年論文（編號 A） | 該編號實為機器人任務規劃論文。真正相符的論文編號不同、年份是 2025，內容大致相符。**編號錯置，論文存在、連結錯** |
| 另一篇 2024 年論文（編號 B） | 該編號實為宇宙學論文。真正的論文是 2026 年，單一作者的提案論文，「大幅降低幻覺率」在摘要層查無實證 |
| 虛擬碼提示用在圖推理的論文 | 編號與標題正確，但實驗只用兩個 2023 世代模型；結果依任務而異，部分任務還被零樣本反超。報告寫的「提升超過 15%」查無此固定數字 |
| 兩個執行期 LLM 管線框架 | 專案存在，但它們是「執行期編譯 prompt」的框架，不是「把設定檔改寫成虛擬碼」的證據，類別錯置 |
| 「提示詞工程社群」的某模式 | 沒有連結、沒有作者，無法查證 |
| 效益矩陣全部數字（省 40–60%、誤操作降 70%、解析錯誤趨近 0%、速度 3 倍） | **整張表沒有任何來源**；偽精度 |

報告完全沒引用**反面文獻**：一篇 EMNLP 2024 的論文（《Let Me Speak Freely?》，arXiv:2408.02442）發現格式限制越嚴，推理能力退化越明顯；後續研究也指出結構化格式（JSON、XML、YAML）使推理準確率退步 10–30%。Claude Code 官方的最佳實踐也建議精簡的自然語言 Markdown，沒有「用虛擬碼寫設定」的建議。

### 為什麼不採用

一句話：**提案的核心機制（執行期繼承與方法呼叫）在這個環境不存在。** 沒有編譯器把 `BaseAgent` 展開進每個 agent，等效機制（引用注入、frontmatter 預載）我已經在用。另外：

- 把執法從「確定性的 shell hook」移回「請模型自己遵守的 `ASSERT`」是降級。
- skill 靠 description 的自然語言比對觸發，改成介面宣告會破壞觸發。
- 設定檔是人也要讀、要維護的，偽程式碼大幅提高維護門檻。
- 規則的違規判法句式（「…＝違規」）本來就是這個觀念的中文版實作。

### 唯一借走的觀念

控制流重、狀態追蹤重的機械規則段，用結構化條件寫法（IF／THEN／列舉風格）可能比散文有更高遵從度，這點有真文獻支撐（虛擬碼提示對模型覺得難的狀態追蹤任務有幫助）。但**不直接改**，任何段落要改寫成結構化條件式，先做 A／B 實測，因為「紙面等效不等於行為生效」。這部分我**未實測**。

## 共通點與差異

### 六份準則都在做的事

1. **把模糊指示變成可判定的條件。** 先列 3 個成因、同一問題失敗 3 次就停、單行審查輸出、「另一個人能不能先看到」。
2. **要求先表態、再動手。** 先講假設、先定成功標準、先爬梯子。
3. **限制範圍。** 只動該動的、不刪無關死碼、不做授權外的事。
4. **要求證據。** 驗證不套模式、每步附「做完了嗎」自測、可重跑的搜尋結果。
5. **承認自己的邊界。** karpathy 的「瑣碎任務用判斷」、fable-method 的「不會多出洞見」、buddhist-method 的「小錯誤不用全套」、ponytail 的「簡潔推理模型上更貴」。

### 哪些準則在簡單任務沒用

- 四條寫程式原則、七步驟迴圈對簡單任務都明寫「瑣碎任務用判斷」。
- fable-method 的評測顯示：價值集中在陷阱情境（假完成、權威衝突），聰明模型做簡單任務幾乎沒提升。
- 格言類（8 條工程格言）更依賴「由人判斷適用場景」，放進多人專案會失控。

### 哪些做法比較可靠

| 做法 | 證據 |
|---|---|
| 決策點強制輸出一行標記 | fable-method 實測，散文 1／4，行式 4／4（作者自己的受控實驗） |
| 量化終止條件 | 多份準則獨立收斂 |
| 先擋再寫（寫前的梯子） | 與「寫完再清理」互補，時機不同 |
| 規則量少而精、細節按需載入 | 多份獨立採用；一篇掃描 100 個專案的研究稱 91% 的指示檔臃腫或矛盾（報告所引，未重新核對） |

## 踩過的坑與教訓

1. **整份採用前，先對照既有設定。** 六份裡四份的核心與我既有做法重疊；整份裝進去只會製造「同一情境命中兩三個 skill」的衝突。
2. **觸發詞重疊是隱形成本。** 兩個 skill 都寫「寫程式、審查、重構」，模型不知道先用哪個。
3. **注入點要對準執行者。** 常駐規則注入主 session，寫程式的卻是子代理，規則打不到人。
4. **引用文獻必須並陳正反。** 同一份格言引的三篇研究有兩篇結論相反，只挑一篇會誤導。
5. **來源編號要查歸屬，不只查存在。** 論文存在、編號貼錯，是這個月看到的典型失效。
6. **量化主張先看基線與樣本。** 「省 40–60%」整張表無來源，就是偽精度。
7. **重量級流程要寫「什麼時候不要用」。**
8. **工具語言與你的輸出語言要對得上。** 巴利文術語在繁體中文環境，每個都要補定錨。

## 可直接套用的檢查清單

評估別人的行為準則前：

- [ ] 這份準則管的是「怎麼想」「怎麼做」還是「怎麼驗」？我現有設定缺哪一塊？
- [ ] 它的核心內容我已經有等效做法嗎？（先逐條對照，再決定要不要裝）
- [ ] 觸發條件或 description 跟我現有的 skill 重疊嗎？
- [ ] 它寫了「什麼時候不要用」嗎？沒有的話我要自己補。
- [ ] 它的評測數字用的是什麼基線？樣本多大？有沒有公開負面結果？
- [ ] 引用的文獻編號、年份、結論，我抽查過幾筆？
- [ ] 常駐規則會不會注入到真正執行的那一層（子代理）？
- [ ] 要借的是內容、判準句，還是包裝？
- [ ] 落地前，有沒有安排 A／B 實測？
