# Sub-Agent Prompt Design Guide

> 適用於 Claude Code 多代理人 Orchestrator 架構中，16 個子代理人的提示詞設計規範。
> 基於 Anthropic 官方 Prompt Engineering Best Practices + 實務迭代經驗。

---

## 1. 核心原則

### 1.1 一個代理人 = 一個合約

每個子代理人的 prompt 本質上是一份**合約（Contract）**，必須包含四個區塊：

```
┌─────────────────────────────────┐
│  IDENTITY   — 你是誰            │
│  SCOPE      — 你負責什麼（與不負責什麼）│
│  PROTOCOL   — 你怎麼做          │
│  OUTPUT     — 你交付什麼格式     │
└─────────────────────────────────┘
```

缺少任何一塊，代理人行為都會漂移。

### 1.2 精確性 > 激勵性

| 無效寫法 | 有效寫法 |
|---------|---------|
| 你是頂級架構師，請給出最好的建議 | 你評估架構方案時使用 CAP 定理、故障域分析、運維複雜度三個維度 |
| 別手軟，直接說 | 輸出必須包含 risk_level 欄位，值為 critical/high/medium/low |
| 仔細想想 | 在回答前，先列出你考慮的 3 個替代方案及其 tradeoff |

Claude 4.x 照字面執行指令。情緒化措辭（「別手軟」「盡全力」）不會改變模型行為，結構化約束才會。

### 1.3 XML Tags 是子代理人的骨架

Claude 對 XML tags 有特別的注意力權重。所有子代理人 prompt 必須使用 XML 結構化：

```xml
<agent_identity>...</agent_identity>
<task_scope>...</task_scope>
<input_schema>...</input_schema>
<output_schema>...</output_schema>
<constraints>...</constraints>
<examples>...</examples>
```

不要用 Markdown headers 替代 XML tags — 在 system prompt 層級，XML 的解析可靠性遠高於 Markdown。

## 2. 四區塊模板

### 2.1 IDENTITY（身份）

定義代理人的**角色 + 經驗 + 思考框架**，而非泛泛的「專家」。

```xml
<agent_identity>
You are a code review lead specializing in Laravel/PHP backend systems.
You have 8+ years reviewing high-traffic payment middleware,
and have seen production incidents caused by:
- Race conditions in concurrent wallet operations
- Silent data loss from unhandled API timeout
- Cache invalidation bugs in multi-tenant systems

You think in terms of: failure modes first, then correctness, then performance.
</agent_identity>
```

**設計要點：**

- 明確技術棧（Laravel/PHP, not just "backend"）
- 列出見過的失敗模式 → 引導代理人注意同類問題
- 聲明思考優先順序 → 控制輸出的焦點排序

**反模式：**

```xml
<!-- BAD: 泛泛角色，無法引導具體行為 -->
<agent_identity>
You are an experienced code reviewer. Be thorough and helpful.
</agent_identity>
```

### 2.2 SCOPE（職責範圍）

明確定義**做什麼**與**不做什麼**，防止代理人越界。

```xml
<task_scope>
<responsibilities>
- Review code changes for correctness, security, and maintainability
- Identify potential race conditions and data consistency issues
- Verify error handling covers all external API failure modes
- Check adherence to project coding conventions
</responsibilities>

<out_of_scope>
- Do NOT refactor code beyond the scope of the review
- Do NOT suggest architecture-level changes (escalate to architect agent)
- Do NOT implement fixes; only identify and describe issues
- Do NOT review test files unless they test critical payment flows
</out_of_scope>

<escalation>
If the change touches wallet balance calculation or cross-platform
transaction flow, flag it as REQUIRES_ARCHITECT_REVIEW.
</escalation>
</task_scope>
```

**設計要點：**

- `out_of_scope` 比 `responsibilities` 更重要 — 代理人傾向「多做」而非「少做」
- 設定明確的升級條件（escalation），讓 Orchestrator 知道何時介入

### 2.3 PROTOCOL（執行協議）

定義代理人的**思考步驟**，而非只描述期望結果。

```xml
<protocol>
For each code change, follow this sequence:

Step 1 — SCAN: Read the full diff. Identify which layers are affected
         (Controller / Service / Repository / Config).

Step 2 — RISK MAP: For each affected file, assess:
         - Can this fail silently? (data loss risk)
         - Can this cause inconsistent state? (race condition risk)
         - Does this handle the unhappy path? (error handling)

Step 3 — VERDICT: Classify each finding as:
         - BLOCK: Must fix before merge
         - WARN: Should fix, but not a blocker
         - NOTE: Suggestion for improvement

Step 4 — SUMMARY: Produce structured output per output_schema.
         If no issues found, explicitly state "No issues identified"
         rather than inventing minor concerns.
</protocol>
```

**設計要點：**

- Step-by-step 觸發 Claude 的 chain-of-thought 推理
- 每步都有具體的判斷標準，不是「仔細檢查」
- 最後一步防止「為了找問題而找問題」的行為

### 2.4 OUTPUT（輸出規格）

用 schema 定義輸出格式，消除歧義。

```xml
<output_schema>
Respond in this exact JSON structure:

{
  "summary": "One-line overall assessment",
  "risk_level": "critical | high | medium | low | none",
  "findings": [
    {
      "file": "path/to/file.php",
      "line": 42,
      "severity": "BLOCK | WARN | NOTE",
      "category": "race-condition | error-handling | security | convention",
      "description": "What the issue is",
      "suggestion": "How to fix it (code snippet if applicable)"
    }
  ],
  "escalation": null | "REQUIRES_ARCHITECT_REVIEW",
  "metadata": {
    "files_reviewed": 5,
    "time_estimate": "15min to address all BLOCK items"
  }
}

If no findings, return findings as an empty array.
Do NOT wrap the JSON in markdown code fences.
</output_schema>
```

**設計要點：**

- Enum 值明確列出（`BLOCK | WARN | NOTE`），不留模糊空間
- 包含 `metadata` 讓 Orchestrator 做決策（例如估算修復時間）
- 明確指示「不要包 markdown code fence」— 否則下游解析會壞

## 3. 進階技巧

### 3.1 Few-Shot Examples（範例驅動）

對於輸出格式複雜或判斷標準微妙的代理人，提供 2-3 個範例：

```xml
<examples>
<example type="good_finding">
{
  "file": "app/Services/WalletService.php",
  "line": 87,
  "severity": "BLOCK",
  "category": "race-condition",
  "description": "debit() reads balance then writes without lock.
                  Concurrent requests can overdraw.",
  "suggestion": "Wrap in Redis WATCH/MULTI or use DB row-level lock:
                  DB::table('wallets')->where('id', $id)->lockForUpdate()->first()"
}
</example>

<example type="over_flagging">
<!-- This is what NOT to do -->
{
  "file": "app/Http/Controllers/GameController.php",
  "line": 12,
  "severity": "WARN",
  "category": "convention",
  "description": "Variable name could be more descriptive"
}
<!-- Too trivial. This wastes reviewer attention. Skip unless it causes ambiguity. -->
</example>
</examples>
```

**設計要點：**

- Good example 展示期望的深度與格式
- Bad example（反例）同等重要 — 劃定「不該標記什麼」的底線
- Claude 4.x 會高度模仿 example 的風格與深度

### 3.2 Context Injection（上下文注入）

子代理人通常需要接收來自 Orchestrator 的動態上下文：

```xml
<input_schema>
You will receive the following context from the orchestrator:

<diff>
{{GIT_DIFF}}
</diff>

<project_context>
- Framework: Laravel 9
- Architecture: Multi-tenant game platform middleware
- Key patterns: Service init via app('Service')->init('Name')
- DB: MySQL multi-database, Redis via Predis
</project_context>

<review_focus>
{{ORCHESTRATOR_SPECIFIED_FOCUS}}
<!-- e.g., "Focus on Pragmatic Play integration changes" -->
</review_focus>
</input_schema>
```

**設計要點：**

- 用 `{{PLACEHOLDER}}` 標記動態欄位，讓 Orchestrator 知道要填什麼
- `project_context` 是靜態的，寫死在 prompt 裡減少 token 浪費
- `review_focus` 是動態的，讓 Orchestrator 可以收窄代理人的注意力

### 3.3 Thinking Budget 控制

不同代理人需要不同深度的推理。透過指令控制思考量：

```xml
<thinking_budget>
<!-- 適用於需要深度推理的代理人（architect, review-lead）-->
Before responding, think through at least 3 alternative approaches.
For each, identify the primary tradeoff. Then select the best option
and explain why the alternatives were rejected.
</thinking_budget>
```

```xml
<thinking_budget>
<!-- 適用於執行型代理人（foundation-implementer）-->
Do not deliberate on alternatives. Follow the specification exactly.
If the specification is ambiguous, flag the ambiguity instead of guessing.
</thinking_budget>
```

**設計要點：**

- Architect / Review-Lead（跑 Opus）→ 鼓勵深度推理
- Foundation-Implementer（跑 Haiku）→ 精確執行，不浪費 token 在「思考」上
- 明確告訴輕量代理人「遇到歧義就問，不要猜」

### 3.4 Inter-Agent Communication Protocol（代理人間通訊）

定義代理人如何向 Orchestrator 回報狀態：

```xml
<communication>
When you need to communicate with the orchestrator:

STATUS signals:
- DONE: Task completed successfully. Attach output.
- BLOCKED: Cannot proceed. Specify what is missing.
- ESCALATE: Issue exceeds my scope. Specify target agent.
- PARTIAL: Completed N of M items. Attach partial output.

Format:
{
  "status": "DONE | BLOCKED | ESCALATE | PARTIAL",
  "target_agent": null | "architect" | "review-lead",
  "message": "Human-readable explanation",
  "output": { ... }
}
</communication>
```

### 3.5 Guardrails（護欄）

防止代理人在邊界情況下做出錯誤決策：

```xml
<guardrails>
- NEVER modify files outside the specified scope
- NEVER execute destructive operations (DROP, DELETE, TRUNCATE)
- NEVER expose values matching: _PASSWORD, _SECRET, _TOKEN, _KEY, _API_KEY
- If the same tool call fails 2 times with identical errors, STOP and report BLOCKED
- If estimated output exceeds 500 lines, split into chunks and report PARTIAL
- If task requires information not provided in context, report BLOCKED (do not hallucinate)
</guardrails>
```

## 4. 各代理人類型的 Prompt 骨架

### 4.1 分析型代理人（architect, critical-analyst）

重點：深度推理、多方案比較、風險評估

```xml
<agent_identity>
[具體角色 + 失敗經驗 + 思考框架]
</agent_identity>

<task_scope>
<responsibilities>[分析、評估、建議]</responsibilities>
<out_of_scope>[不實作、不修改程式碼]</out_of_scope>
<escalation>[升級條件]</escalation>
</task_scope>

<protocol>
Step 1: Understand the problem space (restate in your own words)
Step 2: Generate 3+ alternative approaches
Step 3: Evaluate each against [specific criteria]
Step 4: Recommend with explicit tradeoff analysis
</protocol>

<thinking_budget>
Think deeply. Explore alternatives before committing.
</thinking_budget>

<output_schema>[structured JSON/markdown]</output_schema>
<guardrails>[安全護欄]</guardrails>
```

### 4.2 執行型代理人（foundation-implementer, formatter）

重點：精確執行、零偏差、快速完成

```xml
<agent_identity>
[具體技術棧 + 程式碼規範]
</agent_identity>

<task_scope>
<responsibilities>[按規格實作]</responsibilities>
<out_of_scope>[不重構、不改架構、不加功能]</out_of_scope>
<escalation>[規格不清時回報]</escalation>
</task_scope>

<protocol>
Step 1: Parse the specification completely before writing any code
Step 2: Implement exactly as specified
Step 3: Verify against specification (checklist)
Step 4: Report DONE with output or BLOCKED with reason
</protocol>

<thinking_budget>
Do not deliberate. Execute precisely. Flag ambiguity, do not resolve it.
</thinking_budget>

<output_schema>[code + status report]</output_schema>
<guardrails>[安全護欄 + read-before-write]</guardrails>
```

### 4.3 審查型代理人（review-lead, qa-checker）

重點：全面檢查、不遺漏、不過度標記

```xml
<agent_identity>
[審查經驗 + 常見陷阱清單]
</agent_identity>

<task_scope>
<responsibilities>[檢查、驗證、分類問題]</responsibilities>
<out_of_scope>[不修復、不重構]</out_of_scope>
<escalation>[嚴重問題升級]</escalation>
</task_scope>

<protocol>
Step 1: Full scan — identify all affected areas
Step 2: Risk assessment per area
Step 3: Classify findings (BLOCK / WARN / NOTE)
Step 4: If no real issues, say so explicitly
</protocol>

<examples>
[good finding + over-flagging anti-example]
</examples>

<output_schema>[findings array + risk_level + escalation]</output_schema>
<guardrails>[安全護欄]</guardrails>
```

## 5. Prompt 自檢清單

設計完每個子代理人的 prompt 後，逐項檢查：

```
[ ] IDENTITY 是否包含具體技術棧與失敗經驗？（非泛泛「專家」）
[ ] SCOPE 是否明確定義 out_of_scope？（防越界）
[ ] PROTOCOL 是否有 step-by-step？（非「仔細分析」）
[ ] OUTPUT 是否有 schema + enum 值？（非「結構化輸出」）
[ ] 是否有 2+ examples（含反例）？（格式複雜時必要）
[ ] 是否定義 escalation 條件？（Orchestrator 需要知道）
[ ] 是否設定 thinking budget？（分析型 vs 執行型不同）
[ ] guardrails 是否涵蓋敏感操作？（密碼、刪除、失敗重試）
[ ] 動態欄位是否用 {{PLACEHOLDER}} 標記？
[ ] 整體 token 數是否在預算內？（Haiku agent < 2000 tokens）
```

## 6. 常見錯誤與修正

| 錯誤 | 為什麼會壞 | 修正 |
|------|----------|------|
| 用情緒語言激勵（「盡全力」「別偷懶」） | Claude 4.x 不受激勵影響，只浪費 tokens | 改用結構化約束與評估維度 |
| 只定義 responsibilities 沒有 out_of_scope | 代理人會自行擴展職責範圍 | 永遠定義邊界，寧可多限制 |
| 輸出格式用自然語言描述 | 每次輸出格式不一致，下游解析失敗 | 用 JSON schema + enum |
| 所有代理人用相同 thinking budget | 輕量代理人浪費 token，重量代理人思考不足 | 按角色類型分配 |
| Example 只有正例沒有反例 | 代理人不知道「太多」的界線在哪 | 必須包含 over-flagging / over-engineering 反例 |
| Prompt 超過 4000 tokens | Context window 被 prompt 佔滿，留給任務的空間不足 | 靜態知識放 project_context，動態注入最小化 |
| 沒有 escalation 機制 | 代理人遇到超出能力的問題會硬做出錯誤結果 | 定義明確的 BLOCKED / ESCALATE 條件 |
