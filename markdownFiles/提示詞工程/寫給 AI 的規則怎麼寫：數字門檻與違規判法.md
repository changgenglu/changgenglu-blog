# 寫給 AI 的規則怎麼寫：數字門檻與違規判法

> 2026 年，我把自己的 AI 程式助手設定反覆重寫了好幾輪，最大的心得是：寫給 AI 的規則，要寫成「能判定有沒有違反」的樣子，而且門檻要用數字。這篇整理怎麼寫、怎麼執法、怎麼放手讓 AI 自己決定、怎麼讓常駐規則不無聲長胖，以及換模型世代時怎麼重審。以 Claude Code 為例，其中的原則也適用於其他會讀專案指示檔的程式助手。

## 問題：規則寫了，AI 還是不照做

典型的失敗是這樣的：我在指示檔寫「大型任務請委派子代理」。結果有一次，主代理自己動手寫了 549 行的服務類別，完全沒委派。規則白紙黑字寫著，但「大型」到底多大，沒有人說得準。

規則沒錯，問題是「大」這個字沒有定義。AI（或任何人）都能把「大」解釋成對自己有利的樣子。

寫給 AI 的規則有三種常見的失效方式：

1. **形容詞規則。** 「適度」「大型」「必要時」「盡量」。每個執行者的解釋不同，沒人能說「你違規了」。
2. **只有原則、沒有判法。** 規則說「要驗證後才宣稱完成」，但沒說什麼算驗證。AI 說「我檢查過了」，你也無從反駁。
3. **只寫在文件裡。** 規則存在，但執行時沒有任何機制確認它被遵守。

這篇的核心主張是：**一條規則至少要有「規則句、違規判法、正反例」三樣東西；能量化的地方一律用數字；而且要想清楚誰來執法。**

## 核心做法

### 1. 規則的骨架：規則、違規判法、正例、反例

我現在寫的每一條規則，都用同一個骨架：

```text
判定問句 → 動作 → 正例 → 反例
```

舉一個真實的例子：「該不該停下來問使用者」。

- **判定問句**：我能不能為這個請求寫出唯一一份驗收條件？
- **動作**：能就直接做；不能就問。
- **正例**：使用者說「幫我優化這支 API」→ 問：「要降延遲、提吞吐，還是改可讀性？建議先量延遲。」
- **反例**：使用者問「小數金額該怎麼處理」→ 回答方法即可；直接開始規劃實作，是把提問當成授權。

判定問句的作用是把「感覺」換成「我能不能做到某件具體的事」。這樣模型在自己的推理裡有東西可以檢查，不是憑語感。

### 2. 違規判法：寫成「…＝違規」

違規判法是一個句子，格式固定：**「某個可以觀察到的行為，且沒有某個條件＝違規」。**

幾個我用過的例子：

| 規則 | 違規判法 |
|---|---|
| 術語首見要附中文說明 | 單則回覆正文中，第一次出現的英文技術詞沒有附中文說明＝違規 |
| 修改某類敏感檔前要問使用者 | 對該類目標下了編輯指令，而本 session 對使用者的回覆裡沒有一句明確授權＝違規 |
| 在共用堆疊的環境用 stash | 身處 worktree 卻執行不帶唯一標記的 `git stash`＝違規 |
| 記憶索引的鉤子長度 | 鉤子少於 25 字（看不出教訓）或多於 70 字（把事故經過塞進索引）＝違規 |
| 比喻要點名對應物 | 回覆出現比喻角色，而同一則內沒有逐一點名它對應本案的什麼＝違規 |

寫違規判法有一個副作用，我覺得是最大的好處：**寫不出來，就代表規則本身還沒想清楚。** 我有幾次寫到一半發現，自己根本說不出「怎樣算違反」，這時候回頭改的是規則，不是判法。

判法也可以寫「豁免」。例如術語定錨的豁免有三類：產品與協定專名（Redis、HTTP）、程式碼與識別碼、本則前文已經定錨過的詞。豁免寫明，才不會讓規則被機械式過度套用。

### 3. 數字門檻

凡是能量化的，就量化。我在設定裡用過的數字，供參考：

| 情境 | 門檻 |
|---|---|
| 該不該委派子代理 | 要讀 3 個以上檔案全文、單檔超過 500 行、要查 2 個以上網頁、3 個以上檔案套同一模式 |
| 該不該換方法 | 同工具同參數連續失敗 2 次就停；子代理同一子任務累計失敗 2 次才升級模型 |
| 該不該升級模型 | 小模型失敗 1 次；或任務一開始就是高歧義（設計選邊、複雜根因） |
| 委派 prompt 長度 | 超過 1,500 字容易偏題，這時是「資訊缺」，補資訊同級重派，不要升級 |
| 子代理回傳 | 超過 30 行就要求落檔再回報 |
| 記憶索引鉤子 | 25–70 字，平均不超過 60 字 |
| 單支 skill 的 description | 300 字以內（經 A／B 測過，見下文） |
| 開場固定成本 | 提醒線 16,300 token |

這些數字有三個性質值得說明：

- **數字是校準出來的，不是拍腦袋的。** 例如 300 字的 description 上限，是我跑 A／B 測試（160 次呼叫）後訂的：四支最長的縮到 300 字以內，三支觸發率不變，一支掉了 20 個百分點。所以規則裡寫「縮之前先測」。
- **數字是整條規則的錨點。** 「讀 3 個檔案以上就委派」比「大任務就委派」多了一個無法狡辯的判斷點。
- **數字要有人負責校準。** 門檻會過時。我的規則裡有一條專門寫「委派門檻與回報合約的數字要定期校準」。覺得數字不對時，走修改規則的流程去改，**不是在心裡悄悄放寬**。

### 4. 判定問句比判定條件更耐用

並非所有事情都能量化。「這算完成嗎」「該不該問」「方向是不是錯了」這類題目，我用「判定問句」代替數字：

- 完成判定：「『完成』這個字後面，我能貼出本 session 看過的哪一行輸出？」貼不出來，就寫「已改、未驗」。
- 該問嗎：「我能不能為這個請求寫出唯一一份驗收條件？」
- 該升級模型嗎：「上一次失敗的原因是『判斷錯』還是『資訊缺』？」判斷錯才升級；資訊缺就補資訊同級重派。

每條判定問句後面，我都附 2–3 組正反例，而且正反例取自真實事故。例如「完成」的措辭對照：

| 狀態 | 可以說 | 不可以說 |
|---|---|---|
| 改了、跑過驗證、輸出正確 | 「修復完成，12 個測試通過（輸出見上）」 | — |
| 改了、沒跑 | 「已改，還沒跑。現在跑驗證。」 | 「修好了」「應該沒問題」 |
| 子代理說綠燈、我沒看到輸出 | 「子代理回報綠燈，我尚未複跑」 | 「測試通過」 |
| 試跑只印出指令、沒連上目標 | 「試跑只印指令、未連線；已用唯讀查詢讀回現況：…」 | 「已 dry-run 確認」 |

最後一列是一次事故換來的：一個腳本的「試跑模式」其實只印出指令，完全沒連到目標；主機名填錯也不會報錯，卻被我拿來當「請使用者核准對外寫入」的依據。現在規則要求：請使用者核准之前，附上的依據要有一次對**同一主機、同一目標**的唯讀查詢實際輸出，且非空。

## 怎麼運作：三層執法

規則寫得再清楚，也要想「誰來確認它被遵守」。我把執法分成三層：

1. **規則文字**：有沒有可機械判定的違規判法？只有原則句，就只是軟性建議。
2. **產出時自驗證**：執行者產出前，有一項檢查驗得到這條規則，而且**檢查的口徑與規則一致**嗎？規則寫「每項都要」、自驗只查「至少一次」，形同虛設。
3. **事後偵測**：有 hook 或測試斷言事後抓得到嗎？

不要求三層都有，要求的是**不要只剩第 1 層，而且缺哪層當下講明白**。同一條規則被漏掉 3 次以上，就改提案做成 hook，不是再加規則字數。

### 案例：只記帳、不執法

主代理自己寫了 549 行服務類別之後，我的第一反應是把委派規則寫得更詳細。但這樣只是第 1 層。後來補上的是：

- 一個 hook 即時記帳（記錄主代理親自編輯了哪些程式碼檔）。
- 硬擋：記帳只是記錄，要真的能攔住才算數。
- 偵測缺口的補洞：後來又發現「唯讀跨檔分析加方案比較」這種越線形態，沒有寫程式碼卻做了重度分析，需要另外設計偵測，不能混在同一條規則裡。

另一個相關案例是「硬上限」（Hard Cap，同一件事重試或擴張的次數上限）：第一版只有記帳器，沒有硬擋。**只記帳不執法，等於軟性宣告。** 觸發條件滿足了，沒人看，這張卡就失效。

### 案例：護欄的漏洞

我也用 hook 擋危險的 git 指令與環境寫入，這類黑名單護欄有幾個固定的漏洞型態：

- 只比對字串，沒看真正要執行的指令與目前分支。例如 hook 把 worktree 裡的功能分支誤判為主分支，還掃到 heredoc 裡的文字。
- 管線、heredoc、重導向是常見繞過：「把內容用管線餵進 `kubectl exec`」就繞過了「指令含重導向符號」的判法。
- worktree 底下的 git 路徑語意不同，主 checkout 與其他 worktree 共用 stash 堆疊，裸 `git stash` 會互相踩到。我最後把規則寫成：身處 worktree 卻執行不帶唯一標記的 `git stash`＝違規，並且要把規則放進子代理的 prompt，因為它們不一定繼承主代理的常駐規則。

**結論：護欄做黑名單必漏，所以要預期它會漏，並且搭配事後偵測。**

## 自主決策的邊界

我讓 AI 在「實作到審查」這一段自己拍板：遇到「兩條合理路徑擇一」不停下來問我，而是由主代理裁決並寫進決策日誌，審查時再覆核。這樣速度快很多。

但這個設計出過一次問題。

### 事故：自己決定擴大權限

一個無頭 worker 需要知道剩餘時間，主代理在決策日誌裡自行裁定：把 `date` 指令列進這個 worker 的內建允許清單。按設計，這段不用停等，所以當下沒人擋。

後來 Deep 審查的安全通道實測：`date -f <檔案>` 可以逐行印出任意可讀檔的內容，推翻了這個決定。該權限連同相關功能一起移除，未上線，只是進過分支提交。同一個任務裡還有兩項同型決策也是到審查才定案：讀 issue 留言時沒有作者信任過濾、暫存提交用 `--no-verify`。

稽核的判讀是：決策日誌把「兩條合理路徑擇一」都交給主代理，但**沒有區分「擴大工具權限／放寬信任邊界」這一類**。審查是事後才發生。

建議的規則是：涉及這三類的決策，不得只在決策日誌拍板，先派安全小審或停下來問我：

1. **擴大工具權限**（允許清單、跳過權限檢查）。
2. **讀取不可信輸入**（外部留言、使用者貼的內容）。
3. **跳過 hook**（`--no-verify` 之類）。

### 我的決定：先不改制度

查核之後我做了一個決定，值得如實記錄：**不改制度，卡片結案。** 理由是：

- 決策日誌加審查把關，按設計運作了。決策日誌那一列寫的是「請審查覆核」，審查也在合併前擋下了。
- 缺口只是「放寬權限的決策沒被點名交安全通道、實作繼續疊在它上面」，代價是重工，沒有實際暴露。
- 日後同型決策若在審查前就造成實際暴露（上線，或在真環境放寬權限），再重提。

這個決定我覺得也是一種規則設計：**不是每個事故都要加規則。** 規則本身有成本（常駐、維護、被誤用）。代價是「重工」而非「暴露」的缺口，可以先記下重提條件，等真的有暴露再加。

### 另一個邊界：範圍清單是預估，不是事實

委派時我會給子代理一份「允許修改的檔案清單」。有一次這份清單被當成既定條件，導致裁決時選了折衷設計，我一眼就看出錯了。教訓是：**範圍清單是「預估」，不是「事實」。** 裁決時先問「如果清單錯了，最佳解是什麼」，再回頭看清單要不要改。

## 常駐規則怎麼不無聲長胖

「常駐」是每個 session、每個子代理都要整份載入的規則。它的成本比隨需載入的規則高一個數量級，所以需要三道「進水閥」。

### 1. 常駐只留判法，敘述落報告

一條約束的常駐佔位上限＝規則句加違規判法。判準問一句：**這段拿掉後，執行者還分不分得出自己有沒有違規？** 分得出，就不屬於常駐層。

背景、事故經過、設計理由，搬到歷史檔或報告。我的做法是：規則檔只留「規則句、判法、正反例」，敘述寫進對應的歷史檔。

### 2. 新增要抵銷

加一條就要指出等量空間從哪來：退場已內化的鷹架、敘述搬走、合併重複。**禁的是無聲長大。**

### 3. provenance 從簡

常駐層只記「誰拍板、何時」一句；理由放報告。更重要的是，**不寫「以前不是這樣」。** 只有看過舊版的人才讀得懂的句子，對讀者是雜訊：他手上只有現行檔案，那句話提到的欄位、章節、做法在他眼前並不存在，他的反應是「我是不是漏看了什麼」。

判斷一個子句該不該刪的兩個問題：

- Q1：句子提到的舊東西，現行設定裡找得到嗎？找得到，不違規。
- Q2：這句話有給讀者接下來該做什麼嗎（現行路徑、替代工具、判斷依據）？有，不違規。

Q1 找不到、且 Q2 沒有，就刪。變更史交給 `git log`。

### 樓層放錯，比內容太多更貴

我一度以為要瘦常駐層就是「砍字數」。實測才發現：

- **放錯樓層**的內容（一份命令列工具的指令手冊，躺在硬約束那一層）：4,843 bytes，佔常駐鏈 12.5%。
- **舊世代鷹架**（為舊模型寫、新模型不需要的指令）：490–820 bytes，佔 1.3–2.1%。

差了約 6 倍。所以我的自檢清單把這題排第一：「這段有沒有規定執行者該做什麼或不該做什麼？沒有，它就不是約束，該搬樓層。」**搬不是刪**，內容本身有價值，錯的是位置。

另外一個提醒：只用 grep 找「按需注入」這類關鍵字，對那份命令列手冊回傳零命中，因為它從頭到尾沒寫過那幾個字。**必須問判定問句，不能只靠字串搜尋。**

### 路由表

常駐層只放一張「觸發 → 載入哪個檔」的路由表。例如：

| 觸發 | 載入 |
|---|---|
| 委派子代理前 | 委派守則 |
| 猶豫「完成了嗎」「該問嗎」 | 判斷力 rubric |
| 修改規則檔前 | 維護協議 |
| 要寫報告前 | 文件輸出規範 |

真正按需載入，比「行內條件區塊」徹底：後者還是整份進 context。

### 門檻本身也要有根據

2026 年 8 月我重新檢討「常駐層六個大小門檻」，發現三個問題：度量單位、管轄範圍、執法方式都與目的不符。起因是一次小事：為了讓一條經 A／B 驗證的規則落地，我得先挪出 85 bytes。**85 bytes 約等於 20–30 個 token，大約是一百萬 token 視窗的 0.003%**，為了它搬動三段制度檔的敘述，根本不划算。

我在乎大小是因為 session context，所以度量單位應該是「開場固定成本（token）」，不是檔案 bytes。後來改成量 token，並且約定：**門檻凡屬「改數值」或「改度量」，落地後要能證明真的降低了每輪成本，不能只憑換了度量單位就宣稱改善。**

驗證的例子：我替某個外部工具的允許清單瘦身，改前均值 72,375 token（重複量測的散度約 111–338），改後 70,728，差 1,650，遠大於散度，所以是真實下降。**差值落在散度內，就該回滾。**

## 換模型世代時，重審提示詞

寫給舊模型的鷹架，換了新模型之後常常反效果。我把這類內容整理成六種（舊模型的 scaffolding）：

| 類型 | 例子 | 處理 |
|---|---|---|
| 預期防呆 | 列出「模型可能善意誤觸、但其實不會」的防呆 | 刪（新模型字面遵循，不自行推論，這類變噪音） |
| 原生能力的 scaffolding | 強制每 3 次工具呼叫摘要、強制「先想再答」 | 改用 effort 參數或原生行為 |
| 過度保守措辭被字面執行 | 審查指示「只報高嚴重度、別挑小毛病」 | 改具體門檻（例如「會造成錯誤行為或測試失敗才報」）；新模型更忠實遵守，召回率反而下降 |
| 防過短措辭 | 為舊模型「回覆太短」寫的擴寫指示 | 刪；新世代預設偏長，現在要的是長度框 |
| 過期的 effort 描述 | 「max 邊際遞減」 | 更新為當時實測 |
| 驗證指示 | 「再驗證一步」「用子代理驗自己」 | 刪（新模型會自動自驗，反而過度驗證）；但「宣稱要綁證據」這類反捏造的規則保留 |

豁免：不可逆操作與安全硬約束（git 破壞性操作、脫敏、強制停點）、語言與偏好硬約束，這些與模型能力無關，不算 scaffolding。

**關鍵提醒：同一世代內重掃，收益急遽遞減。** 2026 年 7 月底換代那輪已經掃過的常駐鏈，隔十來天（8 月初）再掃，只剩一處乾淨命中（490–820 bytes）。這是同世代重掃的預期基準。委派方預期挖到大量，執行者就會把不屬於這個類型的條款硬湊進裁撤清單。所以我在規則裡明寫：換模型世代時才重跑，同世代不重複。

### 評估與瘦身：通用知識每次載入都佔 context

2026 年 10 月，我還做過一次 skill 盤點：61 支 skill，逐支分成「通用知識（模型本來就會）」「團隊專屬事實」「行為約束」三類。三個子代理平行讀完後的建議是：保留 36、瘦身 18、棄用 6、合併 1。我依建議執行：封存 7 支，瘦身 18 支（只刪通用段落，frontmatter 與備份逐位元組相同）。

判定的方法是一句話：**「Claude 不讀這段也會嗎？」會，就刪。**

要誠實標記的限制：

- 分類是**推論**，不是行為量測。
- 瘦身後的行為層 A／B 我**沒有跑**，表現若變差，要從備份還原。
- 豁免也要留：真團隊客製（反慣例的約定、專案特有的 enum 與命名、與通用做法相反的決策）必須保留，因為這正是模型猜不到的部分。

## 規則修改本身的流程

改規則是高賭注，所以我把「怎麼改」也寫成規則。

### 權限分級

不同檔案的修改權限不同。判法是：同一個目標同時命中兩列時，要先問的那一列勝出。我的安全規則檔屬於「規則檔，可自行改」，但被另一列點名「要先問」，所以要先問。**整張表讀完再決定，不要命中第一列就動手。**

### 修訂閘

改常駐規則後必跑：

1. **自動測試**：斷言關鍵約束句仍在、量開場固定成本。失敗就先還原。
2. **新鮮 context 的子代理驗收**，只驗三件事：每條指針（檔案加章節）解析得到、規則間沒有語意衝突、標注「經實驗定稿」的措辭沒被無證據改寫。
3. **提示詞肥胖稽核**：對照一份肥胖樣式清單（歷史脈絡、負面表列重複、範例堆疊、強調符通膨、通用知識內嵌、過度剛性規約、舊世代鷹架、相對舊版的變更說明）。

**驗收一律讀磁碟**：禁用「問子代理 context 裡有沒有這條」。常駐層是開場快照，問 context 會系統性回「沒有」。新鮮 context 驗收有效，是因為它用工具讀檔，與備份比對。

### 其他幾條

- 改完的規則要**新 session 才生效**，本 session 與它派出的子代理都讀不到。
- 被否決或驗不過而放棄的草稿，存進 `rejected/`，附一句理由與日期。日後重提同方向，先讀舊否決。
- 改一個「值」（逾時秒數、路徑、模型名、數量上限）之後，用 grep 掃整個設定目錄與看板卡，**搜尋範圍必須含 hook 與設定檔**，因為 hook 才是實際執法者。
- 看到寫死的上界（例如「M1–M12」）先問「以後會不會增長」，會就改寫成不需要維護的樣子。
- 寫進規則裡的外部數據要查出處。我有一條 skill 寫著「註解與程式碼不一致的改動，引入錯誤的勝算約 1.5 倍（某作者 2024）」，但出處從未核實，而同一份檔案的下一段正在禁止「無法查證的宣稱」。後來我核對了論文（摘要原句與規則寫的一致），補上標題與連結。**規則自己禁止的事，不能自己犯。**
- 新規則落地後，**立刻拿它去跑下一個步驟**，是用最低成本驗證「規則寫得出可操作的樣子」的方法。

## 踩過的坑與教訓

1. **形容詞不是規則。** 「大型」「必要時」「適度」，都換成數字或判定問句。
2. **只有規則文字，遲早被漏。** 同一條被漏 3 次，就考慮 hook，而不是加字。
3. **只記帳不執法，等於沒執法。**
4. **黑名單護欄必漏。** 預期它會漏，搭配事後偵測。
5. **自主決策要排除三類：擴大權限、讀不可信輸入、跳 hook。** 但不是每個缺口都要立刻加規則，先看有沒有造成實際暴露。
6. **範圍清單是預估。**
7. **常駐層的成本，多半來自放錯樓層，不是字數。**
8. **改度量不等於改善。** 要驗證每輪成本真的降了。
9. **換模型世代才重審提示詞**，同世代重掃收益遞減。
10. **規則要能被驗收。** 驗收一律讀磁碟，不問 context。

## 可直接套用的檢查清單

寫完一條給 AI 的規則，逐項問：

- [ ] 有沒有一句「…＝違規」？寫不出來，規則還沒想清楚。
- [ ] 形容詞換成數字或判定問句了嗎？
- [ ] 判定問句後面附了 2–3 組取自真實事故的正反例嗎？
- [ ] 豁免寫明了嗎？
- [ ] 三層執法（規則文字、自驗證、事後偵測）各自在不在？缺的當下講明白了嗎？
- [ ] 這段是「行為約束」嗎？不是的話，它該搬出常駐層。
- [ ] 有沒有「以前是 X」的對照子句？有就刪，換成現行做法。
- [ ] 常駐層新增了，有抵銷嗎？
- [ ] 數字門檻有校準依據嗎？覺得不對時走修改流程，不是心裡放寬？
- [ ] 外部引用的數據、論文查過出處嗎？
- [ ] 這條規則要不要放進子代理的 prompt？（它們不一定繼承常駐規則）
- [ ] 新模型世代出來後，這條還是必要的嗎？
